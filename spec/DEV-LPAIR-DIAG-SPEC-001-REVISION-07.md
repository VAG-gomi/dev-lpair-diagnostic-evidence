**What this revision changes, in one paragraph:**
REVISION-06 resolved most of the six previous gaps but left four reconciliation defects, all about what missing information does to eligibility and counting. First, an unevaluable Stage-A check could still allow P3 membership whenever no later check happened to catch the missing field — missing door_open_pre, missing protocol metadata, or an unrecorded REPAIRED flag could pass silently. Second, the P- attribute was defined only for unknown paths, leaving known-partial but uncompletable components with P-NOT-APPLICABLE even though their partial consistency was genuinely undetermined, not inapplicable. Third, INVALID-EST-STATE appeared both as a status-line outcome and as a secondary attribute without an explicit rule, stated in every identity, for when it counts as an I0/I1 summand, when it counts only as an attribute, and where its waste appears in the I3 summation. Fourth, the provenance-omission rules were not operationally consistent: the specification allowed K3-FULL under a recorded True flag with unknown tuple history while also saying period claims must be UNKNOWN and that omitted provenance defaults K3 subcategories to UNRESOLVED, without stating which omissions permit FULL, which require UNRESOLVED, and which permit fall-through. REVISION-07 corrects all four without redesigning the diagnostic: Stage A gains a three-valued outcome (PASS / FAIL / UNRESOLVED) with deterministic UNRESOLVED-* ledger codes that block P3-final and P4 exactly like failures while never being described as violations; the P- attribute gains a complete domain over all estimate states, with P-UNKNOWN for known-partial uncompletable components and P-NOT-APPLICABLE reserved for the genuinely inapplicable full-estimate case; INVALID-EST-STATE counting is made explicit in I0, I1, F/Q, I3, flow, and Table C via a single-counting rule plus a separate attribute cross-tabulation; and provenance omissions are governed by a precise conditional table built on flag sufficiency (a recorded, non-contradictory True flag suffices for FULL/fall-through classification; period-value claims remain UNKNOWN) that replaces the blanket "omitted provenance defaults to UNRESOLVED" wording.

## 2. Stage-A rule for PASS, FAIL, and UNEVALUABLE — deterministic final eligibility (supersedes REV-06 §5.1 Stage-A outcome rule, §5.2 unevaluable paragraph, §5.4 I5/P4 in part; deliverable: complete Stage-A rule with deterministic final episode eligibility and accounting)

### 2.1 Check-evaluation statuses and the presence-vs-comparison distinction (binding)

Every Stage-A check (A1–A6, REV-06 §5.1, retained in substance and order: A1 PROTOCOL → A2 SEQUENCE → A3 TRANS-PATH → A4 INVALID-RECORD → A5 WASTE-UNDEFINED → A6 REPAIRED), applied to a step, boundary, or pair as applicable, returns exactly one of **PASS**, **FAIL**, or **UNEVALUABLE**:
- **FAIL** means: the check was evaluated on recorded fields and the recorded values violate the check's condition (demonstrated deviation or demonstrated invalidity/computability failure, as defined per check in §2.2).
- **UNEVALUABLE** means: the check could not be evaluated for that step/boundary/pair because a field needed for the check is missing (absent / NOT-RECORDED / Unknown where the check requires a recorded value). UNEVALUABLE is never FAIL (retained from REV-06 §5.2, now completed by the final-outcome rule in §2.3).
- **PASS** means: the check was evaluated and the recorded values satisfy its condition.

**Presence-vs-comparison distinction (binding — this is what makes the per-check table in §2.2 principled rather than ad hoc):**
- A **presence check** asks whether required fields are present (and, where applicable, internally consistent on their face). For a presence check, a missing required field **is** the failure: the condition "fields present" is false. Presence checks therefore return FAIL (never UNEVALUABLE) on missing fields. In Stage A, the presence check is **A4 (T0 INVALID-RECORD)**: missing position_before / missing action / missing t_pre ⇒ FAIL for that step (the step is INVALID-RECORD). The consistency part of A4 (recorded phase vs t_pre phase) is a comparison and follows the comparison rule below — see A4 row in §2.2.
- A **comparison check** asks whether recorded values agree with a specified value, derivation, or predecessor/successor value. For a comparison check, a missing field needed for the comparison means the comparison cannot be performed ⇒ **UNEVALUABLE** (never FAIL, never PASS-by-default). In Stage A, the comparison checks are A1 (protocol comparisons needing S / ordering metadata / boundary positions), A2 (continuity comparisons needing predecessor/successor fields), and A3 (TRANS-PATH comparisons needing position_before / position_after / action / t_pre / door_open_pre). A5 (waste computability) is a computability check, not a comparison: missing needed field ⇒ FAIL (waste cannot be computed — computability fails on absence, like presence). A6 (REPAIRED status) is a status check: flag recorded True ⇒ FAIL (repaired); flag recorded False for all steps ⇒ PASS; flag unrecorded ⇒ UNEVALUABLE (status cannot be established).
- **No derivation/substitution rule (binding):** for conformance checks (A1–A3), a missing recorded field must never be replaced by a derived value, a default, or a value from another field. In particular, a missing recorded door_open_pre must not be replaced by the true-schedule derivation (t_pre mod 20 < 10): derivation would substitute the specification for the record and defeat the check's purpose, which is to verify the record against the specification. Derived values may be used only where a rule explicitly defines them as the comparison target (e.g. true periodic features, blocked_spec derivations from recorded path fields — those derivations use recorded fields as inputs; they do not fill missing recorded fields). A check whose inputs include a missing recorded field is UNEVALUABLE, full stop.

### 2.3 Final Stage-A outcome — two-tier determination (binding; supersedes REV-06's "first failing check" as the sole rule)

For each failed episode in scope, evaluate A1–A6 per §2.2, then determine the episode's single final Stage-A status by this two-tier rule (tiers in order; within a tier, check order A1→A6):
- **Tier 1 — FAIL tier:** if any check returns FAIL, the episode's final status is **FAIL** with reason = the first failing check in A1→A6 order (PROTOCOL / SEQUENCE / NONCONF-PATH / INVALID-RECORD / WASTE-UNDEFINED / REPAIRED — REV-06 codes, retained). FAIL in any check dominates UNEVALUABLE in any check, regardless of check order: a demonstrated failure excludes the episode on demonstrated grounds even if another check is unevaluable (e.g. A3 mismatch + A6 flag unrecorded ⇒ NONCONF-PATH, not UNRESOLVED-REPAIRED; A5 missing position_after + A1 S missing ⇒ WASTE-UNDEFINED, not UNRESOLVED-PROTOCOL).
- **Tier 2 — UNRESOLVED tier (only if no check FAILs):** if any check returns UNEVALUABLE, the episode's final status is **UNRESOLVED** with reason = the first unevaluable check in A1→A6 order, coded UNRESOLVED-PROTOCOL / UNRESOLVED-SEQUENCE / UNRESOLVED-TRANS-PATH / UNRESOLVED-INVALID-RECORD / UNRESOLVED-WASTE / UNRESOLVED-REPAIRED. (UNRESOLVED-SEQUENCE and UNRESOLVED-WASTE are defined but unreachable under current definitions per §2.2 — they appear in the code set and in the I5 identity as zero terms, not as assignable reasons in practice.)
- **Tier 3 — PASS:** if every check returns PASS, the episode's final status is **Stage-A PASS** (proceeds to Stage B; REV-05 §5.1 Stage-B/C definitions retained).
- **Language rule (binding):** UNRESOLVED episodes must be described as "Stage-A eligibility not established (reason: UNRESOLVED-*)" — never as "failed", "violated", "nonconformant", or "excluded for violation". The distinction between demonstrated failure (Tier 1) and insufficient evidence (Tier 2) is part of the finding and must survive into summaries, abstracts, and Table C captions: a summary stating "N episodes failed Stage A" must state the FAIL/UNRESOLVED split (N_FAIL + N_UNRESOLVED), never merge them into one "failed" count.

### 2.4 Flow, ledger, I5, and P4 updates (binding)

## 3. Complete P- attribute domain — known-partial consistency is no longer hidden (supersedes REV-06 §3.2 P- attribute domain in part; deliverable: revised P- attribute domain and component matrix)

### 3.1 Attribute values and their exact meanings (binding)

The P- attribute answers one question per component: **is the recorded value consistent with the partial path's expectations, where that question is well-posed?** It is recorded for every component (all estimate states), with exactly one value per component. Values:
- **P-CONSISTENT:** recorded value equals the partial expectation, and the partial path is known (est_full = False, completable) or consistent with the value (est_full = Unknown, computable, recorded = partial_exp). Meaning: no partial-path inconsistency is present for this component (under Unknown, this means consistency with the partial path, not proof that the path was partial — see §3.2).
- **P-INCONSISTENT:** recorded value differs from the partial expectation, and the partial path is known (est_full = False, completable). Meaning: partial-path inconsistency **established** (unconditional — path known, comparison complete, values differ). This is the attribute counterpart of component outcome INCONSISTENT-C (same finding, different dimension: outcome = classification, attribute = consistency status — see §3.2 note on intentional mirroring).
- **P-INCONSISTENT-IF-PARTIAL:** recorded value differs from the partial expectation, partial expectation computable, but path unknown (est_full = Unknown). Meaning: inconsistency **conditional** on the partial path (if the path was partial, the value conflicts with its rules; if the path was full, no inconsistency arises). Never asserted unconditionally (REV-06, retained).
- **P-UNKNOWN:** partial-path consistency cannot be determined from recorded provenance. Two sub-cases, distinguished by est_full context (the value is the same; est_full tells you which sub-case applies, so no second value is needed): (a) est_full = False + incompletable — **known partial path, consistency uncheckable** (the owner's case: partial expectation cannot be computed because a necessary provenance field is missing/unknown, so neither consistency nor inconsistency can be established even though the path is known); (b) est_full = Unknown + incompletable — path unknown and expectation uncomputable (both questions undetermined). In both sub-cases, P-UNKNOWN must be cited as "consistency undetermined", never as "consistent", "inconsistent", or "not applicable".
- **P-NOT-APPLICABLE:** partial-path consistency is genuinely not a question for this component — exactly one case: **est_full = True** (full path governs; partial expectations are not applicable to a full-path output, whether the outcome is MATCH or FULL-MISMATCH). No other case uses this value. In particular, est_full = False (completable or incompletable) never uses P-NOT-APPLICABLE after this revision (REV-06's False-branch NOT-APPLICABLE assignment is superseded in full).

## 4. INVALID-EST-STATE counting reconciled — outcome counts vs attribute counts, in every identity (supersedes REV-06 §2.1/§2.3 counting notes and §6.3 list in part; deliverable: updated I0/I1, F/Q, and I3 definitions with explicit outcome-versus-attribute single counting)

### 4.1 Single-counting rule (binding; stated here once, then repeated in each identity below so no identity can be read without it)

**A step contributes exactly one I0 summand: its tree outcome (REV-05 §4.2 tree as amended by REV-06 §2.3 defect precedence D1–D4). A secondary attribute contributes zero I0 summands, zero I1 lines, and zero F/Q rows/columns.** This rule applies to every defect attribute, not only INVALID-EST-STATE: an OPT step carrying K-defect/Q-defect/EST-STATE attributes is counted once as OPT; a HEAD/SEL step carrying a K-defect attribute is counted once as HEAD/SEL; a SUBOPT-UNCLASS step carrying a K-defect attribute is counted once as SUBOPT-UNCLASS; a FIELD-MISSING-PATTERN step (D1 winner) carrying an EST-STATE attribute (D2 also fired) is counted once as FIELD-MISSING-PATTERN. Attribute occurrences are counted only in the attribute cross-tabulation (§4.2), which answers a different question ("how often does attribute A occur, and on which winning outcomes?") and whose totals must never be added to I0/I1/F/Q-outcome totals, averaged with them, or substituted for them.

**INVALID-EST-STATE specifically (the owner's case, stated with all its branches so no branch is left implicit):**
- **As outcome (counts in I0/I1):** timing-critical suboptimal steps where INVALID-EST-STATE wins defect precedence (D2 winner: no D1 FIELD-MISSING, EST-PROV fires — D3/D4 defects, if also firing, are secondary attributes). Such steps contribute **one** summand to n_INVALID-EST-STATE (status line) in I0 and **one** line to n_P1 (status-line section) in I1. Their P3-final-episode waste (where applicable) contributes to waste_INVALID-EST-STATE in I3 (§4.3).
- **As attribute (counts nowhere in I0/I1):** (i) OPT steps with EST-PROV firing (T2 outcome OPT; EST-STATE attribute); (ii) FIELD-MISSING-PATTERN steps with EST-PROV also firing (D1 winner FIELD-MISSING; EST-STATE attribute); (iii) INVALID-K steps with EST-PROV also firing — impossible by precedence (D2 outranks D3, so EST-PROV wins over INVALID-K; this sub-case cannot occur as "INVALID-K outcome + EST-STATE attribute" — if EST-PROV fires, the outcome is INVALID-EST-STATE, not INVALID-K — stated here so a report never lists it); (iv) INVALID-FEAT-RECORD steps with EST-PROV also firing — likewise impossible by precedence (D2 outranks D4); (v) non-timing-critical HEAD/SEL/SUBOPT-UNCLASS steps with EST-PROV firing (T3d outcome; EST-STATE attribute); (vi) K3/availability-class steps with EST-PROV firing — impossible (defect routing precedes §3 outcomes; EST-PROV steps never receive K3/availability outcomes — REV-06 §2.1 strict rule, retained). Such attribute-carrying steps contribute **zero** summands to n_INVALID-EST-STATE and **zero** lines to I1's INVALID-EST-STATE line; they contribute one summand/line under their winning outcome (OPT / FIELD-MISSING-PATTERN / HEAD / SEL / SUBOPT-UNCLASS respectively). Their attribute occurrences contribute **one** cell count each to the attribute cross-tabulation (§4.2: winning-outcome row × EST-STATE-attribute column) and nowhere else.
- **Common error prohibited (explicit):** n_INVALID-EST-STATE ≠ (outcome count + attribute-occurrence count). A report computing an "INVALID-EST-STATE total" by adding outcome steps and attribute-carrying steps double-counts every step that carries the attribute on a non-winning outcome and misstates I0. The only valid totals are: n_INVALID-EST-STATE-outcome (I0/I1) and n_INVALID-EST-STATE-attribute (attribute table) — reported separately, never summed.

### 4.2 Attribute cross-tabulation (new explicit table; answers "attribute occurrences", never "outcome totals")

Define, for each winning outcome O (I0 outcomes: classes, status lines, state/INVALID lines — REV-06 §6 vocabulary, retained) and each defect attribute A ∈ {EST-STATE-attr, INVALID-K-attr, INVALID-FEAT-attr, K-MISSING-attr, Q-DEFECT-attr}, the cell count c(O, A) = number of steps with winning outcome O carrying attribute A. (Secondary means: the defect is present but did not determine the outcome. EST-STATE-attr occurs on FIELD-MISSING-PATTERN outcomes (D1 wins over D2), OPT outcomes, and non-timing-critical HEAD/SEL/SUBOPT-UNCLASS outcomes; it never occurs on INVALID-K, INVALID-FEAT-RECORD, K3-class, or availability outcomes (D2 wins over D3/D4, and defect routing precedes §3 outcomes). INVALID-K-attr occurs on INVALID-EST-STATE and FIELD-MISSING-PATTERN outcomes (higher-precedence defects win), OPT outcomes, and non-timing-critical outcomes; it never occurs on INVALID-FEAT-RECORD outcomes (D3 wins over D4) nor on K-class/availability outcomes (defect routing precedes §3). INVALID-FEAT-attr occurs on higher-precedence defect outcomes (FIELD-MISSING-PATTERN, INVALID-EST-STATE, INVALID-K), OPT outcomes, and non-timing-critical outcomes; it never occurs on K-class/availability outcomes (defect routing precedes §3). K-MISSING-attr occurs on OPT outcomes and non-timing-critical HEAD/SEL/SUBOPT-UNCLASS outcomes (K-missing secondary to the Q-branch outcome); it never occurs on timing-critical defect outcomes (D1 makes K-missing the outcome there) nor on K-class/availability outcomes (which require K fields present). Q-DEFECT-attr occurs on OPT outcomes (T2), K-defect outcomes (T3a, where the K-defect wins and Q-defect is secondary), and K-class/availability outcomes (T3b, where the outcome is determined by K and Q-defect is irrelevant to it); it never occurs on HEAD/SEL outcomes (which require Q present) nor, as an attribute, on SUBOPT-UNCLASS outcomes (where Q-defect is outcome-defining via T3c/T3d, already captured by the SUBOPT-UNCLASS outcome count — counting it again as an attribute would mix outcome-defining with secondary occurrences). The Q-DEFECT-attr column total is therefore not n_Q: n_Q (F/Q cross-tabulation) counts all Q-missing steps including SUBOPT-UNCLASS outcomes, while the attribute column counts secondary occurrences only.)
- **Row sums:** Σ_A c(O, A) = total attribute occurrences on outcome-O steps (a step carrying two attributes contributes 2 to its row sum — row sums are occurrence counts, not step counts, and must never be equated with n_O).
- **Column sums:** Σ_O c(O, A) = total occurrences of attribute A (e.g. Σ_O c(O, EST-STATE-attr) = n_INVALID-EST-STATE-attribute). Column sums are occurrence totals, never I0 summands.
- **Non-additivity rule (binding):** for any outcome O and attribute A, n_O + c(O, A) is not a meaningful total (it adds steps to occurrences); Σ_O n_O (= total_recorded) and Σ_O Σ_A c(O, A) (= total attribute occurrences) are totals over different units (steps vs occurrences) and must never be summed, averaged, or compared as if commensurate. Reports must label attribute-table totals "occurrences", never "steps", unless the cell is provably single-attribute-per-step (which the table does not assume).
- **F/Q interaction (explicit):** the F/Q cross-tabulation (REV-06 §4, retained) has rows = winning outcomes only. Attribute occurrences do not create F/Q rows or columns. Q-availability (F/Q membership) is a step property determined by Q-field presence (§4.1 REV-06 definitions, retained): a step with Q-DEFECT-attr is Q-missing (F/Q column Q) by definition of the attribute — consistent, not double-counted: the step appears once in the F/Q table (winning-outcome row × Q column) and once per attribute in the attribute table (different tables, different questions). An EST-STATE attribute does not affect F/Q membership (estimate-state ≠ Q-availability): an OPT step with EST-STATE attribute and Q present appears in the F/Q table under OPT × F, and in the attribute table under OPT × EST-STATE-attr — once in each table, never twice in either.

## 5. Provenance omissions made operationally consistent — flag sufficiency, UNKNOWN claims, and the corrected collection-authorisation sentence (supersedes REV-06 §8 decision 8(e) blanket wording in part; deliverable: revised provenance-omission rules aligned with OQ-4 and collection authorisation)

### 5.1 Flag-sufficiency principle (binding; this is the rule that resolves the owner's item 4)

**A recorded, non-contradictory R-EST-CUR flag suffices for classification.** Classification (component outcomes, step outcomes, K3-FULL/fall-through assignment) uses the recorded estimate state as stated, provided no EST-PROV contradiction fires (REV-06 §2.1, retained) and no gate contradiction fires (REV-06 §2.3, retained). In particular:
- R-EST-CUR = True recorded + no EST-PROV contradiction + recorded features ≠ true ⇒ **K3-FULL permitted** (KF1), regardless of tuple status (UNKNOWN permitted) and regardless of period omission (no R-PERIOD field exists — period omission is not a contradiction and not a blocker for classification).
- R-EST-CUR = True recorded + no EST-PROV contradiction + recorded features = true ⇒ **fall-through permitted** (KF2), on the same permissions (tuple UNKNOWN permitted; period omitted permitted).
- The flag's sufficiency is for **classification only**: it establishes, for classification purposes, that the model is treated as being in full-estimate state at that step. It does **not** establish any claim about the period value, the period's correctness, or the estimates' internal composition — those claims are governed by §5.2 (UNKNOWN list) and are not made by KF1/KF2 rows. A KF1 row therefore asserts "recorded periodic features differ from true periodic features under a recorded full-estimate state" — never "the model's period estimate was X" or "the model's period estimate was correct/incorrect".
- **Why flag sufficiency is sound (stated so it can be challenged):** K3-FULL's comparison is recorded-features vs true-features. Neither the tuple (history) nor the period value enters that comparison: the tuple constrains whether True *could* be recorded (EST-PROV — a contradiction check, not a permission requirement: UNKNOWN history cannot contradict True, so it cannot block it), and the period value constrains *why* the recorded features have their values (a mechanism/explanation question, not the classification comparison). Requiring tuple or period provenance for FULL classification would conflate the classification comparison with its explanation — the same conflation this revision series has repeatedly removed (cf. REV-05 §3.1 governing principle: full expectations are world-referential in the sense that recorded periodic features are compared to true features; the comparison does not require the estimates' internal values). Conversely, EST-PROV contradictions *do* block classification, because a contradictory state record means the flag itself cannot be trusted as stated — contradiction is a defect in the record, while omission is an absence in the record, and only the former defeats the flag.

### 5.3 KF1/KF2 conditions restated with omission permissions (complete in one place; supersedes REV-06 §3.4 tuple condition as the sole statement)

- **KF1 (K3-FULL) permitted iff ALL of:** (i) R-EST-CUR = True recorded; (ii) no EST-PROV contradiction (tuple not VERIFIED-contradictory per REV-06 §2.1 clause (a); held values not NONE-GENUINE-contradictory per clause (b) — open_len/last_opening; period not checkable, §5.2); (iii) K fields present, no K-defect (tree preconditions, REV-05 §4 as amended by REV-06 §2.3); (iv) recorded features ≠ true for at least one component (FULL-MISMATCH per REV-05 §3.2 True rows). **Permissions (explicit):** tuple UNKNOWN permitted; tuple VERIFIED with first_ord ≤ current ordinal permitted; period omitted permitted; partial provenance omitted permitted (irrelevant under True — full expectations govern); VAL/AVAIL omitted permitted (gate inapplicable, not blocking — §5.2). **Blocks (explicit):** tuple VERIFIED NEVER or VERIFIED before-first (EST-PROV); held open_len/last_opening NONE-GENUINE (EST-PROV); K-defect (tree routing); recorded = true (→ KF2, not KF1).
- **KF2 (fall-through, est_full True) permitted iff ALL of:** (i)–(iii) as KF1; (iv) recorded features = true for both components. Same permissions and blocks as KF1 (with (iv) inverted). Note: KF2 asserts value-correctness under a recorded full state; it asserts nothing about period correctness (§5.2) and nothing about tuple/period provenance completeness.
- **General permission rule (binding, all rows):** provenance omission **permits** an outcome iff the outcome's defining comparison does not require the omitted field; it **blocks** an outcome iff the outcome's defining comparison requires the omitted field and no alternative comparison defines the outcome. Corollaries (stated so the rule can be applied without re-derivation): true-matching fall-through (any est state) is never blocked by omission (value-vs-true comparison needs recorded features + true features only — both available by definition of the row); partial-match fall-through (False + completable) is blocked by partial-provenance omission (comparison needs partial_exp — omission ⇒ incompletable branch, true-comparison outcomes instead); FULL is never blocked by tuple/period omission (comparison needs recorded features + true features + recorded True flag only); UNRESOLVED-C is the outcome *for* omission cases where a true-difference is demonstrated but attribution needs the omitted field (Unknown est; False + incompletable) — omission there is outcome-defining, not outcome-blocking.
