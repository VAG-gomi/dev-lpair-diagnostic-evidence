## 2. T0 presence failure and K = 0 — two qualifications (R9-01, R9-07)

### 2.1 T0 presence failure vs missing recorded phase (governing; corrects REV-08 §2.1(c))

REV-08 §2.1(c) is corrected as follows. The sentence (or any equivalent sentence) stating that a FIELD-MISSING-PATTERN exit "includes a T0 presence failure" is **superseded and must not be cited**. The governing rules, restated completely so no cross-reference to the superseded sentence is needed, are:

- **Missing T0 identity/ordering field** (T0-P fails, per REV-08 §4.1 presence set excluding recorded phase, `door_open_pre`, and `position_after`, retained): tree outcome **INVALID-RECORD**. Stage-A contribution: A4-P FAIL INVALID-RECORD (FAIL tier). This case is a presence failure of the step's identity/ordering fields, without which the step cannot be placed in sequence; it is not a field-missing pattern outcome.
- **T0 presence fields complete, recorded phase missing** (T0-P passes, T0-C/A4-C unevaluable for that step): tree outcome **FIELD-MISSING-PATTERN**. Stage-A contribution: A4-C UNRESOLVED-INVALID-RECORD (UNRESOLVED tier, subject to A4-C aggregation in §4.2 and episode two-tier determination). This case is a missing **feature** value, not a missing identity field; the step can be placed and counted, but its phase consistency cannot be evaluated.
- **Recorded phase present but inconsistent with the phase derived from `t_pre`** (T0-P passes, T0-C/A4-C demonstrated inconsistency): tree outcome **INVALID-RECORD**. Stage-A contribution: A4-C FAIL INVALID-RECORD (FAIL tier, subject to A4-C aggregation in §4.2).

These three cases are exhaustive for Check T / Check A4 as defined in REV-08 §4.1 (retained, with A4-C aggregation added in §4.2 below). No other T0-related tree outcome exists. In particular, FIELD-MISSING-PATTERN in the tree arises from missing **feature** fields (including recorded phase under the second case, and other missing feature/provenance fields under the existing FIELD-MISSING-PATTERN bridge, retained) — never from a T0 identity/ordering field failure. A report that counts a T0-P-failure step as FIELD-MISSING-PATTERN in I0 must be corrected to INVALID-RECORD; a report that counts a missing-phase step as INVALID-RECORD in I0 must be corrected to FIELD-MISSING-PATTERN (per REV-08 §4, retained).

**Audit note (for §9).** Every description of T0 presence failure, missing recorded phase, and FIELD-MISSING-PATTERN in REV-08 §§2.1(c), 4.1–4.3, §1 R8-03 row, and §6 audit rows concerning A4/T0 was checked against the three cases above. The only description found to contradict them is REV-08 §2.1(c)'s inclusion of T0 presence failure in FIELD-MISSING-PATTERN, corrected here. REV-08 §4.1–§4.3, the R8-03 row, and the §6 A4/T0 rows already agree with the three cases and are retained (with A4-C aggregation added in §4.2, which does not change any single-step case above — it governs only how multiple steps' A4-C results combine within one episode).

### 2.2 K_rec = 0 rule, qualified before the availability outcomes (governing; corrects REV-08 §2.1(b))

REV-08 §2.1(b) is corrected as follows. Its opening statement is replaced by the qualified rule below, stated **before** any availability-state outcome is listed, so the exception cannot be missed or read as an afterthought:

> **Qualified K_rec = 0 rule.** Except where KX2a fires, a K_rec = 0 step is classified as an availability state (KBLANK, KNEVER, KUNK, K-STATUS-UNKNOWN, or a phase-only sub-state, per the REV-07/REV-08 availability table, retained). **Exception (KX2a, governing):** if `est_full_cur = True` and K_rec = 0, the step outcome is **INVALID-K** (K-gate defect: full-estimate status combined with K = 0 is contradictory, per REV-06 §2 / REV-07 §5, retained), and **no availability-state outcome is assigned** to that step. The step is counted in I0 as INVALID-K (one summand), not as an availability state and not as both. Availability fields for a KX2a step (which raw features were available, which were missing) may be reported descriptively in the step's record, but descriptive availability reporting is not an outcome assignment and must not be summed into any availability-state count.

**Precedence stated explicitly.** K-gate defect determination (KX2a) precedes availability-state assignment in the tree order for K_rec = 0 steps: the gate is evaluated first, and if it fires, availability assignment does not occur as an outcome. This precedence is consistent with defect precedence D1–D4 in substance (gate defects are defect outcomes, not availability outcomes) and with REV-08 §2.1(b)'s own later sentence (now promoted to the opening qualification, not left as a trailing exception). For `est_full_cur = False` or Unknown with K_rec = 0, KX2a does not fire (KX2a requires True), and availability-state classification applies as in REV-08 §2.1(b) (retained). For `est_full_cur = True` with K_rec = 1, KX2a does not fire, and §3 comparison applies as in REV-08 §3 (retained, with tuple handling in §3 below).

**No dual assignment (governing).** No step receives both an availability-state outcome and INVALID-K for the same winning tree classification. A report that lists a True + K_rec = 0 step in both an availability count and an INVALID-K count double-counts it and violates the single-counting rule (REV-07 §4, retained). The correction is to count it once, as INVALID-K, with availability reported descriptively only.

## 3. Estimate-tuple omission and unclassified-pending — one governing rule, scoped (R9-02, R9-06)

REV-08 §3.4's blanket statement — that if the estimate tuple is omitted and EST-PROV clause (a) cannot be evaluated, the step must not receive a §3 component outcome — is **superseded** by this section. The replacement does not revoke flag sufficiency, does not treat missing information as proof that a contradiction is absent, and does not extend the True-branch exception to False/Unknown by implication. Each estimate state's rule is stated independently, from its own logic.

### 3.1 The question, stated precisely

EST-PROV clause (a) (REV-06 §2.1, retained as a firing rule) fires when a recorded `est_full_cur = True` contradicts VERIFIED first-estimates provenance: VERIFIED NEVER tuple, or VERIFIED first-estimates ordinal later than the current ordinal. Clause (a) can fire only on VERIFIED tuple data. If R-EST-TUPLE is omitted (NOT-RECORDED) or Unknown, clause (a) cannot be evaluated: it has neither fired nor been shown not to fire. The question is therefore not "does omission prove no contradiction?" (it does not), but "may the step nevertheless enter §3, and if so, with what status for the unevaluated check?" The answer differs by estimate state, because the states assert different things.

### 3.2 Governing rule — tuple omission does not by itself block §3 entry, with a flagged exception under True

**Rule (governing, all estimate states).** Omission of R-EST-TUPLE, by itself, never blocks a step from entering §3 comparison. What omission does, in each state, is stated in §§3.2–3.3 and summarised here:

- **Under True (§3.2, exception E-TUPLE):** classification (KF1/KF2) is permitted, but EST-PROV clause (a) is recorded as **UNEVALUABLE**, never as PASS, and the KF outcome carries the flag `EST-PROV-(a)-UNEVALUABLE` alongside it. The flag means: "history-type contradiction not checked (tuple omitted); contradiction neither demonstrated nor excluded." A report must never cite a flagged KF outcome as evidence that the history check passed, that no history contradiction exists, or that the full-estimate state is verified against history. Flagged KF outcomes are counted in I0/I1 via their step outcome (K3-FULL for KF1, pattern outcome for KF2 fall-through) exactly as unflagged outcomes with the same step outcome are (the flag is an attribute, zero additional summands, per single-counting, REV-07 §4, retained) — the flag qualifies the *claim* about the outcome, not the *count* of the outcome.
- **Under False (§3.3, independent reason):** classification (partial comparison / MATCH-TRUE / UNRESOLVED-C per REV-08 §3) is permitted, and clause (a) unevaluability is **not** a flagged exception for the §3 outcome, because clause (a) cannot fire against False in the first place (False-side asymmetry, REV-06 §2.1, retained: False never contradicts VERIFIED history, since estimates may be losable / not yet appeared). What remains UNKNOWN under False + tuple omission is first-estimates **timing** (which affects K_rec = 0 availability assignment → K-STATUS-UNKNOWN only, per REV-07 §5.2, retained), not the K_rec = 1 partial/value outcomes. Tuple omission under False therefore requires no exception: there is no True-branch rule being extended, because the True-branch rule (contradiction check on a True claim) has no False analogue.
- **Under Unknown (§3.3, independent reason):** classification (MATCH-TRUE / UNRESOLVED-C by true comparison, with P- attribute per REV-08 §2.2) is permitted, and clause (a) unevaluability is likewise not a flagged exception for the §3 outcome, because Unknown asserts no full-estimate claim for clause (a) to contradict. What remains UNKNOWN under Unknown + tuple omission is first-estimates timing and full-estimate existence (the Unknown branch itself, per REV-07 §5.2, retained). Tuple omission under Unknown therefore requires no exception either: the outcome already carries UNKNOWN in its estimate state, and the report must not upgrade that UNKNOWN to a history-checked claim.

**Why this is not "omission = pass".** Under True, the permitted classification rests on flag sufficiency (REV-07 §5.1, retained, now stated as exception E-TUPLE): clause (a) is a **contradiction check** — it can only *defeat* a True flag when it fires on VERIFIED data. Omission cannot fire it, so omission alone cannot defeat the flag. That is the entire content of the exception. It does **not** assert that clause (a) would pass if the tuple were recorded; it does not assert that the recorded True flag is historically correct; and it does not convert the outcome into a verified-history outcome. The UNEVALUABLE flag exists precisely to prevent those three misreadings. Any report that drops the flag when summarising flagged KF outcomes misrepresents the outcome's status and must be corrected.

**What still blocks §3 (boundary, see §3.4).** Tuple omission does not block §3. Other omissions may still block or redirect §3, under §3.4's scoped boundary: (i) a demonstrated contradiction (EST-PROV firing on VERIFIED data, or held NONE-GENUINE values under clause (b)) routes to INVALID-EST-STATE before §3, regardless of tuple status; (ii) a missing comparison input (recorded value, K flag, or required partial provenance for the computable branch) makes the relevant comparison incomputable, with the outcome determined by the matrix's incomputability branch or by FIELD-MISSING-PATTERN where the tree so provides — never by assuming the missing input's value; (iii) a missing gate input that leaves K-defect status undetermined is handled by §3.5 (pending flag + independently determined tree outcome), not by forcing a §3 outcome. Tuple omission is none of (i)–(iii) for §3 entry purposes, which is why it is excepted here while (i)–(iii) are not.

### 3.3 Independent False and Unknown rules (stated without reference to the True exception)

- **False rule (governing).** `est_full_cur = False` + R-EST-TUPLE omitted or Unknown: the step enters §3 under REV-08 §3 (partial comparison if computable, value comparison if incomputable). EST-PROV clause (a) is **not applicable** to a False claim (it checks True claims against history), so its unevaluability is not recorded as an exception flag on False outcomes. The UNKNOWN that must be recorded under False + tuple omission is: first-estimates timing UNKNOWN (affects only K_rec = 0 availability → K-STATUS-UNKNOWN; does not affect K_rec = 1 outcomes) and, where partial provenance is also omitted, partial consistency P-UNKNOWN (per REV-08 §2.2). A False outcome must never be cited as evidence about first-estimates timing.
- **Unknown rule (governing).** `est_full_cur = Unknown` + R-EST-TUPLE omitted or Unknown: the step enters §3 under REV-08 §3 (value comparison MATCH-TRUE/UNRESOLVED-C; partial comparison determines the P- attribute only, conditionally). EST-PROV clause (a) is **not applicable** to an Unknown claim (it checks True claims), so its unevaluability is not recorded as an exception flag on Unknown outcomes. The UNKNOWN that must be recorded is the estimate state itself (Unknown) plus, where applicable, P-UNKNOWN for incomputable partial comparisons. An Unknown outcome must never be cited as evidence that full estimates did or did not exist at that step.

**Explicit non-extension clause (governing).** The True-branch exception E-TUPLE must not be cited as authority for any False or Unknown classification. False and Unknown classifications rest on §§3.3's independent reasons above. A future revision that changes the True exception does not, by implication, change the False or Unknown rules, and vice versa; each must be amended explicitly.

### 3.4 Scoped pre-§3 boundary (supersedes REV-08 §3.4 blanket prohibition)

REV-08 §3.4 is replaced by the following scoped boundary. Two kinds of unevaluability must be distinguished; only one blocks §3 outcomes:

- **(C) Contradiction-check unevaluable, classification inputs present.** A contradiction check (EST-PROV clause (a) on omitted tuple, EST-PROV clause (b) on NOT-RECORDED held values as opposed to recorded NONE-GENUINE values, or a K-gate check whose provenance/availability inputs are omitted) cannot be evaluated, **but** the classification inputs for the applicable §3 comparison are present and sufficient (recorded flag, recorded values for comparison, K flag, and, for the computable branch, required partial provenance). → **Classification permitted**, with the unevaluated check recorded as UNEVALUABLE (flagged alongside the outcome, never as PASS), exactly as in §3.2 for clause (a) under True. The same principle applies to clause (b) NOT-RECORDED held values: omission of a held value (as opposed to a recorded NONE-GENUINE value, which **fires** clause (b) → INVALID-EST-STATE) leaves clause (b) UNEVALUABLE and permits KF classification with flag `EST-PROV-(b)-UNEVALUABLE`; it does not assert that the held value was present. For K-gate checks, the analogous flag is `GATE-UNEVALUABLE-<check>` naming the unevaluated check; a flagged §3 outcome must never be cited as evidence that the gate passed.
- **(M) Comparison-input missing.** A field required to perform the governing comparison itself is missing (recorded value VAL missing, K flag missing, or partial provenance missing where the matrix requires it for the computable branch and no incomputability branch defines the outcome). → **Comparison incomputable.** The outcome is then determined by the matrix's incomputability branch where one exists (False/Unknown partial incomputable → MATCH-TRUE/UNRESOLVED-C by true comparison, with P-UNKNOWN), or, where no incomputability branch defines an outcome for the missing input (e.g., recorded value missing under True, so no KF comparison can be performed at all), the tree outcome is FIELD-MISSING-PATTERN (missing-field bridge, retained) with a pending flag for the undetermined attribution (§3.5). In neither sub-case is the missing input's value assumed, interpolated, or derived from another field (no-substitution, REV-07 §2.1 / REV-08 §4.4, retained).

**Demonstrated contradictions still block (governing).** Nothing in §3.4(C) permits classification when a contradiction check **fires** on present data: EST-PROV clause (a) firing (VERIFIED NEVER / VERIFIED before-first) or clause (b) firing (recorded NONE-GENUINE held value against True) routes to INVALID-EST-STATE before §3, and a K-gate check firing routes to INVALID-K / INVALID-FEAT-RECORD per defect precedence, regardless of tuple or other omission status. Unevaluability (check cannot be run) and firing (check ran and contradicted) are different states and must never be merged in reports: UNEVALUABLE ≠ PASS and UNEVALUABLE ≠ FAIL.

### 3.5 Unclassified-pending — auxiliary attribution status, never an I0 outcome or exclusion (R9-06; governing)

**Definition (governing).** `Unclassified-pending` is an **auxiliary attribution status** attached to a step, recording that a specific attribution (a §3 component outcome, a K-defect determination, or an EST-PROV/gate determination, as named in the flag) is undetermined because a required pre-§3 check could not be evaluated. It is **not** a tree outcome, **not** a component outcome, **not** a P- attribute value, and **not** a waste bucket. A pending flag always names: (i) the undetermined attribution (e.g., "K-defect status", "EST-PROV clause (a)", "gate KX2f"), (ii) the omitted field or unevaluated check causing it, and (iii) the tree outcome under which the step is counted (below). A flag without those three elements is incomplete and must not be reported as a pending status.

**Counting treatment (governing; chosen option, with alternatives rejected).** Every step counted in I0 retains **exactly one winning tree outcome**, determined **independently** of the pending attribution, as follows:

- (a) Where the unevaluability is caused by a missing field and no other tree rule independently determines the outcome, the tree outcome is **FIELD-MISSING-PATTERN** (missing-field bridge, retained). The step is counted in I0 as FIELD-MISSING-PATTERN (one summand), counted in the P2 denominator as a FIELD-MISSING-PATTERN pre-step where applicable, and contributes unassigned waste in P3-final episodes per the bridge (in practice, a FIELD-MISSING-PATTERN step's episode is unlikely to be P3-final for independent Stage-A reasons, but the bridge rule governs if it is). The pending flag (naming the undetermined attribution) is carried as a secondary attribute (zero additional I0 summands, per single-counting, REV-07 §4, retained).
- (b) Where another tree rule independently determines the outcome (T0-P failure → INVALID-RECORD; OPT routing; availability-state assignment; winning defect outcome on a present field; K-class/status-line outcome on present inputs), **that outcome stands** and the pending flag is carried as a secondary attribute alongside it (zero additional I0 summands). The pending flag does not change the outcome, its waste bucket, or its F/Q column. Example: a step with T0-P failure (INVALID-RECORD) and an unevaluated gate on another field is counted once as INVALID-RECORD, with the gate pending flag recorded descriptively; it is not counted twice, and it is not reclassified as FIELD-MISSING-PATTERN.
- (c) **Pending status never removes a step from I0, P2, or any identity denominator.** A pending step is counted in its tree-outcome bucket and in denominators exactly as a non-pending step with the same tree outcome would be. A reconciliation that omits pending steps from an I0 total, or that adds a separate "pending" summand to I0, is invalid. The only counts that distinguish pending steps are **attribute/flag counts** (e.g., "of the FIELD-MISSING-PATTERN steps, N carry a gate-pending flag"), which are reported separately from outcome counts and never summed into them.

**Alternatives explicitly rejected.** (i) *Formal I0 outcome:* rejected, because it would create a new outcome class that competes with the tree's single-outcome partition, would require redefining I0–I6, F/Q, and waste identities for a status that asserts no classification, and would allow a step to be counted as "pending" while hiding which attribution is pending. (ii) *Exclusion from the I0 population:* rejected, because it would silently remove steps from denominators, break I0's partition of counted steps, and hide missing-field steps from frequency accounting (the opposite of the FIELD-MISSING-PATTERN bridge's purpose). (iii) *Implicit disappearance (no outcome, no exclusion, no flag):* rejected as not an option at all — any step with no I0 outcome and no reconciliation term breaks I0 by construction and must be treated as a reporting error, not as a pending status.

**Distinction from exception E-TUPLE (governing).** A step classified under exception E-TUPLE (§3.2) is **not** unclassified-pending for its §3 outcome: it **has** a §3 outcome (KF1/KF2), counted normally, with an UNEVALUABLE flag for the **history check only**. Unclassified-pending, by contrast, means the **attribution itself** (component outcome, defect determination, or gate determination, as named) has no value. The two flags must not be conflated: `EST-PROV-(a)-UNEVALUABLE` alongside a KF outcome means "outcome assigned, history check not run"; a pending flag for "K-defect status" means "no K-defect determination assigned". A report must use the flag that matches the undetermined object, not a generic "pending" label.

**P3/P4 consequence (governing, limited).** Pending status by itself does not exclude an episode from P3-final (P3 eligibility is determined by Stage-A/B/C, REV-07 §2 / REV-08 §4, retained) and does not by itself block P4. What pending status **does** block is any claim that depends on the pending attribution: a pending K-defect status cannot support an assigned-pattern frequency or waste claim for that step; a pending EST-PROV/gate determination cannot support a claim that the corresponding contradiction is absent. If a P3-final episode contains a pending step, that step's waste follows its tree outcome (FIELD-MISSING-PATTERN → unassigned per bridge; other outcomes → their outcome's bucket), and the report must flag the pending attribution alongside the episode's accounting result. Pending status is therefore a claim-scope limiter, not an eligibility gate — a distinction that must be preserved in summaries.

## 4. Step-label precedence and A4-C aggregation — stated once, applied everywhere (R9-03, R9-04)

### 4.1 Complete step-label precedence (governing; supersedes every unqualified "regardless" statement in REV-08 §3.3)

For a step that reaches §3 comparison (K_rec = 1, no earlier tree exit, per REV-08 §2.1), let the two domain components' outcomes be as assigned by REV-08 §3 (component governing comparisons, retained, with tuple handling in §3 above). The **step-level label** is determined by the following precedence, stated once here and cross-referenced (not restated in variant wording) elsewhere:

1. **If any domain component outcome is INCONSISTENT-C** (demonstrated internal inconsistency against a known governing partial path, False + computable branch) → step label **K3-PARTIAL-INCONSISTENT** (status line, unassigned waste, descriptive-only, per REV-05 §3.4, retained).
2. **Else, if any domain component outcome is UNRESOLVED-C** (true-differing with undetermined partial consistency, False + incomputable or Unknown branch) → step label **K3-UNRESOLVED** (class, unassigned waste, per REV-05 §3.4 / REV-06 §6, retained).
3. **Else, if any domain component outcome is KF1** (True branch, recorded ≠ true) → step label **K3-FULL** (class, assigned waste, per REV-05 §3.4, retained). (In practice, KF1 occurs only when the step-level estimate state is True, in which case both components are KF1/KF2, so rule 3 cannot co-occur with rules 1–2 for a single step's components under a single estimate state; rule 3 is included for completeness of the precedence statement and for error detection — a step presenting both KF1 and INCONSISTENT-C/UNRESOLVED-C component outcomes indicates a routing or recording error, to be flagged, not silently labelled.)
4. **Else (every domain component outcome is fall-through-eligible: KF2, partial-match, or MATCH-TRUE, as applicable to that component's combination)** → step **falls through** to pattern classification (HEAD / SEL / SUBOPT-UNCLASS as applicable under the tree). No K-class or K-status-line label is assigned.

**Qualified replacements (governing).** Every occurrence in REV-08 §3.3 (and any other REV-08 text) of the unqualified phrase "any component UNRESOLVED-C → step outcome K3-UNRESOLVED, regardless of the other component's outcome" is replaced by: "any component UNRESOLVED-C → step outcome K3-UNRESOLVED, **subject to the §4.1 precedence** (INCONSISTENT-C, if present in the same step, takes precedence and the step label is K3-PARTIAL-INCONSISTENT)". Similarly, every occurrence of "any component INCONSISTENT-C → step outcome K3-PARTIAL-INCONSISTENT, regardless of the other component's outcome" is retained in substance but must be read as "subject to the §4.1 precedence" (INCONSISTENT-C is itself the highest-precedence blocking outcome, so its "regardless" reading is correct **except** where it is quoted alongside the UNRESOLVED-C rule — in any joint statement, the precedence order in §4.1 governs, and the joint statement must cite §4.1). No other "regardless" statement in REV-08 §3.3 survives: step fall-through statements are governed by §4.1 rule 4 (all components eligible), not by any single component.

**Component outcomes retained (governing).** The precedence selects only the **step-level label**. Both component outcomes remain recorded individually in the component table, with their own P- attributes (per REV-08 §2, retained), regardless of which label wins. Example: a mixed-completability step with phase INCONSISTENT-C and remaining UNRESOLVED-C is labelled K3-PARTIAL-INCONSISTENT at step level, but its component table still shows phase = INCONSISTENT-C (P-INCONSISTENT) and remaining = UNRESOLVED-C (P-UNKNOWN). A report that overwrites the losing component's outcome with the winning label's outcome, or that omits the losing component from the component table, misrepresents the step and must be corrected.

**Waste follows the step label (governing).** Waste for a step is recorded under the selected step-level outcome's bucket only: K3-PARTIAL-INCONSISTENT steps' waste under `waste_K3-PARTIAL-INCONSISTENT` (unassigned), K3-UNRESOLVED steps' waste under `waste_K3-UNRESOLVED` (unassigned), K3-FULL steps' waste under `waste_K3-FULL` (assigned), fall-through steps' waste under their pattern outcome's bucket (HEAD/SEL/SUBOPT-UNCLASS as applicable). Waste is **never** split per component (e.g., half under INCONSISTENT-C and half under UNRESOLVED-C for a mixed step) and **never** counted under two buckets for the same step. Because both K3-PARTIAL-INCONSISTENT and K3-UNRESOLVED waste are unassigned, the **total** unassigned waste is the same under either label for a mixed step — but the **bucket attribution** differs, and bucket attribution is what the precedence governs. A report must therefore state the step label alongside any unassigned-waste total that includes mixed steps, or the total cannot be audited by bucket.

### 4.2 A4-C aggregation — single status per episode, all reasons retained (governing; adopts the recommended rule)

For an episode, let C be the set of candidate steps for T0 comparison (REV-08 §4.2 scope note, retained: steps not already excluded by step-type exclusion before T0). A4-C status for the episode is determined by the following aggregation, applied to C as a whole (not per step, and not as two simultaneous statuses):

- **A4-C = FAIL** if any step in C has a recorded phase present but inconsistent with the phase derived from `t_pre` (demonstrated inconsistency). The FAIL status holds **regardless** of how many steps in C have missing recorded phases — missing-phase reasons are retained as underlying reasons (below), but they do not convert a demonstrated inconsistency into an UNRESOLVED status, and they do not create a second A4-C status.
- **Else, A4-C = UNRESOLVED** if any step in C has a recorded phase missing (T0 fields present for that step, per §2.1). The UNRESOLVED status holds when no step in C demonstrates inconsistency.
- **Else, A4-C = PASS** (every step in C has a recorded phase present and consistent with `t_pre`).

**Single-status rule (governing).** Each episode has exactly one A4-C status (FAIL, UNRESOLVED, or PASS) under this aggregation. An episode containing both a missing-phase step and an inconsistent-phase step has A4-C = FAIL (first bullet), **not** both FAIL and UNRESOLVED as A4-C statuses. The missing-phase condition is recorded as an underlying reason in the ledger (see below), but it is not a second A4-C status.

**Ledger reasons (governing).** The ledger entry for the episode records **every** applicable A4 reason found, regardless of the aggregated status: (i) each inconsistent-phase step's FAIL reason (step identifier + demonstrated inconsistency), (ii) each missing-phase step's UNRESOLVED reason (step identifier + UNRESOLVED-INVALID-RECORD reason type). "Records every reason" means the ledger entry lists step identifiers for both kinds, not merely counts. If A4-C = FAIL due to inconsistency, the missing-phase reasons are underlying reasons in the same entry (they do not disappear because FAIL dominates). If A4-C = UNRESOLVED due to missing phase, the entry lists the missing-phase steps (there are, by the aggregation, no inconsistent-phase steps in C in this case). If A4-C = PASS, the entry records no A4 reason.

**A4-C status vs episode final status (distinguished, governing).** A4-C status is a **check status** (one of six Stage-A checks, A1–A6). Episode **final** Stage-A status is determined from all six check statuses by the two-tier rule (REV-07 §2.3, retained): any check FAIL → final FAIL (first failing check in A1→A6 order as the final-status code); else any check UNRESOLVED → final UNRESOLVED (first unevaluable check in A1→A6 order as the final-status code); else PASS. Consequences: (a) an episode with A4-C = FAIL has final status FAIL (with final code INVALID-RECORD if A4 is the first failing check, or an earlier check's code if an earlier check also FAILs — in the latter case, A4's FAIL reason is retained as an underlying reason, not as the final code); (b) an episode with A4-C = UNRESOLVED has final status UNRESOLVED with code UNRESOLVED-INVALID-RECORD **only if** no check FAILs and no earlier check is UNRESOLVED — otherwise its final code is the earlier FAIL/UNRESOLVED code, with A4's UNRESOLVED reason retained underlying; (c) an episode with A4-C = PASS may still have any final status depending on the other checks. A report must never equate "A4-C = UNRESOLVED" with "final status = UNRESOLVED-INVALID-RECORD" without checking the other checks and the two-tier rule — §5's counts depend on this distinction.

**Alternative explicitly not adopted.** No alternative aggregation (e.g., UNRESOLVED dominates FAIL within A4-C, or missing + inconsistent → a new combined status) is adopted. The FAIL-dominates rule within A4-C matches the episode-level two-tier rule (FAIL dominates UNRESOLVED across checks, REV-07 §2.3, retained), so the same priority applies within the check and across checks, with no priority inversion. If a future owner decision adopts a different within-check priority, it must amend §4.2, the two-tier rule's application to A4, §5's counts, and §7's reconciliation table together.

## 5. Step counts vs episode counts — four quantities, stated relationships, crosswalk required (R9-05)

### 5.1 Four quantities, defined separately (governing)

For missing recorded phase (the R9-05 case; the same unit discipline applies to any field-missing reconciliation, but the quantities below are defined for recorded phase specifically):

- **(a) `n_steps_missing-phase`** — number of steps, across all episodes in scope, whose tree outcome is FIELD-MISSING-PATTERN **and** whose missing field is recorded phase (I0 sub-count, per REV-08 §4.3, retained in form). Unit: **steps**. This is a sub-count of `n_FIELD-MISSING-PATTERN` (I0), not a separate I0 summand. It counts steps, not episodes: an episode with three missing-phase steps contributes 3 to (a).
- **(b) `n_episodes_with-missing-phase`** — number of episodes, in scope, containing at least one candidate step (REV-08 §4.2 scope, retained) with a missing recorded phase (T0 fields present for that step). Unit: **episodes**. An episode with three missing-phase steps contributes 1 to (b). By construction, (b) counts episodes, (a) counts steps, and (b) ≤ (a) whenever (a) > 0 (each counted episode contributes at least one counted step; equality holds if and only if every counted episode contains exactly one missing-phase step).
- **(c) `n_episodes_final-UNRESOLVED-INVALID-RECORD`** — number of episodes whose **final** Stage-A status is UNRESOLVED with code UNRESOLVED-INVALID-RECORD (i.e., no check FAILs, A4 is the first unevaluable check in A1→A6 order, and A4-C = UNRESOLVED per §4.2). Unit: **episodes (final status)**. (c) ≤ (b): every final-UNRESOLVED-INVALID-RECORD episode contains a missing-phase step by §4.2 (A4-C = UNRESOLVED requires one), but not every episode with a missing-phase step has that final status (it may have final FAIL, or final UNRESOLVED with an earlier code — see §4.2 and §5.1(e)).
- **(d) `n_episodes_FAIL-final_with-underlying-UNRESOLVED-INVALID-RECORD`** — number of episodes whose **final** Stage-A status is FAIL (any code) **and** whose ledger entry records UNRESOLVED-INVALID-RECORD as an underlying reason (i.e., the episode contains a missing-phase step whose reason was retained per §4.2, but the final status is FAIL due to A4-C = FAIL on another step or due to another check's FAIL). Unit: **episodes (final FAIL, underlying reason)**. (d) is disjoint from (c) by final status (FAIL vs UNRESOLVED), so (c) + (d) never double-counts an episode.

**Fifth quantity, for completeness (governing).** (e) `n_episodes_recording-UNRESOLVED-INVALID-RECORD` — number of episodes whose ledger entry records UNRESOLVED-INVALID-RECORD in **any** position (final code or underlying reason). Partition: (e) = (c) + (d) + `n_episodes_UNRESOLVED-final-other-code_with-underlying-UNRESOLVED-INVALID-RECORD` (episodes whose final status is UNRESOLVED with an earlier code, e.g., UNRESOLVED-TRANS-PATH from A3, but whose ledger also records an A4 missing-phase reason underlying). The three summands are disjoint by final status (UNRESOLVED-INVALID-RECORD final / FAIL final / UNRESOLVED-other-code final) and exhaustive for ledger recording. Provided the ledger records every reason found (REV-08 §4.3 as clarified in REV-09 §4.2), (e) = (b): every episode containing a missing-phase step records the reason, and no episode without a missing-phase step records it (A4-C = UNRESOLVED requires a missing-phase step; A4-C = FAIL episodes record missing-phase reasons only for steps that actually have missing phases). The identity (e) = (b) is therefore a **ledger-completeness check**, not a counting coincidence: if a future report's (e) ≠ (b), the ledger is incomplete or the scope definitions differ, and the discrepancy must be investigated, not averaged away.

**Relationships summary (governing; no equality between steps and episodes is asserted).**

- (b) ≤ (a), with equality iff ≤1 missing-phase step per counted episode.
- (c) ≤ (b), with equality iff every missing-phase episode has final UNRESOLVED-INVALID-RECORD (i.e., no missing-phase episode has a FAIL or an earlier UNRESOLVED code) — a strong condition that must not be assumed.
- (d) ≤ (b), and (c) + (d) ≤ (e) = (b) (when ledger-complete), with the remainder of (e) being UNRESOLVED-other-code-final episodes with the underlying reason.
- (c) is an I5 summand term (final-UNRESOLVED by code, §5.2 of REV-08 / §7 below); (d) is **not** an I5 UNRESOLVED summand (it is an I5 FAIL summand, by its final status); (e) is **not** an I5 term at all (it is a ledger-audit total). Equating (e) with (c), or (a) with any episode quantity, is invalid under this revision.

### 5.2 Crosswalk requirement (governing)

Totals alone cannot reconcile step counts with episode counts, because the mapping from steps to episodes is many-to-one and final-status determination depends on other checks. A future report that cites any of (a)–(e) must therefore provide, alongside the totals, an **explicit crosswalk**: for each episode in scope, its identifier, its candidate steps' identifiers with their missing/inconsistent phase flags, its A4-C status (§4.2), its other check statuses (or a reference to them), its final Stage-A status and code, and its ledger reasons (final + underlying). The crosswalk is a reporting format requirement, not a data claim: it states what a report must show so that (a)–(e) can be recomputed from it. A report that provides only totals (a)–(e) without a crosswalk (or an equivalent explicit mapping) has not reconciled step and episode counts under this revision, even if its totals happen to satisfy the inequalities in §5.1 — inequalities are necessary, not sufficient, for reconciliation. Where episode identifiers are not available in a future collection's field set, the collection plan must state how the crosswalk will be constructed (e.g., job + episode ordinal + step ordinal as a composite identifier) before collection; it must not assume identifiers exist.

## 10. Bounded conclusion — what this revision fixes, what remains unresolved, and what is still not validated

**Answer: REVISION-09 corrects the eight identified formal contradictions and counting ambiguities and is ready for owner approval as a specification — with the remaining limits stated below, which are limits of authorisation, measurement, mechanism evidence, and independent code-audit reproduction, not hidden inconsistencies in the corrected rules as far as the edge cases enumerated in §§2–8 are concerned. This conclusion is about the specification's readiness, not about any diagnostic having succeeded. No diagnostic has succeeded, no mechanism has been established, no trajectory has been collected under this revision, and no identity in REV-05 §6 / REV-06 §§4–6 / REV-07 §§2–4 / REV-08 §§2–5 / REV-09 §§2–5 has been empirically validated.**

**Specification consistency — what is now established (formally, within the text, subject to owner approval):**
- T0 and K = 0 wording now matches their governing rules (§2): T0 presence failure is INVALID-RECORD everywhere (not FIELD-MISSING-PATTERN anywhere), missing recorded phase with T0-P passed is FIELD-MISSING-PATTERN in the tree and UNRESOLVED-INVALID-RECORD at Stage A everywhere, and K_rec = 0 classification is qualified before it is stated (KX2a → INVALID-K, no availability outcome, gate-before-availability precedence, no dual assignment). The stale §2.1(c) sentence and the overbroad §2.1(b) opening sentence are the only REV-08 wordings in this area found to contradict REV-08 §4, and both are corrected here with audit agreement across §1, §7, and §9.
- Tuple omission is now decided, not left as a contradiction (§3): under True, classification is permitted under explicit exception E-TUPLE with EST-PROV-(a)-UNEVALUABLE flagged alongside the outcome (never PASS, never "contradiction absent"); under False and Unknown, classification is permitted for independent reasons (clause (a) not applicable to non-True claims), with the correct UNKNOWNs recorded (first-timing under False; estimate state itself under Unknown) and with a non-extension clause preventing the True exception from being cited for non-True cases. The scoped (C)/(M) boundary replaces the blanket prohibition: contradiction-check unevaluability with classification inputs present permits classification with a flag, while comparison-input missingness never permits assuming the missing value (incomputability branch or FIELD-MISSING-PATTERN + pending flag). Demonstrated contradictions still block, in all states.
- Pending status now has a counting home (§3.5): auxiliary attribution status, never a formal I0 outcome, never an I0 exclusion, always alongside an independently determined tree outcome (FIELD-MISSING-PATTERN where a missing field is the cause, otherwise the independently determined outcome), always flagged with attribution + cause + tree outcome, always zero additional I0 summands, and always a claim-scope limiter (not an eligibility gate) for P3/P4 purposes. The two rejected options (formal outcome, exclusion) and the non-option (implicit disappearance) are rejected explicitly, so a future report cannot reintroduce them by silence.
- Precedence and aggregation are now deterministic (§4): step labels follow INCONSISTENT-C > UNRESOLVED-C > fall-through-eligible, with both component outcomes retained and waste following the step label's bucket only; A4-C follows FAIL-if-any-inconsistency, else UNRESOLVED-if-any-missing, else PASS, with a single A4-C status per episode and all underlying reasons retained with step IDs. The within-check priority matches the across-check two-tier priority (FAIL dominates UNRESOLVED in both places), so there is no priority inversion to exploit or misread.
- Step and episode counts are now in different units, by definition (§5): four (plus ledger-total) quantities with stated inequalities/identity, a crosswalk requirement (episode IDs + step IDs + check statuses + final status + reasons) without which totals alone do not constitute reconciliation, and an explicit statement that I5 sums final statuses while the ledger sums reasons. The worked cases W9-4/W9-5 (§8) prove the inequalities (a) ≠ (b) and (c) ≠ (b) in general, so no future report can present step-equals-episode totals as a reconciliation.
- Episode terminology is now clean in governing text (§6): decision 4 uses "non-success episode in scope" directly, the full decision list was audited for surviving unqualified episode-failure wording (none remains in governing text), and audit-table quotations of superseded wording are labelled as such, never as governing claims.
