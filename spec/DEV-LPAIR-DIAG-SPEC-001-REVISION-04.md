**What this revision changes, in one paragraph:**
REVISION-03 fixed five inconsistencies but introduced or left five of its own. First, it described partial-feature availability as if both phase and remaining needed an open length, and as if a K = 1 step implied a clean span — neither is true of the verified code: raw phase needs only a cleanly observed opening, raw remaining needs that opening plus an open length, and a K = 1 step reached through full estimates says nothing about span cleanliness. Second, its K3-UNRESOLVED prose, table rows, and partition proof did not use one rule: one clause made missing provenance alone enough for UNRESOLVED even when the recorded features matched the true schedule, and the table treated blanked K = 0 slots as if they could mismatch. Third, it kept FIELD-MISSING waste inside the causal waste total while excluding such steps from pattern counts, and it kept individual steps in pattern counts while excluding their whole episode from waste accounting, without separating the five populations those claims actually use. Fourth, its sole/joint and blocker wording still implied counterfactual outcomes ("could account for the loss", "multiple sufficient waste sources", "failure's waste must come from elsewhere") after its own language audit forbade mechanism claims from waste sums. Fifth, its identities mixed pattern counts and waste sums over different populations. REVISION-04 corrects all five: availability is split into raw phase, raw remaining, and blanked model inputs, with a new span-cleanliness field; K3-UNRESOLVED is defined once, per component, and used identically in prose, table, and proof; pattern, contributor-frequency, episode-waste, and job-level populations are defined separately with exact denominators and an all-or-nothing episode rule for waste accounting; sole/joint/blocker language is restated as pure recorded-path arithmetic with an explicit non-counterfactual clause and a prohibited-phrasing audit; and a single numbered identity set (I0–I6) reconciles every count and sum. None of these identities has been checked against data — they are specification requirements (§6).

## 2. Corrected feature availability — raw phase, raw remaining, and blanked model inputs are three distinct things (supersedes REV-03 §2.1 partial paragraph, §2.3 partial-provenance sentence, and §3.1 KBLANK/KNEVER/KUNK descriptions in part)

### 2.1 Code facts that determine the rule (OBSERVED, re-checked for this revision)

**Exact scratch encoder invocation (OBSERVED, `dev-lpair-001/lpair.py` `LEncoder.encode`):** per encode, the encoder calls `world.observe()`, then `ScheduleModel.observe(tick, door)` exactly once, then — with **no argument** — `self.model.open_ticks_remaining()` and `self.model.ticks_since_opening()`. Both feature calls are therefore evaluated at the **last observed tick** (the current step's tick, since observe has just processed it). The sibling wrapped encoder (`TEMPLATE/nn/agent_wrapped.py` `WrappedEncoder.encode`) makes the identical no-argument calls. The ScheduleModel used by the scratch encoder is imported from `TEMPLATE/nn/wrapper.py` (the exact file read for this revision); the availability rules below are rules of that file's code, not of encoders in general.

**ScheduleModel feature rules (OBSERVED, `TEMPLATE/nn/wrapper.py`):**
- **Full estimates** = period, open_len, and last_opening_tick all non-None after the observe call (`_has_estimates`). With full estimates, `ticks_since_opening` returns `(tick − last_opening) % period` (periodic phase) and `open_ticks_remaining` returns `open_len − phase` while open, else 0, for any tick by projection.
- **Partial span** (`_partial_span`): returns `(elapsed, door_open_now)` where elapsed = last_tick − last_opening_tick, **only if** last_opening_tick is not None, the gap flag is False (no gap since the opening: no episode boundary, no skipped ticks, no contradiction since the opening was recorded), last_tick is not None, the previous observation is present, and last_tick ≥ last_opening_tick. Otherwise it returns None. The partial span needs **no period and no open_len**.
- **Raw phase** (`ticks_since_opening`, no argument): with full estimates, periodic phase; without full estimates, the partial span's elapsed value if a partial span exists, else None. **Raw phase availability therefore requires: full estimates, OR a clean opening span. It never requires open_len.** (With an explicit tick argument, `ticks_since_opening(tick)` returns None without full estimates — see the recomputation trap in §2.3. The encoder never calls it that way.)
- **Raw remaining** (`open_ticks_remaining`, no argument): with full estimates, periodic remaining; without full estimates, only if the call tick equals the last observed tick (true at encode time) **and** open_len is not None **and** a partial span exists — then `max(0, open_len − elapsed)` while open, 0 while closed. **Raw remaining availability therefore requires: full estimates, OR (clean opening span AND open_len known). It always requires open_len on the partial path.**
- **Asymmetry (OBSERVED consequence):** remaining-available implies phase-available (on the full path both are available; on the partial path remaining requires a partial span, which is exactly what gives phase). Phase-available does **not** imply remaining-available (clean opening without open_len gives phase, not remaining). There is **no** code path on which remaining is available while phase is not. Any table or argument that treats the two features as symmetrically available, or that infers phase unavailability from open_len unavailability, contradicts the code.
- **Encoder K rule and blanking (OBSERVED, both encoders):** K = 1 iff phase and remaining are both non-None after the observe call; otherwise the phase/remaining slots stay 0.0 (blanked) and K = 0. **Blanking couples the two features at the model-input level even though they are independent at the raw level:** a phase-only step (raw phase available, raw remaining missing) presents to the network exactly the same slots (0.0, 0.0, K = 0) as a neither-available step. The network input therefore cannot distinguish phase-only from neither-available; only separately recorded raw availability (R-FEAT-PHASE / R-FEAT-REM) can.
- **Estimates can be lost after first appearing** (REV-03 §2.1, retained, OBSERVED): on contradiction, stale events are dropped and period/open_len are cleared. First-appearance ordinal therefore never establishes current availability, for full estimates or for partial span (a gap after the opening ends the partial span even though the opening tick is still held in state until cleared).

**What REV-03 got wrong, stated plainly (so no reader re-derives it):** REV-03 §2.1 defined "partial knowledge" as open_len + clean opening and applied that definition to both features; that definition describes only the both-features case. REV-03 §2.3 then required both provenance fields for any partial comparison and claimed clean span was "implied by K_rec = 1 via the partial path" — but K = 1 via the **full** path implies nothing about span cleanliness, and REV-03 defined no field that records span cleanliness at all. REV-03 §3.1's KBLANK parenthetical ("an observed opening without open_len gives phase availability via the partial path only if open_len is also known") reverses the code: an observed clean opening without open_len gives phase availability and does not give remaining availability. All three statements are superseded by this section.

### 2.2 Raw states and model-visible inputs (the corrected availability picture)

For a step after its encode's observe call, exactly one raw state holds (when raw availability is recorded; otherwise UNKNOWN):

| Raw state | Raw phase | Raw remaining | K flag | Model-visible phase slot | Model-visible remaining slot | What the network input shows |
| --- | --- | --- | --- | --- | --- | --- |
| FULL | Available (periodic) | Available (periodic) | 1 | phase / 20.0 | remaining / 10.0 | True periodic features (up to ScheduleModel correctness) |
| PARTIAL-BOTH | Available (elapsed, non-modulo) | Available (open_len − elapsed while open, 0 while closed) | 1 | elapsed / 20.0 | remaining / 10.0 | Partial features; elapsed can exceed the true period |
| PHASE-ONLY | Available (elapsed, non-modulo) | Missing (open_len unknown, or no partial remaining) | 0 | 0.0 (blanked) | 0.0 (blanked) | **Indistinguishable from NEITHER at the input level** — raw phase exists in ScheduleModel state but is hidden by blanking |
| NEITHER | Missing (no clean opening, or gapped span) | Missing | 0 | 0.0 (blanked) | 0.0 (blanked) | No schedule features |
| RAW-UNKNOWN | Unknown (not recorded) | Unknown (not recorded) | As recorded (0 or 1) | As recorded (slot values) | As recorded (slot values) | Raw state cannot be determined from K or slots alone: K = 0 establishes only "not both available" (at least one missing, by the encoder AND-gate); K = 1 establishes both available (by the same gate) |

**Two distinctions this table enforces (do not collapse them):**
- **Information held by ScheduleModel vs information in the network input.** A PHASE-ONLY step holds schedule information in ScheduleModel state (a cleanly observed opening and the elapsed ticks since it) that is **not** in the network input (blanked to 0.0). A K3 judgement concerns the network input's features (recorded slots, §3); a statement about what the mechanism "had available" internally concerns raw availability. The two must never be substituted for each other: PHASE-ONLY is not "no schedule information" (raw view) and it is not "phase information in the input" (input view) — it is both a raw-available fact and a blanked-input fact, stated together.
- **A blanked slot is not an estimate.** When K = 0, the recorded phase/remaining slots are the constant 0.0 by the blanking rule, not ScheduleModel outputs. Comparing a blanked 0.0 to a true feature value is not a mismatch judgement and not a match judgement (§3.2, K_rec = 0 rule). Only K_rec = 1 slots, or separately recorded raw values, are estimates that can match or mismatch.

### 2.3 New and amended provenance fields (Essential for any future collection that makes availability or K3 claims)

REV-03 §2.2 fields are retained (R-EST-CUR, R-LAST-OPEN three-valued, R-OPEN-LEN three-valued, R-FEAT-PHASE, R-FEAT-REM, R-EST-TUPLE with VERIFIED/UNKNOWN status). The following field is **added**, and two recording rules are **added**:

| Field ID | Level | Definition (exact) |
| --- | --- | --- |
| R-SPAN-CLEAN | Per-step (Essential for partial comparisons) | **span_clean**: True iff, after the observe call at this step's encode, ScheduleModel holds a last_opening_tick that is not None, its gap flag is False, its last observed tick is at or after that opening, and a previous observation is present — i.e. iff `_partial_span()` would return a value. False iff any of those conditions fails (including: no opening held, gap flag set by an episode boundary, skipped ticks, or contradiction). Unknown (null) iff the collection does not record the gap flag / partial-span status at this step. **R-LAST-OPEN holding an integer tick never, by itself, establishes R-SPAN-CLEAN = True** — an opening tick can be held while the span since it is gapped. If R-SPAN-CLEAN is Unknown, partial comparisons are uncompletable for that step (§3.1), not assumed clean. |

**Recording rule R-REC-1 (encode-time raw values only):** R-FEAT-PHASE and R-FEAT-REM must be recorded from the encoder's own no-argument calls at encode time (the values the encoder tested for the K gate). A collection that recomputes features offline with an explicit tick argument (`ticks_since_opening(tick)`, `open_ticks_remaining(tick)`) does **not** reproduce the encoder's raw availability: with an explicit tick, the partial phase path returns None without full estimates (OBSERVED code), so a partial-phase step would be falsely recorded as phase-unavailable. Offline explicit-tick recomputation is **invalid provenance** for R-FEAT and for any K3 comparison; steps whose R-FEAT values come only from such recomputation must be treated as R-FEAT Unknown.

**Recording rule R-REC-2 (three-valued provenance is mandatory for partial fields):** R-LAST-OPEN and R-OPEN-LEN use the REV-03 three-valued encoding (integer / NONE-GENUINE / NOT-RECORDED). A bare null conflating NONE-GENUINE with NOT-RECORDED is insufficient provenance: NONE-GENUINE (ScheduleModel holds no opening / no open_len) supports an INVALID-K or no-partial-expectation conclusion (§3.3), while NOT-RECORDED supports only UNRESOLVED. Records that conflate them must be treated as NOT-RECORDED (the weaker provenance) for every judgement.

### 2.4 Corrected availability-state descriptions (supersede REV-03 §3.1 descriptions)

- **KBLANK (K_rec = 0, ordinal < first_estimates_ordinal, tuple VERIFIED):** establishes only that the K flag was off before full estimates first appeared. It does **not** establish absence of schedule information. Sub-states (descriptive, same class, same unassigned bucket — always shown when R-FEAT is recorded): **KBLANK-PHASE-ONLY** (R-FEAT-PHASE True, R-FEAT-REM False: a clean opening was observed and elapsed ticks were available in ScheduleModel state, but open_len was not yet known, so the network input was blanked); **KBLANK-NEITHER** (both R-FEAT False: no clean opening span, hence no raw feature); **KBLANK-UNKNOWN-FEAT** (either R-FEAT Unknown: individual availability UNKNOWN, must not be described as either sub-state). The correct statement for a KBLANK step is: "K flag off before first full estimates; raw phase/remaining: [R-FEAT values, or UNKNOWN]; network input slots blanked."
- **KNEVER (K_rec = 0, tuple VERIFIED NEVER):** establishes only that full estimates never appeared in the job and the K flag was off at this step. It is a trajectory consequence (the observed (tick, door) sequence never supplied full-estimate conditions), not a protocol claim (REV-03 §3.3 criterion retained). Sub-states as for KBLANK: **KNEVER-PHASE-ONLY** (partial phase may have been available at various steps in the job even though full estimates never appeared — indeed, a K = 1 step in a NEVER job is necessarily PARTIAL-BOTH, §3.3 row KP1); **KNEVER-NEITHER**; **KNEVER-UNKNOWN-FEAT**. A KNEVER step must never be described as "schedule-blind" without the R-FEAT sub-state stated: PHASE-ONLY steps are not schedule-blind in the raw sense, only blanked at the input.
- **KUNK (K_rec = 0, ordinal ≥ first_estimates_ordinal, tuple VERIFIED):** establishes only that the K flag was off after full estimates had once appeared (possible explanations: contradiction clearing estimates, gapped span, or recording error — the state alone does not distinguish them). Sub-states as above (KUNK-PHASE-ONLY / KUNK-NEITHER / KUNK-UNKNOWN-FEAT). Attribution suspended (unassigned), not assigned to any cause.
- **K-STATUS-UNKNOWN (K_rec = 0, tuple UNKNOWN):** the availability class itself is unknown (cannot distinguish BLANK/NEVER/UNK without the tuple). Not a sub-state of any of them; counted separately (§6, I0/I1).
- **A note on "schedule-blind" language:** the word "blind" must not be used for a K = 0 step without stating whether it means raw-blind (NEITHER), input-blanked (any K = 0 step, including PHASE-ONLY), or both. Unqualified "schedule-blind" for a PHASE-ONLY step is overclaiming and must be corrected to the sub-state form above.

## 3. K3-UNRESOLVED defined once — per-component rule, corrected decision table, partition proof (supersedes REV-03 §2.3 K3 rule and §2.4 table in full; deliverable 3)

This section governs **SUBOPTIMAL, timing-critical steps** only (the only steps that receive K classes in the partition; OPT steps and non-timing-critical steps carry K status as attributes only, REV-02 §2.2 retained). True periodic features are as in REV-01 §3.4 (retained): true_phase = t_pre mod 20, true_remaining = (10 − true_phase) if true_phase < 10 else 0. Recorded features are phase_rec / remaining_rec from the step record (model-visible slots unscaled: phase_rec = slot × 20.0, remaining_rec = slot × 10.0, when K_rec = 1).

### 3.1 Per-component comparisons — what can be judged, and what cannot

For each component c ∈ {phase, remaining}, define the **applicable expectation** and the **partial-comparison completability** exactly:

- **Phase partial comparison completable** iff R-LAST-OPEN is an integer tick AND R-SPAN-CLEAN = True (both recorded). Then partial_phase_exp = t_pre − last_opening_tick (elapsed ticks, **not** modulo-wrapped, OBSERVED partial path).
- **Remaining partial comparison completable** iff phase partial comparison is completable AND R-OPEN-LEN is an integer. Then partial_remaining_exp = max(0, open_len − partial_phase_exp) if door_open_pre is true, else 0 (OBSERVED partial remaining rule: open_len − elapsed while open, 0 while closed; the max(0, ·) follows the code's `max(0, open_len − elapsed)`).
- **If est_full_cur = True**, the applicable expectation for both components is the true periodic value (full projection is the model's own semantics at this step). Partial expectations are irrelevant when full estimates are current (the model is not using the partial path).
- **If est_full_cur = False**, the applicable expectation for a component is its partial expectation **if completable**; if not completable, the component has **no applicable expectation** other than the true periodic value used for mismatch detection (below).
- **If est_full_cur = Unknown** (not recorded and not inferable by REV-03 §2.2 rules (a)/(b)), no FULL-vs-PARTIAL attribution is available for either component; the true periodic value is used for mismatch detection only.

**Per-component outcome** (computed for phase and remaining separately, using recorded features only when K_rec = 1 — see §3.2 for K_rec = 0):
- **MATCH(c)** iff recorded_c equals the applicable expectation for c. For est_full_cur = True, applicable = true periodic. For est_full_cur = False with completable partial comparison, applicable = partial expectation. For est_full_cur = False/Unknown with recorded_c equal to the true periodic value, MATCH(c) holds on the true-comparison ground below (a recorded value equal to the true value cannot explain suboptimality via that component, whatever its provenance — if est_full_cur = False and partial comparison is completable, this case coincides with partial match whenever elapsed < 20, and with partial mismatch only if elapsed ≥ 20 while recorded_c still equals true periodic, which cannot occur from ScheduleModel output: partial output is elapsed, full output is periodic — a recorded value equal to true periodic while est_full_cur = False is therefore either a first-cycle partial value (elapsed = true phase, hence also a partial match) or a record inconsistency to be flagged INVALID-K if provenance contradicts it; in no case is it a schedule error via component c).
- **MISMATCH(c)** iff est_full_cur = True and recorded_c ≠ true periodic value, OR est_full_cur = False and partial comparison is completable for c and recorded_c ≠ partial expectation for c. MISMATCH is always relative to a stated applicable expectation — a bare "recorded ≠ true" is **not** MISMATCH when est_full_cur = False (see UNRESOLVED-C and the partial-match fall-through below).
- **UNRESOLVED-C(c)** iff recorded_c ≠ true periodic value AND est_full_cur ≠ True AND the applicable comparison for c cannot be completed (est_full_cur = Unknown, so FULL-vs-PARTIAL attribution is unavailable; OR est_full_cur = False and partial comparison is not completable for c, so neither the partial expectation nor the FULL attribution can be checked). UNRESOLVED-C requires a **demonstrated difference from true periodic features** — missing provenance without such a difference is not UNRESOLVED-C (see §3.2 fall-through and K_rec = 0 rules). Note the asymmetry that resolves REV-03's clause-2 error: recorded_c = true periodic value with uncompletable provenance is MATCH(c) on true-comparison ground, never UNRESOLVED-C, because there is no demonstrated error for that component to resolve.

**Partial-match fall-through (retained from REV-03, restated per component):** a component whose recorded value matches its partial expectation is not an error via that component, even if it differs numerically from true periodic features (non-modulo elapsed ≥ 20). Only components with MISMATCH or UNRESOLVED-C outcomes can support a K3 class for the step.

### 3.2 Step combination rule — the single rule used in prose, table, and proof

Apply in this exact order to a suboptimal, timing-critical step:

1. **INVALID-K precedence.** If the K record contradicts the encoder rule (§3.3 rows KX2a–KX2e), the step's K status is INVALID-K. INVALID-K takes precedence over every K3 class and availability state. (OPT steps with an INVALID-K attribute are counted as OPT in I0 with the attribute cross-tabulated, §6 — the precedence here concerns K classification, not the I0 summand rule for OPT steps.)
2. **K_rec = 0 rule.** If K_rec = 0 (and the record is not INVALID-K), the step takes an availability state (KBLANK / KNEVER / KUNK / K-STATUS-UNKNOWN per §2.4 and REV-03 §2.4 tuple rules), **never a K3 class**. Reason: recorded slots are blanked constants (0.0), not estimates (§2.2). A blanked 0.0 differing from true features is not a MISMATCH; a blanked 0.0 coinciding with a true feature value is not a MATCH — the two possible coincidences never occur together (blanked phase 0.0 equals true_phase only at phase 0, where true_remaining = 10, not 0; blanked remaining 0.0 equals true_remaining only at phase ≥ 10, where true_remaining = 0 and true_phase ≠ 0). Availability states carry no K3 judgement, whatever the blanked slots' numerical coincidence with true values. Raw-feature judgements (R-FEAT) for K_rec = 0 steps are descriptive mechanism-internal quantities (§2.2), never K3 classes.
3. **K_rec = 1, any UNRESOLVED-C → K3-UNRESOLVED.** If either component's outcome is UNRESOLVED-C, the step is K3-UNRESOLVED, regardless of the other component's outcome. Reason: a demonstrated true-difference exists for at least one component whose error status (FULL-sense vs PARTIAL-sense) cannot be determined, so the step's schedule-error status is unresolved as a whole. (A step with one MISMATCH component and one UNRESOLVED-C component is UNRESOLVED, not PARTIAL: the unresolved component prevents a complete PARTIAL attribution for the step.)
4. **K_rec = 1, est_full_cur = True, any MISMATCH → K3-FULL.** (No UNRESOLVED-C component exists in this branch, since est_full_cur = True makes true periodic the applicable expectation for both components.)
5. **K_rec = 1, est_full_cur = False, any MISMATCH → K3-PARTIAL.** (No UNRESOLVED-C component exists in this branch by step 3's precedence: if any component were UNRESOLVED-C, step 3 would already have applied. Hence every mismatching component here has a completable partial comparison, and every non-mismatching component matches its partial expectation or its true value.)
6. **Otherwise (K_rec = 1, all components MATCH) → fall-through (K3 NOT_SUPPORTED for this step).** The step proceeds to HEAD/SEL in the partition with a K-correct (est_full True) or partial-correct (est_full False) or true-correct (est_full Unknown, matched true) attribute recorded. This includes: est_full_cur = Unknown with both components matching true periodic (REV-03 row K-U2, retained); est_full_cur = False with partial comparisons completable and matching (REV-03 row K-P2, retained); est_full_cur = False with partial comparisons uncompletable but both components matching true periodic (corrected from REV-03 clause 2, which would have forced UNRESOLVED).
7. **K fields missing → FIELD-MISSING-K.** If K_rec, phase_rec, or remaining_rec is absent from the record (as opposed to recorded as 0), the step's K status is FIELD-MISSING-K (§3.3 row KX3). For pattern classification: an OPT step is still class OPT (OPT determination needs R(s)/action, not K fields); a suboptimal step with missing K fields is FIELD-MISSING-PATTERN (§4.2) — it cannot be assigned K3/BLANK/NEVER/UNK/HEAD/SEL through K precedence, and its K3 attribution is UNKNOWN (not inferred, not zero-filled). FIELD-MISSING-K is a K-status label; FIELD-MISSING-PATTERN is the pattern-classification outcome for suboptimal steps with that label (§4.2, §6 I0).

**Missing provenance is never evidence of mismatch (explicit rule, all sections):** no step is assigned MISMATCH, K3-FULL, or K3-PARTIAL on the basis of a missing field. Missing fields produce UNRESOLVED-C only when a demonstrated true-difference exists for that component (§3.1), FIELD-MISSING-K/PATTERN when K fields are absent (§3.2 step 7), or availability-UNKNOWN sub-states when R-FEAT/tuple fields are absent (§2.4). If no applicable rule can be established from the recorded fields for a component, that component's attribution is UNKNOWN/UNRESOLVED for that component — the step rule in §3.2 then applies (UNRESOLVED-C only on demonstrated true-difference; otherwise MATCH-on-true or availability/FIELD-MISSING handling as above). No result is invented to fill the gap.

### 3.4 Partition proof (for the K3 sub-split; the REV-02 §2.5 priority-order proof is otherwise retained)

**Claim:** for suboptimal, timing-critical steps in Population F (full Q available), the §3.2 rule assigns exactly one of {K3-FULL, K3-PARTIAL, K3-UNRESOLVED, KBLANK, KNEVER, KUNK, K-STATUS-UNKNOWN, FIELD-MISSING-PATTERN, HEAD, SEL} (via fall-through to HEAD/SEL), or INVALID-K (record-integrity outcome), with no overlap and no gap — and therefore n_K3 = n_K3-FULL + n_K3-PARTIAL + n_K3-UNRESOLVED holds exactly over the steps assigned K3 classes.

**Proof sketch (specification-level, not empirical):** fix such a step. If K fields are missing, step 7 assigns FIELD-MISSING-PATTERN (suboptimal by assumption) — done, unique. Else K_rec is 0 or 1. If the record meets any KX2 condition, step 1 assigns INVALID-K — done, unique (KX2 conditions are contradictions with the encoder gate, hence incompatible with any consistent K3/availability assignment). Else K_rec = 0 → step 2 assigns exactly one availability state by the tuple rules (VERIFIED before-first → KBLANK; VERIFIED NEVER → KNEVER; VERIFIED at/after-first → KUNK; UNKNOWN tuple → K-STATUS-UNKNOWN) — the tuple statuses are mutually exclusive by definition (VERIFIED vs UNKNOWN; before-first vs at/after-first vs NEVER are disjoint ordinal relations) — done, unique. Else K_rec = 1: each component's outcome is exactly one of MATCH / MISMATCH / UNRESOLVED-C by §3.1 (for est_full True, UNRESOLVED-C cannot occur since true periodic is the applicable expectation for both components; for est_full False, a component is MISMATCH iff it differs from a completable partial expectation, UNRESOLVED-C iff it differs from true with no completable partial comparison, MATCH otherwise — the three are disjoint by construction; for est_full Unknown, a component is UNRESOLVED-C iff it differs from true, MATCH iff it equals true — again disjoint, and MISMATCH does not occur as a distinct outcome under Unknown, since no applicable expectation other than true exists to mismatch against). The step rule then applies in fixed priority: any UNRESOLVED-C → UNRESOLVED (step 3); else est_full True + any MISMATCH → FULL (step 4); else est_full False + any MISMATCH → PARTIAL (step 5); else all MATCH → fall-through to HEAD/SEL (step 6). Each priority branch's condition is disjoint from the earlier branches' conditions (step 3 excludes UNRESOLVED-C from later branches; step 4 requires est_full True, step 5 requires est_full False, so they cannot both apply; step 6 requires no MISMATCH and no UNRESOLVED-C). Hence exactly one class. The K3 identity follows by counting: steps assigned K3 classes are partitioned by the three K3 values, so their total is the sum of the three sub-counts. ∎

**What the proof does not establish (stated explicitly):** the proof establishes that the *rule* partitions the steps it is applied to; it does not establish that any real collection's records satisfy the rule's field requirements (that is a collection-validity question), nor that the assigned classes are correct descriptions of any mechanism (that is a mechanism question, §5). A collection in which the proof's preconditions fail (missing fields, contradictory records) yields INVALID/UNKNOWN outcomes under the rule, not proof failures.

Job-level P3 denominator: # P3 failed episodes (for trigger frequencies and per-episode-all checks, §4.2). | Episode waste accounting (§5), trigger frequencies, and — only via P4 — job-level accounting-sufficient claims. | Any failed episode failing (i)–(v): wholly excluded from P3 (all its steps, including individually conformant pre-break steps). Its arithmetic waste, if computable, goes to the excluded-episode descriptive ledger (§4.3) only — never into any P3 sum, never into a job-level waste total. |
| **P4 — Job-level accounting-sufficiency** | A **job** (construction × world × seed, stated scope) qualifies for a job-level accounting-sufficient claim iff **all** of: (a) the frequency combination rule is prescribed before collection (Rule C / T / CT with form verbatim + threshold values, REV-03 §5.4 retained); (b) **every** failed episode in the job's stated scope is P3-eligible (zero excluded failed episodes — see §4.2 strict rule); (c) waste conditions (§5) are evaluated per episode over P3 episodes only; (d) the Shared pattern-only caveat (if applicable, REV-03 §5.4 condition 5 retained) and mechanism-status line (§5) are satisfied. ### 4.2 Field-type distinctions that make the five populations work (binding)

- **Pattern fields vs path fields vs record fields.** Pattern classification (P1) needs pattern fields: position_before, phase/t_pre, action, act (or Q-routing), K fields (or FIELD-MISSING handling), reference R(s)/V(s). Episode waste accounting (P3) needs, in addition, path fields: position_after for every step, continuity across steps, transition conformance of position_after/crush/reached/door/tick, and finite V for every step. Record fields — recorded target (R-TARGET), recorded transition_type, recorded blocked_log as a *record* (as opposed to blocked_spec derived from T_spec) — are **not** path fields for waste: waste is computed from positions and reference values, not from recorded target/type labels. Hence a C-TARGET-only or C-TYPE-only failure (record label wrong, path fields conformant) leaves P3 eligibility intact with TYPE-FLAG, while excluding the step from Level 2-T. Conversely, a C-TRANS failure (a path field deviates) breaks P3 eligibility for the whole episode even if the recorded target/type labels happen to be self-consistent. This is the precise sense in which REV-03's TYPE-FLAG retention is retained and its C-TRANS exclusion is strengthened to whole-episode.
- **FIELD-MISSING-PATTERN bridge (the R4-03 reconciliation, stated exactly).** A suboptimal step with missing K fields in a P3-eligible episode has: no pattern class (not counted in any class count in I1/I2 numerators); membership in P2's denominator (n_pre includes it, §4.1); waste, if computable from its path fields and reference (it is, when the episode is P3-eligible — otherwise the episode would not be P3-eligible), counted in P3's **unassigned** total under the FIELD-MISSING sub-bucket (§4.4). It is therefore counted exactly once in each ledger it belongs to (P1 status line, P2 denominator, P3 unassigned waste) and zero times in any pattern class count. A step with missing *path* fields (position_after, reference) cannot be in a P3 episode at all (P3 condition (iv) fails) — its waste is waste-undefined (I4), never FIELD-MISSING waste. The two missing-field cases must never be merged: "missing K fields, waste computable" (FIELD-MISSING waste, in P3 unassigned total) vs "missing path fields, waste uncomputable" (waste-undefined, episode excluded from P3).
- **Trigger identity (companion to I2).** For P3 failed episodes, each episode has exactly one inevitability step f. Trigger frequency for class P: trigger_freq(P) = (# P3 failed episodes whose f-step class is P) / (# P3 failed episodes). Episodes whose f-step class is FIELD-MISSING-PATTERN contribute to the denominator but to no numerator, counted as n_trigger-unknown and reported alongside (so Σ_P trigger_freq(P) ≤ 1, with equality iff n_trigger-unknown = 0). The f-step cannot be CRUSH-ND (crush-waste theorem: f is never a crush step, REV-02 retained) and cannot be UNREACH/TERMINAL-DEV in a P3 episode (P3 conditions exclude them). At-steps are never in P2 (n_pre) and pre steps are never in trigger numerators (§5.2 retained).
- **REPAIRED episodes.** A repaired episode (any step flagged REPAIRED with originals preserved, REV-03 §4.1 retained) is excluded from P3 by default and from P4's "every failed episode P3-eligible" check (a repaired failed episode in scope makes the job P4-ineligible unless an owner decision admits repaired episodes). If a future owner decision admits repaired episodes under a stated repair rule, admitted repaired episodes form a separately labelled population **P3-R** (same eligibility otherwise, repair rule stated, originals preserved) whose waste sums and frequencies are reported separately and **never merged** with P3. No P3-R population exists until such a decision is made.
- **Successful and deviation episodes.** Successful episodes (goal reached) have no f and no slack/waste accounting; they are counted in job completeness (REV-03 §5.4 condition 1 retained: successful, deviation, and non-conformant episodes listed separately) but in no P2/P3 denominator. Deviation episodes (C-PROTO failure, episode continues after reaching, length > 200, etc.) are excluded from P2/P3/P4 entirely and reported in the excluded-episode ledger by reason.

### 4.3 Excluded-episode ledger (mandatory for any report making P2/P3/P4 claims)

For each job in scope, the report must list: total failed episodes in scope; # P3-eligible failed episodes; and, for each excluded failed episode, its identifier and exactly one exclusion reason by the precedence **PROTOCOL (C-PROTO) > SEQUENCE (C-CONT) > NONCONF (C-TRANS) > WASTE-UNDEFINED (path/reference missing or V = ∞) > INVALID-RECORD > REPAIRED** (episode-level reasons take precedence over step-level reasons; a step in an excluded episode is counted once under the episode's reason, never also under a step reason for the same population). For excluded episodes, the report may show descriptive arithmetic waste (V(next_recorded) − V(s) + 1 summed over recorded steps, where computable) in a clearly labelled **excluded-episode descriptive waste** line — this line is **never** added to P3 sums, never used in sole/joint checks, and never presented as episode waste accounting. Pre-break steps' individual waste values from a continuity-broken episode belong only to this descriptive line, not to any causal sum. If an excluded episode's descriptive waste cannot be computed, it is counted as waste-undefined (I4) with reason stated.

### 4.4 P3 waste ledger (per episode, pre+at segments only)

For a P3 episode ep, with slack_start(ep) as in REV-02 §4.1 and waste(s) = V(next_actual) − V(state) + 1 (OPT waste 0, crush waste 0 by theorem, suboptimal waste ≥ 1 — all computed, none assumed):
- **Assigned waste:** waste_SEL(ep) + waste_HEAD(ep) + waste_K3-FULL(ep) + waste_K3-PARTIAL(ep), each summed over pre/at steps of that class in ep. (Shared SEL/HEAD are pattern classes; Shared mechanism separation remains pattern-only, REV-03 §5.4 condition 5 retained.)
- **Unassigned waste:** waste_unassigned_total(ep) = waste_K3-UNRESOLVED + waste_KBLANK + waste_KNEVER + waste_KUNK + waste_K-STATUS-UNKNOWN + waste_SUBOPT-UNCLASS + waste_FIELD-MISSING-PATTERN, each summed over pre/at steps of that class/status in ep. (K-STATUS-UNKNOWN steps in a P3 episode: possible only if the step's K-status is unknown but its path fields are complete — such steps have no pattern class; their waste, if computable, is unassigned under the K-STATUS-UNKNOWN sub-bucket. Note: K-STATUS-UNKNOWN steps are availability-unknown, not FIELD-MISSING-K — the two sub-buckets are distinct and both shown.)
- **Zero lines (computed, not defaulted):** OPT steps and crush steps in ep contribute computed waste 0 each; they are listed as n_zero-computed counts, not as buckets, and never confused with waste-undefined (I4).
- **Ledger identity (I3, §6):** total_P3_waste(ep) = assigned + unassigned_total, and total_P3_waste(ep) must equal slack_start(ep) − slack_after(f). If the telescoping equality fails for a P3 episode, that episode is **P3-INVALID** (classification, segment, or V error): it is removed from P3, reported in the excluded-episode ledger with reason P3-INVALID, and investigated — its waste values are never adjusted to force the equality.
- **Post-segment ledger (descriptive only):** post waste (s > f, any class) is summed separately per episode as descriptive post waste, never added to total_P3_waste(ep), never in sole/joint checks, never in P2.

## 5. Counterfactual-free accounting language (supersedes REV-03 §5.1 contributor definition, §5.3 sole/joint/blocker definitions, §5.6 exclusion wording, and §3.2 non-conformant wording in part; REV-03 §5.4 Rule C/T/CT form and §6 language audit table are retained and extended)

### 5.1 Definitions, restated as pure recorded-path arithmetic (each carries its non-counterfactual clause)

**Waste-sufficient (accounting) — sole, episode-level:** waste_P(ep) ≥ slack_start(ep) + 1, where waste_P(ep) is the sum of waste(s) over pre-segment steps of class P plus waste(f) if f's class is P, computed over P3 episode ep (§4.4). **Non-counterfactual clause (mandatory, part of the definition):** this inequality is a statement about sums on the recorded path only. It does not state, imply, or estimate what the episode's outcome would have been on any other trajectory, including a trajectory in which steps of class P were removed, replaced, or changed, or in which the pattern did not occur. Such trajectories are not observed; their states, Q inputs, and reference values are not the recorded ones; no outcome for them is asserted by this definition, and no outcome for them may be inferred from it.

**Waste-sufficient (accounting) — sole, job-level:** episode-level sole holds for every P3 failed episode in the job's scope (P4-eligible jobs only, §4.1). Same non-counterfactual clause, at job scope: the claim is that the inequality holds on every recorded failed path in scope, nothing about any unobserved path.

**Waste-sufficient (accounting) — joint, episode-level:** for a stated assigned-pattern set S (subset of {SEL, HEAD, K3-FULL, K3-PARTIAL}; K3-family sets must state subcategory composition per REV-03 §5.3 retained): sum_{P∈S} waste_P(ep) ≥ slack_start(ep) + 1, AND no single P ∈ S is episode-level sole (otherwise report sole, not joint), AND waste_unassigned_total(ep) < slack_start(ep) + 1 (otherwise the episode's joint claim is INCONCLUSIVE under the blocker below). Same non-counterfactual clause: the joint inequality is a sum relation on the recorded path only.

**Waste-sufficient (accounting) — joint, job-level:** episode-level joint holds for every P3 failed episode in scope, with the same set S. Same non-counterfactual clause.

**Unassigned blocker (episode-level):** if waste_unassigned_total(ep) ≥ slack_start(ep) + 1 and waste_P(ep) < slack_start(ep) + 1, then the episode's accounting claim for P is INCONCLUSIVE (accounting). **Stated arithmetically, without production language:** the recorded-path sums do not single out P by the threshold, because another bucket's recorded-path sum also meets the threshold. No statement is made about which bucket's steps "produced" the episode's outcome, and no statement is made about what would have happened had any bucket's steps been different. If waste_P(ep) ≥ slack_start(ep) + 1 **and** waste_unassigned_total(ep) ≥ slack_start(ep) + 1, then **both inequalities hold on the recorded path**; report both sums alongside each other. The claim is "P waste-sufficient (accounting)" with the unassigned sum also meeting the threshold stated — never "P the only waste source", never "P produced the loss", never "unassigned waste also caused it".

**Contributor (restated, REV-03 §5.1 superseded):** a contributor is a pattern class occurring on pre-segment steps (s < f) in P3 failed episodes, whose waste is summed in contributor quantities (P2). The word "contributor" in this specification means only "pre-segment occurrence counted in P2" — it does not mean "cause", "source", or "producer" of anything. The phrase "candidate waste sources" is retired; the replacement is "pre-segment pattern classes with waste summed in P2".

**Inevitability step (trigger observation) (retained term, REV-03 §6):** the step f at which slack first becomes negative on the recorded path. "Trigger" always means this observation. The at-step's class and waste are recorded-path facts (trigger frequency, at-step waste); they assert nothing about what would have happened had the at-step's action differed.

**Mechanism-established (retained, REV-03 §6):** a distinct, stronger claim requiring intervention/counterfactual evidence beyond observed-path diagnostics (e.g. a run in which the pattern is intervened upon under otherwise identical conditions, with the outcome difference measured and the intervention's validity stated). Default status for every waste-sufficient (accounting) result remains **mechanism INCONCLUSIVE (accounting only)** unless such evidence is separately authorised, obtained, linked by identifier, and reported with its own validity limits. Path dependence is the reason observed-path waste cannot substitute for intervention evidence: changing an earlier action changes later states, Q inputs, and reference values, so any counterfactual path is a different trajectory, not the recorded trajectory with one step's waste removed — and this specification asserts nothing about such trajectories.

### 5.2 Exact exclusions, restated arithmetically (supersede REV-03 §5.6 wording; the exclusion conditions themselves are retained)

- **Dec/K NOT_SUPPORTED for a region:** every pre/at eligible step in the region is OPT, so the region's recorded-path pre/at waste sum is 0. **Stated arithmetically:** no pattern in this region meets the waste threshold on the recorded path; any threshold-meeting sum on recorded paths lies in other regions' pre/at steps, in unassigned buckets, or in episodes excluded from P3 (reported separately in the excluded-episode ledger). No statement is made about where the episode's outcome "came from".
- **K3 NOT_SUPPORTED for a region:** every timing-critical pre/at step in the region is K-correct or partial-correct (fall-through, §3.2 step 6). No timing-critical steps in the region ⇒ K3 N/A for the region, not NOT_SUPPORTED. (Unchanged in substance from REV-03; the fall-through reference is updated to §3.2.)
- **Ex1-EVENT-as-sole-accounting-source NOT_SUPPORTED:** crushes_total = 0 (REV-03 rule, relabelled). This excludes crush events as a sole accounting source on the recorded path; it does not exclude Ex-DEV, policy patterns, or other event patterns, and it asserts nothing about counterfactual crush-free trajectories.
- **Ex-DEV NOT_SUPPORTED for a job:** every step CONFORMANT and every episode protocol-conformant (exact zero mismatches, REV-02 rule retained).
- **Job-level INCONCLUSIVE (default)** for accounting-sufficient claims where any §4.1 P4 condition fails, n_pre = 0, segments are not reported separately, non-conformant/sequence-invalid episodes are pooled into causal denominators, or region/scope is not stated.

Occurrences in **claim sentences about episodes, patterns, or outcomes** must be rewritten in the mandatory form or the sentence removed and the mechanism status stated as INCONCLUSIVE. (The check applies to claim sentences only: the same words in criterion descriptions — e.g. "what would justify a protocol attribution" in REV-03 §3.3, or "what would have happened" inside this section's own non-counterfactual clauses — are not claim sentences and are not flagged. ## 6. Numbered identity set — the single reconciliation standard (supersedes REV-03 §4.4 identities in full; identities are specification requirements, NOT empirically validated claims)

**Status of this section (explicit, per work-order item 5):** no identity below has been checked against data in this revision, because this revision authorises no computation. Each identity is a **requirement** that a future computation and report must satisfy exactly. Failure of any identity in a future report means the report is invalid as a counting/accounting matter (counting error, classification error, segment error, or V error — to be investigated, never adjusted silently). Failure does not falsify the specification; it invalidates the report. A report that does not show every identity that applies to its claims is incomplete.

**Single-counting priority for I0 (binding):** every P0 step is counted exactly once in I0, by this priority: (1) INVALID-RECORD (missing position_before/action/tick, contradictory phase, or — for suboptimal steps — INVALID-K contradiction; see below); (2) TERMINAL-DEV; (3) UNREACH; (4) CRUSH-ND; (5) OPT; (6) K classes (K3-FULL / K3-PARTIAL / K3-UNRESOLVED / KBLANK / KNEVER / KUNK / K-STATUS-UNKNOWN — for suboptimal, timing-critical steps; K classes do not apply to OPT steps, which are already counted at priority (5)); (7) HEAD / SEL (suboptimal, non-timing-critical steps with full Q, or timing-critical steps falling through K3 per §3.2 step 6); (8) SUBOPT-UNCLASS (Population Q: Q/act missing for the split); (9) FIELD-MISSING-PATTERN (suboptimal steps with missing K fields, not OPT, not otherwise invalid). **Attributes are never summands:** INVALID-K, FIELD-MISSING-K, REPAIRED, TYPE-FLAG, and PHASE-ONLY sub-states are cross-tabulated alongside I0 (e.g. "of n_OPT steps, k carry FIELD-MISSING-K attribute"), never added to I0 totals. Consequence, stated to prevent the REV-03 ambiguity: an OPT step with missing K fields is counted once as OPT in I0 (with FIELD-MISSING-K attribute shown); a suboptimal step with missing K fields is counted once as FIELD-MISSING-PATTERN in I0 (with FIELD-MISSING-K attribute shown); a suboptimal step with an INVALID-K contradiction is counted once as INVALID-RECORD in I0 (with INVALID-K sub-label shown); an OPT step with an INVALID-K attribute is counted once as OPT in I0 (with INVALID-K attribute shown) — the K-contradiction for an OPT step is a record-integrity flag for K purposes, not a change to its OPT class (OPT determination does not use K fields). K-STATUS-UNKNOWN is a summand (priority (6)) only for suboptimal, timing-critical K = 0 steps with tuple UNKNOWN; an OPT step with tuple UNKNOWN is counted as OPT (priority (5) first).

- **I0 — Total recorded (per job, per episode, per region/segment as applicable):**
  total_recorded = n_OPT + n_K3-FULL + n_K3-PARTIAL + n_K3-UNRESOLVED + n_KBLANK + n_KNEVER + n_KUNK + n_K-STATUS-UNKNOWN + n_HEAD + n_SEL + n_SUBOPT-UNCLASS + n_FIELD-MISSING-PATTERN + n_CRUSH-ND + n_UNREACH + n_TERMINAL-DEV + n_INVALID-RECORD.
  Every P0 step counted exactly once (priority above). Dec3 remains an attribute, not a summand (REV-02 retained).
- **I1 — P1 pattern identity:**
  n_P1 = n_OPT + n_K3-FULL + n_K3-PARTIAL + n_K3-UNRESOLVED + n_KBLANK + n_KNEVER + n_KUNK + n_K-STATUS-UNKNOWN + n_HEAD + n_SEL + n_SUBOPT-UNCLASS + n_FIELD-MISSING-PATTERN.
  Equivalently: n_P1 = total_recorded − n_CRUSH-ND − n_UNREACH − n_TERMINAL-DEV − n_INVALID-RECORD. n_P1-classifiable = n_P1 − n_FIELD-MISSING-PATTERN (labelled whenever used).
- **I2 — P2 contributor and trigger identities (per region, P3 episodes only):**
  n_pre = Σ over pattern classes (OPT, K3-FULL, K3-PARTIAL, K3-UNRESOLVED, KBLANK, KNEVER, KUNK, K-STATUS-UNKNOWN, HEAD, SEL, SUBOPT-UNCLASS) of count_P_pre + count_FIELD-MISSING-PATTERN_pre.
  (OPT pre steps and crush/OPT zero-waste steps: OPT steps in pre segments count in n_pre and in count_OPT_pre; their waste is 0 — frequency and waste ledgers are separate, and an OPT-heavy pre segment correctly shows high OPT frequency with zero OPT waste.)
  # P3 failed episodes = Σ over pattern classes of (# episodes with f-class P) + n_trigger-unknown.
  Post identity (descriptive only, separate ledger): n_post = Σ count_P_post + count_FIELD-MISSING-PATTERN_post (post steps of P3 episodes only; post steps of excluded episodes belong to the excluded-episode descriptive ledger, §4.3, never to n_post).
- **I3 — P3 waste ledger + telescoping (per P3 episode, pre+at segments):**
  total_P3_waste(ep) = waste_SEL + waste_HEAD + waste_K3-FULL + waste_K3-PARTIAL + waste_K3-UNRESOLVED + waste_KBLANK + waste_KNEVER + waste_KUNK + waste_K-STATUS-UNKNOWN + waste_SUBOPT-UNCLASS + waste_FIELD-MISSING-PATTERN (all pre/at, ep).
  Assigned subtotal = waste_SEL + waste_HEAD + waste_K3-FULL + waste_K3-PARTIAL. Unassigned subtotal = total_P3_waste(ep) − assigned subtotal (equivalently the sum of the remaining buckets above; both forms shown).
  **Telescoping check (must hold exactly for every P3 episode):** total_P3_waste(ep) = slack_start(ep) − slack_after(f). Failure → episode P3-INVALID (§4.4), removed from P3, reported in the excluded-episode ledger. OPT/crush zero contributions are included as computed zeros (n_zero-computed counts, I4); they add 0 and do not affect the equality.
- **I4 — Waste-undefined vs computed-zero separation:**
  n_waste-undefined (by reason: MISSING-POSITION-AFTER, MISSING-REFERENCE, V-INFINITE/UNREACH, MISSING-POSITION-BEFORE) counts P0 steps whose waste cannot be computed. **Zero** waste-undefined steps are in any P3 episode (P3 condition (iv) forbids them). n_waste-undefined steps are assigned waste in **no** ledger (not 0, not unassigned, not descriptive-waste sums — they are counts only, with reasons). n_zero-computed counts P3 steps whose waste is computed as 0 (OPT steps, crush steps). The two counts are distinct quantities and must never be merged, summed, or substituted: computed 0 is a value; undefined is an absence of value.
- **I5 — Per-population reconciliation (must be shown for every population a report uses):**
  For P1: total_recorded − n_CRUSH-ND − n_UNREACH − n_TERMINAL-DEV − n_INVALID-RECORD = n_P1 (same as I1, shown as a reconciliation).
  For P2: (P3-episode pre steps) = n_pre, with P3-ineligible-episode pre steps reconciled via the excluded-episode ledger (count of pre steps in excluded failed episodes, by episode reason, shown separately — they are not in n_pre and not in any P2 numerator).
  For P3: (failed episodes in scope) = (# P3 episodes) + (# excluded failed episodes, by reason code §4.3, precedence PROTOCOL > SEQUENCE > NONCONF > WASTE-UNDEFINED > INVALID-RECORD > REPAIRED). A step in an excluded episode is counted once under the episode's reason, never also under a step reason for P3. The same precedence, applied per population, governs P1/P2/2-T/2-C reconciliations where a step is excluded for multiple reasons (precedence stated in the report; if a different precedence is used, it must be stated and applied consistently, and every identity must still sum exactly).
  For P4: (failed episodes in scope) = (# P3 episodes) + 0 excluded (P4 eligibility requires zero excluded); otherwise the job is P4-ineligible and no job-level denominator is asserted (I2 trigger denominator then covers P3 episodes only, labelled per-episode scope, not job scope).
  For 2-T / 2-C: reconciliations in REV-03 §4.4 form, with reason codes from §4.3 checks, restated per population (a step excluded from 2-T for a target-only failure may still be in P3 — the reconciliations are per population and must not be merged into one exclusion count).
- **I6 — F/Q and job totals:**
  F counts (full-Q population) and Q counts (Q-missing population, SUBOPT-UNCLASS) are reported separately for every identity above, never pooled into a combined pattern total without showing both splits. Combined total_recorded = n_F-total + n_Q-total only for total-recorded accounting (where n_F-total / n_Q-total are the F/Q splits of total_recorded, each itself satisfying I0 over its sub-population). Job totals = Σ over episodes in the job, with P3/P4 scopes stated per job (a job total over P3 episodes only must be labelled "P3 episodes only", never as a job total without qualification).

## 8. Bounded conclusion — what this revision fixes, and what remains unresolved (deliverable 6)

**Answer: REVISION-04 corrects the five identified internal inconsistencies and is ready for owner approval as a specification — with the remaining limits stated below, which are limits of authorisation, measurement, and mechanism evidence, not hidden inconsistencies in the corrected rules. This conclusion is about the specification's readiness, not about any diagnostic having succeeded. No diagnostic has succeeded, no mechanism has been established, and no trajectory has been collected under this revision. No identity in §6 has been empirically validated; each is a requirement a future computation must satisfy exactly, and failure of any identity in a future report invalidates that report's counting, not this specification.**

**What is now internally consistent (and was not, before this revision):**
- Availability follows the verified code (§2): raw phase needs a clean opening alone (no open_len, no period); raw remaining needs a clean opening plus open_len; remaining-available implies phase-available and never the reverse; the K flag is the AND-gate over raw values and the model-visible slots are blanked whenever K = 0, so a phase-only step is described as raw-available and input-blanked together, never as "no schedule information" and never as "phase information in the input". Span cleanliness is a recorded field (R-SPAN-CLEAN), never inferred from K = 1 or from an opening tick alone. The corrected availability table (§2.2) and state descriptions (§2.4) replace REV-03's both-fields partial definition, its K = 1 ⇒ clean-span claim, and its reversed KBLANK parenthetical.
- K3-UNRESOLVED is one rule everywhere (§3): per-component outcomes (MATCH / MISMATCH / UNRESOLVED-C) combined by a fixed priority (INVALID-K, then K_rec = 0 availability states, then any UNRESOLVED-C → UNRESOLVED, then FULL, then PARTIAL, then fall-through). Missing provenance without a demonstrated true-difference is never a mismatch; blanked K = 0 slots are never compared to true features as estimates; split provenance is handled per component (a judgeable phase mismatch with no unresolved component is PARTIAL; an unjudgeable remaining true-difference is UNRESOLVED; matching true features with missing provenance is fall-through, corrected from REV-03 clause 2). The table (§3.3) and the partition proof (§3.4) use this rule identically, and n_K3 = n_K3-FULL + n_K3-PARTIAL + n_K3-UNRESOLVED holds by the proof over the steps the rule is applied to.
- Populations and accounting reconcile across five defined populations (§4): P0 (all recorded steps, I0 single-counting priority with attributes never double-summed), P1 (descriptive pattern counts + FIELD-MISSING-PATTERN status line, I1), P2 (contributor frequencies over pre segments of P3 episodes, with FIELD-MISSING-PATTERN steps in the denominator only, I2), P3 (all-or-nothing episode waste accounting with telescoping check, excluded-episode descriptive ledger, I3/I4), and P4 (job-level gate: frequency prescribed + zero excluded failed episodes in scope). A FIELD-MISSING-PATTERN step in a P3 episode is counted exactly once in each ledger it belongs to (P1 status line, P2 denominator, P3 unassigned waste) and zero times in any pattern class count — the bridge REV-03 lacked. Target/type-only failures keep TYPE-FLAG retention in P3 (path fields, not record fields, govern waste) while excluding the step from transition-event claims.
- Accounting language contains no counterfactual mechanism implication (§5): sole, joint, and blocker rules are stated as inequalities between sums on the recorded path, each carrying an explicit clause asserting nothing about any unobserved trajectory in which the pattern was removed, replaced, or changed. Phrases such as "even without any other pattern's waste, the episode would have lost recoverability", "unassigned waste alone could account for the loss", "multiple sufficient waste sources", and "failure's waste must come from elsewhere" are listed as prohibited in claim sentences with mandatory arithmetic replacements, and the audit rule is extended to flag them. Passing the audit changes the language of a conclusion, not its mechanism status, which remains INCONCLUSIVE (accounting only) for every waste-sufficient result unless intervention evidence is listed.
- Identities are single and numbered (§6): I0 (total recorded), I1 (P1), I2 (contributor + trigger), I3 (P3 ledger + telescoping), I4 (waste-undefined vs computed-zero), I5 (per-population reconciliation with reason-code precedence), I6 (F/Q and job totals). F/Q counts are never pooled without showing both splits; combined totals are labelled by scope (P3-only totals are never presented as unqualified job totals).

**Remaining limits — stated explicitly, so that "ready for owner approval" is not misread as "ready for collection", "diagnosis complete", or "mechanism proved":**
1. **Thresholds, combination rule, and several definitions are still unset or unapproved** (decisions 1–17 in §7). The revision defines the *forms* exactly (availability table, K combination rule, five populations, identity set, counterfactual-free language, Table C form), but T_pre/Y_pre/T_trig values, the Rule C/T/CT choice, the protocol-attribution criterion, the repair-inclusion rule, the ScheduleModel-version verification ruling, and the REV-04 definition approvals themselves require owner decisions before collection. Until they are set, the strongest job-level statements available are exact exclusions, descriptive pattern/frequency/waste reports, and per-episode accounting results — not job-level accounting-sufficient claims, and not mechanism claims of any kind.

No V table was computed, no step was checked, and no waste sum was produced, because this work order authorises correction only.
