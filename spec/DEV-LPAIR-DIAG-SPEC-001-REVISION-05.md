**What this revision changes, in one paragraph:**
REVISION-04 was substantially improved but left six formal gaps, all in how edge cases are classified — not in the pilot evidence. First, its component rule let a recorded value equal the true schedule while contradicting its own partial expectation, with no complete invalid rule for that combination, so its partition proof overstated mutual exclusivity. Second, it used one field name for both a raw value and its availability, so its K-gate contradiction checks could not be applied reliably. Third, it assumed one missing-field defect at a time, so a step missing both K and Q/act information — or a non-timing-critical step missing K information it does not need — had no consistent outcome across P1, P2, trigger counts, and I0/I1. Fourth, it created P3-INVALID for telescoping failures but left that code out of the exclusion-reason scheme and the P4 gate. Fifth, it called blocked_log a record field for waste purposes while retaining it inside C-TRANS, so a blocked-log-only discrepancy had no stated P3 consequence. Sixth, its I0 priority list was flat and therefore misclassified the overlapping-defect cases in the third gap. REVISION-05 corrects all six without redesigning the diagnostic: a complete component-outcome matrix with an explicit inconsistency outcome and precedence; split field types (value, availability flag, slot, recording status) with corrected gate checks; a single decision tree for overlapping defects that replaces the flat I0 list; three explicit P3 stages (initial eligibility, accounting validation, final membership) with P3-INVALID in the ledger and the gate; and a PATH/LOG split of transition conformance under which a log-only discrepancy does not exclude an episode from waste accounting. The diagnostic's scientific question is preserved: K3 still asks whether schedule features explain suboptimality, K3-FULL remains the schedule-error class, and partial-correct features remain fall-through — what changes is that a mismatch against a model's own partial expectations is now honestly labelled as a record inconsistency, not as schedule behaviour (see §3.4).

**Reading rule (binding):** whenever a rule in this specification cites "raw availability", it means the -AVAIL fields (or, equivalently, VAL-is-not-None when VAL is recorded and STATUS is ENCODE-TIME). Whenever a rule cites "recorded features" or phase_rec/remaining_rec, it means the unscaled -SLOT values. Whenever a rule cites "raw values", it means the -VAL fields. A rule that cites the wrong field type for its purpose is misapplied even if its conclusion happens to match: in particular, K-gate checks must never be run on -SLOT values (blanked 0.0 is not "unavailable" evidence beyond the K flag itself) and never on -VAL values alone without their -AVAIL flags (a NULL-VALUE is evidence of unavailability only through the flag identity in §2.3).

### 2.2 What "K fields" means (for §4 K-defect routing)

"K fields" for a step = R-K-FLAG + R-SLOT-PHASE + R-SLOT-REM. "K fields missing" = any of those three absent (NOT-RECORDED). -VAL/-AVAIL/-STATUS fields are **provenance fields**, not K fields: their absence does not by itself make K fields missing (a step can have complete K fields with unknown raw provenance — then gate checks are inapplicable and availability sub-states are UNKNOWN-FEAT, but K classification proceeds on slots + R-EST-CUR + R-LAST-OPEN/R-OPEN-LEN/R-SPAN-CLEAN as in §3). Conversely, complete -VAL/-AVAIL fields do not cure missing K fields: if slots are absent, phase_rec/remaining_rec do not exist and §3 comparisons cannot run (routed per §4 tree).

### 2.3 K-gate contradiction checks, rewritten (supersede REV-04 §3.3 KX2 rows; all checks use -AVAIL, never -VAL alone and never -SLOT)

Each check fires only when every field it cites is recorded with STATUS ENCODE-TIME (for -AVAIL fields) or recorded at all (for R-EST-CUR/R-LAST-OPEN/R-OPEN-LEN/R-SPAN-CLEAN/R-K-FLAG). If any cited field is Unknown/NOT-RECORDED/RECOMPUTED-INVALID, the check **does not fire** (absence of evidence, not evidence of consistency — the step proceeds under Unknown-provenance handling, never as "gate-consistent by default" in a way that would assert consistency; gate-consistency is simply not established, and §3 Unknown-branch rules apply where relevant).

- **KX2a:** R-EST-CUR = True ∧ R-K-FLAG = 0 ⇒ INVALID-K. (Full estimates imply both raw values available, hence K = 1 by the encoder gate.)
- **KX2b (corrected OR-form; REV-04 required both False — superseded):** R-K-FLAG = 1 ∧ (R-FEAT-PHASE-AVAIL = False ∨ R-FEAT-REM-AVAIL = False), where each False cited is recorded (not Unknown) ⇒ INVALID-K. (The gate requires **both** available; either one recorded False contradicts K = 1. A single recorded False suffices; the other flag may be True, False, or Unknown — the OR-form already fires on the recorded False.)
- **KX2c:** R-EST-CUR = False ∧ R-LAST-OPEN = NONE-GENUINE ∧ R-K-FLAG = 1 ⇒ INVALID-K. (K = 1 without full estimates requires a partial path, which requires a held opening.)
- **KX2d:** R-EST-CUR = False ∧ R-LAST-OPEN integer ∧ R-SPAN-CLEAN = True ∧ R-OPEN-LEN = NONE-GENUINE ∧ R-K-FLAG = 1 ⇒ INVALID-K. (K = 1 without full estimates requires remaining available, which requires open_len.)
- **KX2d-span:** R-EST-CUR = False ∧ R-SPAN-CLEAN = False (recorded) ∧ R-K-FLAG = 1 ⇒ INVALID-K. (An unclean span gives no partial phase and no partial remaining, so K = 1 is impossible without full estimates.)
- **KX2e (corrected both-True form; REV-04 left the form implicit — now explicit):** R-K-FLAG = 0 ∧ R-FEAT-PHASE-AVAIL = True ∧ R-FEAT-REM-AVAIL = True (both recorded True) ⇒ INVALID-K. (Both available ⇒ gate sets K = 1.) A single recorded True with the other False is consistent with K = 0 (not both); a single recorded True with the other Unknown does not fire (cannot establish both).
- **KX2f (new; AVAIL/VAL and slot/raw contradictions):** any of the following, with the cited fields recorded and STATUS ENCODE-TIME where -VAL/-AVAIL are cited, ⇒ **INVALID-FEAT-RECORD** (a K-defect outcome distinct from INVALID-K; routed per §4 tree as a K-defect):
  - (f1) R-FEAT-PHASE-AVAIL = True ∧ R-FEAT-PHASE-VAL = NULL-VALUE, or R-FEAT-PHASE-AVAIL = False ∧ R-FEAT-PHASE-VAL = integer (and the same two patterns for REM). (Flag/value identity violated within the provenance record itself.)
  - (f2) R-K-FLAG = 1 ∧ R-FEAT-PHASE-VAL recorded ∧ R-SLOT-PHASE × 20.0 ≠ R-FEAT-PHASE-VAL (beyond float-representation tolerance, stated in R-CFG as the exact comparison used — this revision does not set a numeric tolerance; the collection's R-CFG must state it before collection), or the same pattern for REM with × 10.0. (Slot does not reproduce the raw value the encoder is recorded as having produced.)
  - (f3) R-K-FLAG = 0 ∧ (R-SLOT-PHASE ≠ 0.0 ∨ R-SLOT-REM ≠ 0.0) with the slot recorded. (Blanking rule violated: K = 0 requires both slots 0.0.)
  - Note: (f2) requires K = 1; when K = 0, slots are blanked by rule and carry no information about VAL (a phase-only step has VAL integer with slot 0.0 by design — that is **not** a contradiction; (f2) must never be applied to K = 0 steps).

**INVALID-K vs INVALID-FEAT-RECORD (distinction, binding):** INVALID-K = the K flag contradicts the encoder gate or the model's estimate state (KX2a–KX2e). INVALID-FEAT-RECORD = the feature record contradicts itself (flag/value/slot identity, KX2f). Both are K-defects for §4 routing (timing-critical suboptimal steps take the corresponding defect outcome; non-timing-critical steps carry the defect as an attribute only). They are kept as separate outcomes because their remedies differ: INVALID-K indicates a gate/state recording error; INVALID-FEAT-RECORD indicates a provenance/slot recording error. Neither outcome asserts anything about schedule behaviour.

## 3. Complete K3 outcome rule — component matrix, combination rule, corrected table, proof (supersedes REV-04 §3.1–§3.4 in full; deliverables: corrected K3 outcome rule, corrected K3 decision table, partition proof)

This section governs **timing-critical, suboptimal steps with K fields present and no K-defect** (the §4 tree routes all other steps before §3 is reached: path-invalid, state-excluded, OPT, K-defect, and non-timing-critical steps never reach §3). True periodic features are as in REV-01 §3.4 (retained): true_phase = t_pre mod 20, true_remaining = (10 − true_phase) if true_phase < 10 else 0. Recorded features are phase_rec = R-SLOT-PHASE × 20.0 and remaining_rec = R-SLOT-REM × 10.0 (model-visible slot values unscaled — §2.1 reading rule). Partial expectations are as in REV-04 §3.1 (retained, restated here for completeness): partial_phase_exp = t_pre − last_opening_tick (elapsed, not modulo-wrapped) when phase partial comparison is completable; partial_remaining_exp = max(0, open_len − partial_phase_exp) if door_open_pre is true, else 0, when remaining partial comparison is completable.

### 3.1 Governing principle — why full mismatch and partial mismatch are different kinds of finding

- **Full expectations are world-referential.** Under est_full_cur = True, the model's features are periodic projections from its estimates (period, open_len, last_opening) onto the true schedule's cycle. Comparing recorded features to true periodic features tests whether the model's **estimates about the world** are correct. A mismatch here is a genuine schedule-estimation error: the model claims periodic knowledge and the claim is wrong. This is the only mismatch outcome that supports a schedule-error class (K3-FULL).
- **Partial expectations are model-self-referential.** Under est_full_cur = False, the partial expectation for a component is computed from the model's **own** held opening, span cleanliness, and open_len — the same state that generated the recorded partial output under the stated ScheduleModel rules (carried from REV-04 §2.1). Comparing recorded features to partial expectations therefore tests whether the **record is self-consistent** (features, provenance, and tick agree under the stated rules), not whether the model's view of the world is correct. A mismatch here ordinarily indicates a recording, timing, or implementation inconsistency — for example, the recorded opening/span/tick does not match the state that produced the recorded feature, or the feature was recomputed under different rules. It does not, by itself, indicate a distinct schedule-estimation behaviour, because under correct recording the encoder's partial output equals its partial expectation **by construction**.
- **Partial-vs-true difference is neither.** A partial-correct feature (recorded = partial expectation) that differs numerically from the true periodic feature (non-modulo elapsed ≥ 20, or remaining computed from elapsed rather than phase) is the normal, expected consequence of lacking a period. It is a **design limitation of partial knowledge**, not a per-step error and not a consistency failure. It is recorded descriptively (partial-correct attribute) and falls through to HEAD/SEL; it never becomes a failure class. Any future proposal to make partial-vs-true difference itself a failure class would be a redesign of the diagnostic's question (it would classify nearly every late partial step as failing) and is **not** adopted here.
- **Consequence for labels (binding):** the label K3-PARTIAL, which in REV-03/REV-04 denoted a schedule-error-like class for partial mismatches, is **retired**. Its replacement, K3-PARTIAL-INCONSISTENT (§3.4), denotes only the self-consistency finding above. No report may cite a K3-PARTIAL-INCONSISTENT step as evidence that "partial schedule knowledge caused suboptimality" or any equivalent schedule-behaviour claim; the citable claim is exactly: "recorded features conflict with the partial expectations computed from the step's own recorded provenance under the stated ScheduleModel rules (recording, timing, or implementation inconsistency — specific cause not determined by this diagnostic)."

### 3.3 Step combination rule — one precedence, applied identically in prose, table, and proof

§3 applies only to timing-critical, suboptimal steps with K fields present and no K-defect (per §4 tree). For such a step:

1. **K_rec = 0 rule.** If R-K-FLAG = 0, the step takes an availability state (KBLANK / KNEVER / KUNK / K-STATUS-UNKNOWN by tuple rules, REV-04 §2.4 retained), **never a K3 class and never a component outcome**. Reason (retained from REV-04): recorded slots are blanked constants (0.0), not estimates; blanked values are never compared to true or partial expectations as estimates. (Raw -VAL/-AVAIL facts for K_rec = 0 steps remain descriptive mechanism-internal quantities per REV-04 §2.2, never K3 classes.)
2. **K_rec = 1, any INCONSISTENT-C → K3-PARTIAL-INCONSISTENT.** A definite record defect in any component dominates attribution gaps: the step's K data cannot be trusted as stated, so no schedule-error or unresolved-attribution class may be assigned to the step as a whole. (If one component is INCONSISTENT-C and the other is UNRESOLVED-C, the step is INCONSISTENT, not UNRESOLVED — stated precedence, resolving the split-provenance ambiguity in REV-04.)
3. **K_rec = 1, any UNRESOLVED-C (and no INCONSISTENT-C) → K3-UNRESOLVED.** A demonstrated true-difference exists for at least one component whose error status cannot be determined from recorded provenance.
4. **K_rec = 1, est_full_cur = True, any FULL-MISMATCH (and no INCONSISTENT-C/UNRESOLVED-C, which cannot occur under est_full True per §3.2) → K3-FULL.** The only schedule-error K3 class.
5. **K_rec = 1, all components MATCH or MATCH-TRUE → fall-through (K3 NOT_SUPPORTED for this step).** The step proceeds to HEAD/SEL in the partition (or to SUBOPT-UNCLASS if Q-defective, per §4 tree step T3c). Attributes recorded: K-correct (est_full True), partial-correct (est_full False, completable, matched partial), or true-correct (matched true with uncompletable/Unknown provenance).
6. **K fields missing, gate contradictions, and feat/slot contradictions do not reach this rule** — they are routed by the §4 tree (FIELD-MISSING-PATTERN, INVALID-K, INVALID-FEAT-RECORD respectively) before §3 is applied. §3's proof (§3.6) therefore covers exactly the steps in §3's domain; it does not claim to classify K-defect steps, which have their own tree outcomes.

**Missing provenance is never evidence of mismatch (restated, binding across §§3–6):** no step or component is assigned MISMATCH, FULL-MISMATCH, or INCONSISTENT-C on the basis of a missing field. INCONSISTENT-C requires a completable partial comparison and a recorded value differing from it. UNRESOLVED-C requires a demonstrated true-difference plus an uncompletable/Unknown comparison. MATCH-TRUE requires a recorded value equalling true. If no applicable rule can be established from the recorded fields for a component, that component's outcome is UNRESOLVED-C only when a true-difference is demonstrated; otherwise MATCH-TRUE (if equal to true) or, for K_rec = 0 / K-missing steps, the availability/defect outcome of §4 — never an invented mismatch.

### 3.6 Partition proof — with edge cases enumerated (supersedes REV-04 §3.4 proof)

**Claim:** for steps in §3's domain (timing-critical, suboptimal, K fields present, no K-defect — after §4 tree steps T0–T3a), the §3.3 rule assigns exactly one of {K3-FULL, K3-PARTIAL-INCONSISTENT, K3-UNRESOLVED, KBLANK, KNEVER, KUNK, K-STATUS-UNKNOWN, fall-through-to-HEAD/SEL/SUBOPT-UNCLASS}, with no overlap and no gap; and therefore, over steps assigned K3 classes, n_K3 = n_K3-FULL + n_K3-UNRESOLVED + n_K3-PARTIAL-INCONSISTENT holds exactly, where the third term is a descriptive inconsistency count with unassigned waste (not an assigned schedule-error count — the identity is a counting identity over descriptive K3-labelled outcomes, and only its FULL term may enter assigned sums).

**Proof sketch (specification-level, not empirical):** fix a step in §3's domain. K_rec is 0 or 1 (K fields present by domain). If K_rec = 0, §3.3 step 1 assigns exactly one availability state: the tuple statuses (VERIFIED before-first / VERIFIED NEVER / VERIFIED at-or-after-first / UNKNOWN) are mutually exclusive by definition (VERIFIED vs UNKNOWN; before-first vs at-or-after-first vs NEVER are disjoint ordinal relations for a VERIFIED tuple) — done, unique, and no component outcome is assigned (blanked slots are not estimates). If K_rec = 1, each component's outcome is exactly one entry of the §3.2 matrix: for est_full True, the two rows (recorded = true ⇒ MATCH; ≠ true ⇒ FULL-MISMATCH) are disjoint and exhaustive, and INCONSISTENT-C/UNRESOLVED-C cannot occur (true periodic is the applicable expectation); for est_full False + completable, the two rows (recorded = partial_exp ⇒ MATCH; ≠ partial_exp ⇒ INCONSISTENT-C) are disjoint and exhaustive, including recorded = true ≠ partial_exp (INCONSISTENT-C by the matrix — the owner's case is therefore classified, not left between MATCH and mismatch); for est_full False + incompletable, the two rows (recorded = true ⇒ MATCH-TRUE; ≠ true ⇒ UNRESOLVED-C) are disjoint and exhaustive; for est_full Unknown, the two rows (recorded = true ⇒ MATCH-TRUE; ≠ true ⇒ UNRESOLVED-C) are disjoint and exhaustive regardless of completability (path unknown prevents FULL-MISMATCH and INCONSISTENT-C by definition). The step rule then applies in fixed priority: any INCONSISTENT-C ⇒ INCONSISTENT (step 2); else any UNRESOLVED-C ⇒ UNRESOLVED (step 3); else est_full True + any FULL-MISMATCH ⇒ FULL (step 4 — INCONSISTENT-C/UNRESOLVED-C cannot co-occur here, per the matrix); else all MATCH/MATCH-TRUE ⇒ fall-through (step 5). Each priority branch's condition excludes the earlier branches' conditions (step 3 requires no INCONSISTENT-C; step 4 requires est_full True, which excludes INCONSISTENT-C/UNRESOLVED-C; step 5 requires no MISMATCH/INCONSISTENT-C/UNRESOLVED-C). Hence exactly one step outcome. The K3 counting identity follows by counting steps assigned the three K3-labelled outcomes. ∎

**Edge cases explicitly covered (each verified against the tree/matrix, not merely asserted):**
- **Simultaneous Q + K missingness:** outside §3's domain — routed by §4 tree (timing-critical ⇒ FIELD-MISSING-PATTERN with Q-defect as secondary attribute; non-timing-critical ⇒ SUBOPT-UNCLASS with K-defect as attribute). §3's proof does not need to classify such steps because the tree classifies them first; §4.4 states their P1/P2/trigger treatment identically.
- **Non-timing-critical steps with missing K fields:** outside §3's domain — §4 tree T3d (HEAD/SEL or SUBOPT-UNCLASS by Q-defect; K-defect attribute only). They never receive K3/availability classes, so they cannot break the §3 partition.
- **Contradictory feature provenance (owner's case + gate contradictions):** owner's case (recorded = true, partial mismatch, est_full False, completable) ⇒ INCONSISTENT-C ⇒ K3-PARTIAL-INCONSISTENT (§3.2 matrix, §3.5 row KI1). Gate contradictions (KX2a–KX2e) and feat/slot contradictions (KX2f) ⇒ INVALID-K / INVALID-FEAT-RECORD via §4 tree, before §3 is reached — so no step reaches §3 with a gate contradiction that §3 would have to resolve.
- **Episodes rejected after the telescoping check:** outside §3's domain (episode-level, §5) — such episodes' steps retain their §3/§4 step outcomes descriptively, but contribute to no P3 ledger, no P2 denominator, and no P4 claim; their episode-level accounting is the excluded-episode descriptive ledger (§5.2), not a step-classification failure.
- **Unknown path with computable partial expectation:** covered by the Unknown rows of the matrix (recorded ≠ true ⇒ UNRESOLVED-C, never INCONSISTENT-C — inconsistency requires a known partial path).
- **Split provenance (one component completable, the other not):** covered per component by the matrix plus step precedence (INCONSISTENT dominates UNRESOLVED — §3.3 step 2 before step 3; row KI2).

**What the proof does not establish (stated explicitly):** the proof establishes that the *rule* partitions the steps in its stated domain; it does not establish that any real collection's records satisfy the rule's field requirements (that is a collection-validity question, answered per step by the tree/matrix outcomes including defect outcomes), nor that assigned classes describe any mechanism (mechanism status remains INCONCLUSIVE (accounting only) per REV-04 §5 retained, unless intervention evidence is separately supplied). A collection in which the proof's preconditions fail yields defect outcomes under the tree, not proof failures.

## 4. Overlapping missing-field rule — one decision tree for every step (supersedes REV-04 §6 I0 flat priority list and REV-04 §3.2 step 7 / §4.1 Q/K routing in part; deliverable: complete overlapping-missing-field classification rule)

### 4.1 Definitions (used identically in §§4–6)

- **Q-defect:** selector Q missing, OR any head Q missing, OR taken act missing — any one of the three needed for the SEL/HEAD split. (Action present alone does not cure act missingness for the split: without act, the selector's chosen head is unknown, so SEL/HEAD cannot be distinguished — SUBOPT-UNCLASS handling, retained from REV-04 §4.2.)
- **K-defect:** any of: (a) K fields missing (any of R-K-FLAG / R-SLOT-PHASE / R-SLOT-REM absent); (b) gate contradiction (KX2a–KX2e, §2.3); (c) feat/slot contradiction (KX2f, §2.3). K-defect outcomes are, respectively: (a) FIELD-MISSING-PATTERN (timing-critical) — see tree; (b) INVALID-K; (c) INVALID-FEAT-RECORD.
- **Timing-critical:** retained definition from REV-02/REV-04 (a step on which schedule features could affect whether the taken action is in the suitable set R(s) — i.e. steps where K classification is decision-relevant). Timing-criticality is a property of the step's state/action context under the reference, not of its recorded fields: a step's timing-criticality is determined even when its K fields are missing (otherwise missingness would change the branch and the tree would be circular — the reference computation that determines timing-criticality uses positions/reference, not K fields). If timing-criticality itself cannot be determined for a step (reference uncomputable), the step is UNREACH-handled per REV-04 §4.2 (reference uncomputable ⇒ UNREACH), not tree-routed.
- **Secondary attribute:** a defect recorded alongside a step's outcome without changing the outcome. Secondary attributes are cross-tabulated (counts shown), never summands, and never alternate outcomes: a step has exactly one outcome (tree result) plus zero or more secondary attributes.

### 4.2 Decision tree (authoritative for P0/I0 classification — the REV-04 flat priority list is superseded and must not be used)

Apply in order. Stop at the first step that assigns an outcome. (T0–T2 need neither K nor Q fields, which is why OPT outranks both defect types.)

- **T0 — Path fields.** Position_before present and a valid grid cell, taken action present, t_pre present, and phase consistent (phase = t_pre mod 20)? If any fails ⇒ **INVALID-RECORD** (sub-label by reason: MISSING-POSITION / MISSING-ACTION / MISSING-TICK / CONTRADICTORY-PHASE, REV-04 §4.1 retained). (Missing position_after does **not** trigger T0 — it triggers waste-undefined handling at episode level (§5, Stage A condition A4); a step can be pattern-classified with position_after missing, but its episode cannot be P3-eligible.)
- **T1 — State exclusions.** Position_before is the goal ⇒ **TERMINAL-DEV**. Reference V(s) = ∞ (or uncomputable) ⇒ **UNREACH**. State-forced crush step (position_before ∈ D ∧ door closed under true schedule) ⇒ **CRUSH-ND**. (Order among state labels follows REV-04 §4.1 priority: TERMINAL-DEV, then UNREACH, then CRUSH-ND — retained; state labels outrank pattern classes because the step is not pattern-eligible.)
- **T2 — OPT.** Taken action ∈ suitable set R(s) (reference, REV-01 §3.2 retained) ⇒ **OPT**. (OPT needs neither K nor Q fields. Any K-defect or Q-defect present is recorded as a secondary attribute only — e.g. "OPT step with K fields missing (attribute)" — and does not change the outcome. OPT waste is computed 0 in P3 episodes where applicable.)
- **T3 — Suboptimal steps (taken action ∉ R(s)). Branch on timing-criticality:**
  - **T3a — Timing-critical + K-defect ⇒ K-defect outcome (Q-defect, if also present, is a secondary attribute only).** Missing K fields ⇒ **FIELD-MISSING-PATTERN**. Gate contradiction ⇒ **INVALID-K**. Feat/slot contradiction ⇒ **INVALID-FEAT-RECORD**. (Rationale: K classes precede HEAD/SEL in the partition order, so a K defect blocks the partition before Q is reached. The Q-defect is still recorded — a future repair that supplies K fields would then face the Q question — but it does not change the current outcome.)
  - **T3b — Timing-critical + no K-defect ⇒ §3 outcome.** K_rec = 0 ⇒ availability state (KBLANK / KNEVER / KUNK / K-STATUS-UNKNOWN). K_rec = 1 ⇒ K3-FULL / K3-PARTIAL-INCONSISTENT / K3-UNRESOLVED / fall-through per §3.3. (Fall-through proceeds to T3c.)
  - **T3c — Fall-through (from T3b) ⇒ HEAD/SEL or SUBOPT-UNCLASS by Q-defect.** Q-defect present ⇒ **SUBOPT-UNCLASS**. Q-defect absent ⇒ **HEAD** or **SEL** by Q comparison (REV-02 §2 rules retained; Shared SEL/HEAD are pattern-only per REV-04 §5.4 condition 5 retained).
  - **T3d — Non-timing-critical ⇒ HEAD/SEL or SUBOPT-UNCLASS by Q-defect (K-defect, if present, is a secondary attribute only).** Q-defect present ⇒ **SUBOPT-UNCLASS**. Q-defect absent ⇒ **HEAD** or **SEL** by Q comparison. (Rationale: K classification is not decision-relevant for non-timing-critical steps, so K missingness/contradiction cannot block a Q-determinable HEAD/SEL outcome, and cannot create a FIELD-MISSING-PATTERN outcome where none is needed. A non-timing-critical step with K-defect and Q-defect is SUBOPT-UNCLASS with K-defect attribute — not FIELD-MISSING-PATTERN.)

**Why a tree, not a list (binding rationale):** a flat priority list orders outcomes independently of step properties, so it must pick one winner between FIELD-MISSING-PATTERN and SUBOPT-UNCLASS for all steps — but the correct winner depends on timing-criticality (T3a vs T3d), which a list cannot express. The tree conditions on timing-criticality explicitly, which is why it replaces the list. Any future classification rule that reintroduces a flat list for these outcomes is incomplete under REV-05 unless it reproduces the tree's timing-criticality branch.

State/INVALID lines = TERMINAL-DEV, UNREACH, CRUSH-ND, INVALID-RECORD. (This replaces REV-04's FIELD-MISSING-only denominator note with the general class/status rule — the FIELD-MISSING case is now one of four status lines under the same rule.)
- **Trigger lines:** for final-P3 episodes, one trigger line per class and per status (episodes whose f-step outcome is that class/status). n_trigger-unknown is defined as the residual: #final-P3 episodes − Σ trigger lines (all classes + all statuses). **Requirement: n_trigger-unknown must equal 0 for a valid P3 report** — every f-step in a final-P3 episode has a tree outcome by construction (f-steps are suboptimal, pattern-eligible, and in P3-eligible episodes, so T0–T3 assigns them an outcome). A non-zero residual indicates a classification gap (a step the tree failed to classify, e.g. a missing tree branch in reporting code) and invalidates the trigger reporting until investigated — it is a check quantity, not a bucket for unclassifiable steps. (This replaces REV-04's use of n_trigger-unknown as a bucket for FIELD-MISSING f-steps: FIELD-MISSING f-steps now have their own descriptive trigger line, so they are not "unknown".)
- **Waste ledgers (§6, I3):** class waste (SEL/HEAD/K3-FULL) is assigned; all other P1 lines' waste (availability classes, K-STATUS-UNKNOWN, and all four status lines) is unassigned, each in its own sub-bucket, shown separately. Status-line waste never enters assigned sums, sets, or thresholds (it enters waste_unassigned_total as a blocker input only, per §5/§6 retained form with the updated bucket list).

## 5. P3 stages, P3-INVALID accounting, and the PATH/LOG boundary (supersedes REV-04 §4.1 P3 condition (iii), §4.3 ledger, and §4.4 P3 ledger scope in part; deliverables: corrected P3 eligibility, validation, and exclusion-reason rules)

### 5.1 Three stages — initial eligibility, accounting validation, final membership (binding)

P3 membership is determined in stages, in order. A stage is evaluated only for episodes that passed all earlier stages. This sequential structure — not a priority list — is what guarantees one-count-per-episode reconciliation (§6, I5).

- **Stage A — Initial eligibility (path + protocol + record completeness).** A failed episode is initially eligible iff **all** of:
  - **A1 (C-PROTO):** episode/job protocol holds (length ≤ 200, ends after a reached step per positions or at exactly 200 steps, does not continue after a reached step per positions, start_phase S ∈ 0..19, episodes in stated order with stated start_phases). Protocol is judged on **positions** (reached per position_after = goal), not on reached flags — see §5.3 boundary for flag-driven termination.
  - **A2 (C-CONT):** continuity holds for the whole episode (position_before(0) = (0,0); position_before(s) = position_after(s−1) for s > 0; t_pre(0) = S; t_pre(s) = t_pre(s−1) + 1). Any break fails Stage A for the whole episode (REV-04 consequence retained, now as a Stage-A reason, not a step-level exclusion).
  - **A3 (C-TRANS-PATH):** every step passes C-TRANS-PATH (§5.3). (C-TRANS-LOG failures do **not** fail Stage A — see §5.3.)
  - **A4 (Computable waste):** every step has position_before/position_after present and reference V finite (hence no UNREACH step, no waste-undefined step). Missing position_after, missing reference, or V = ∞ fails Stage A for the whole episode.
  - **A5 (No disqualifying record status):** no INVALID-RECORD step (T0 outcome, §4.2) and no REPAIRED step in the episode. (Steps with secondary attributes — K-defect/Q-defect attributes on OPT/HEAD/SEL steps, TYPE-FLAG, LOG-FLAG, PHASE-ONLY sub-states — do **not** fail A5. Steps with defect **outcomes** (INVALID-K / INVALID-FEAT-RECORD / FIELD-MISSING-PATTERN / K3-PARTIAL-INCONSISTENT) do **not** fail A5 either: defect outcomes concern K classification, not path/record completeness for waste — their waste is computable from path fields and reference, so it enters the P3 unassigned ledger (§6, I3). A5 fails only on T0 INVALID-RECORD and REPAIRED status.)
  - Stage-A failure reasons (exactly one per episode, by the stage's own check order A1 → A2 → A3 → A4 → A5 — the first failing check in that order is the episode's Stage-A reason; later checks are not evaluated for ledger purposes, which preserves one-count-per-episode without a cross-stage priority list): PROTOCOL (A1), SEQUENCE (A2), NONCONF-PATH (A3), WASTE-UNDEFINED (A4), INVALID-RECORD (A5, T0 type), REPAIRED (A5, repaired type). (A5's two sub-reasons are distinguished in the ledger: INVALID-RECORD vs REPAIRED are separate codes, not merged.)
- **Stage B — Accounting validation (for Stage-A-eligible episodes only).** Compute, in order: (B1) inevitability step f (first step where slack becomes negative on the recorded path — REV-02 §4.2 definition retained); (B2) pre/at/post segments from f; (B3) slack_start, slack_after(f), and per-step waste sums by class/status (§6, I3); (B4) telescoping check: total_P3_waste(ep) = slack_start(ep) − slack_after(f). **Failure of any of B1–B4 ⇒ P3-INVALID** (see §5.2). In particular: no f found for a failed episode ⇒ P3-INVALID/NO-F (segments cannot be defined, so pre/at accounting cannot proceed — this is a validation failure, not a modelling choice about the episode); telescoping equality fails ⇒ P3-INVALID/TELESCOPE (classification, segment, or V error — to be investigated, never adjusted). Stage-B values for a P3-INVALID episode are shown descriptively in the excluded-episode ledger (§5.2) with the failure reason, never used in any P3 sum, sole/joint check, or P4 claim.
- **Stage C — Final membership.** P3-final = episodes passing Stage A **and** Stage B. Only P3-final episodes contribute to P2 denominators, trigger denominators, P3 waste ledgers, and P4 claims. The term "P3-eligible" without qualification is retired: reports must say "Stage-A-eligible" or "P3-final" as applicable. REV-04's "Level 2-P" and "P3-eligible" wordings for final membership are superseded by this stage language (see §8 audit).

### 5.2 Excluded-episode ledger with P3-INVALID (replaces REV-04 §4.3 ledger)

For each job in scope, the report must list: total failed episodes in scope; # P3-final episodes; and, for each non-final failed episode, its identifier and **exactly one** ledger reason, determined structurally: if the episode failed Stage A, its Stage-A reason (PROTOCOL / SEQUENCE / NONCONF-PATH / WASTE-UNDEFINED / INVALID-RECORD / REPAIRED, first failing check in A1→A5 order); else (Stage-A pass, Stage-B fail) its Stage-B reason (**P3-INVALID/TELESCOPE** or **P3-INVALID/NO-F**). No episode receives two reasons, and no episode is omitted: ledger identity (§6, I5) is #failed-in-scope = #P3-final + Σ Stage-A exclusions (by code) + #P3-INVALID (both sub-reasons summed, shown separately). Descriptive arithmetic waste for excluded episodes (V(next_recorded) − V(s) + 1 summed over recorded steps, where computable) may be shown in a clearly labelled **excluded-episode descriptive waste** line per episode — never added to P3 sums, never used in sole/joint checks, never presented as episode waste accounting. For P3-INVALID/TELESCOPE episodes, the descriptive line must show both sides of the failed equality (computed total_P3_waste vs slack_start − slack_after(f)) so the discrepancy is auditable; **waste values must never be adjusted to force the equality** (adjustment would conceal the classification/segment/V error the check exists to detect).

### 5.3 Transition conformance split — C-TRANS-PATH vs C-TRANS-LOG, and the blocked_log decision (binding decision)

REV-04 retained a single C-TRANS definition that included blocked_log, while REV-04 §4.2 called blocked_log a record field rather than a path field. That combination left a blocked-log-only discrepancy's P3 consequence undefined. The split below decides it explicitly. C-TARGET and C-TYPE definitions and consequences are retained unchanged (TYPE-FLAG, excluded from Level 2-T only).

- **C-TRANS-PATH (path conformance — Stage-A condition A3):** position_after matches T_spec(s, a_taken)'s position outcome; next t_pre matches T_spec's tick outcome (t_pre + 1, with crush/reset tick semantics per REV-01 clock rules retained); door_open_pre matches the true schedule at t_pre; and position_after is consistent with crush/movement outcomes (if crush_spec true under T_spec, position_after must be the start (0,0); if crush_spec false, position_after must equal target_spec (clipped target) or position_before for stay/blocked movement per T_spec movement rules). PATH concerns **what happened in the world** (positions, ticks, door states) as recorded.
- **C-TRANS-LOG (record-integrity conformance — NOT a Stage-A condition):** recorded blocked_log = blocked_spec (derived from position_before, action, door_open_pre under T_spec movement rules); recorded crushed flag = crush_spec; recorded reached flag = reached_spec. LOG concerns **whether the record's labels agree with the specified derivation** from path fields.
- **Decision (explicit, per work order item 5):** a **blocked-log-only discrepancy does NOT exclude the episode from P3.** More generally, a LOG-only failure (PATH passes, LOG fails on any of blocked_log / crushed flag / reached flag) leaves the episode Stage-A-eligible for waste purposes, with affected steps flagged **LOG-FLAG** (analogous to TYPE-FLAG), excluded from Level 2-T (transition-event claims), and counted in conformance reporting (§5.4) — but **not** counted as a P3 exclusion and **not** blocking P4. Rationale (stated, so the decision is auditable): blocked_spec is a deterministic function of (position_before, action, door_open_pre) — all three already PATH-checked — so a LOG-only failure adds no path information: it cannot indicate a path deviation that PATH missed, and it cannot change waste, which is computed from positions and reference values only. The same rationale holds for crushed/reached flags as labels (their position counterparts — reset-to-start, goal position — are PATH-checked).
- **Boundary (where LOG-FLAG ends and PROTOCOL begins):** LOG-FLAG applies only when episode structure is consistent with **positions**. If episode structure followed a wrong flag rather than positions, that is a Stage-A PROTOCOL failure (A1), not a LOG-FLAG: (i) episode terminated at a step where position_after ≠ goal but the reached flag said reached (termination followed the flag, not the position outcome); (ii) episode continued past a step where position_after = goal but the reached flag said not reached (continuation violated the position-reached termination rule). In both cases the episode's **structure** deviates from the position-based protocol, so A1 fails with reason PROTOCOL (not LOG-FLAG). The distinction is therefore: label wrong + structure right ⇒ LOG-FLAG (P3 retained); label wrong + structure following the wrong label ⇒ PROTOCOL (Stage-A exclusion). Reports must state which case applies for every LOG discrepancy that coincides with a termination/continuation boundary.
- **What P3 membership does and does not imply (binding):** P3-final membership implies waste computability (PATH + continuity + protocol-on-positions + computable waste + validation pass). It does **not** imply full conformance. Full conformance for Ex-DEV purposes requires PATH + LOG + TARGET + TYPE + CONT + PROTO all passing (see §5.4). An episode can therefore be P3-final yet non-conformant for Ex-DEV (LOG/TARGET/TYPE failures flagged). Conversely, an episode failing PATH/CONT/PROTO cannot be P3-final even if its labels are all self-consistent. The two gates must never be merged into a single "conformant" label.

### 5.4 P4 gate (restated with final membership) and Ex-DEV gate (separated)

- **P4 gate (job-level accounting-sufficient claims):** a job qualifies iff **all** of: (a) frequency combination rule prescribed before collection (Rule C / T / CT with form verbatim + threshold values, REV-04 §5.4 retained); (b) **every** failed episode in the job's stated scope is P3-final (zero Stage-A exclusions **and** zero P3-INVALID — either kind of exclusion blocks P4; per-episode P3-final results for such jobs remain reportable as per-episode results, labelled as such, never as job-level claims); (c) waste conditions (§6 I3 + REV-04 §5.3 sole/joint rules retained with assigned set {SEL, HEAD, K3-FULL} per §3.4) evaluated per episode over P3-final episodes only; (d) Shared pattern-only caveat (if applicable, REV-04 §5.4 condition 5 retained) and mechanism-status line (REV-04 §5 retained: INCONCLUSIVE (accounting only) unless intervention evidence listed). LOG-flagged P3-final episodes **do not** block P4 (LOG failures are not P3 exclusions per §5.3), but any P4 report must list LOG-flagged episodes and their counts alongside the claim (transparency requirement, not a gate). TYPE-flagged episodes likewise do not block P4.
- **Ex-DEV gate (separate, retained in substance from REV-02/REV-04):** Ex-DEV NOT_SUPPORTED for a job requires exact zero mismatches across **all** conformance checks (PATH + LOG + TARGET + TYPE + CONT + PROTO). A job with LOG-only failures therefore cannot claim Ex-DEV NOT_SUPPORTED, even if it is P4-eligible for waste claims. The two gates answer different questions (waste computability vs record conformance) and their results must be reported separately, never combined into one "conformant" verdict.

- **I1 — P1 pattern identity:**
  n_P1 = total_recorded − n_CRUSH-ND − n_UNREACH − n_TERMINAL-DEV − n_INVALID-RECORD.
  Equivalently: n_P1 = Σ classes + Σ status lines (INVALID-K + INVALID-FEAT-RECORD + FIELD-MISSING-PATTERN + K3-PARTIAL-INCONSISTENT). n_P1-classifiable = Σ classes only (status lines excluded, labelled whenever used). P1 is descriptive only (retained).
- **I2 — P2 contributor and trigger identities (per region, P3-final episodes only):**
  n_pre = Σ over classes of count_P_pre + Σ over status lines of count_S_pre (pre-segment steps of P3-final episodes; status-line pre steps in the denominator only, never in any class numerator; descriptive status-frequency lines reported separately).
  (OPT pre steps count in n_pre and in count_OPT_pre; their waste is 0 — frequency and waste ledgers are separate, and an OPT-heavy pre segment correctly shows high OPT frequency with zero OPT waste.)
  Trigger identity: #P3-final episodes = Σ over classes of (# episodes with f-outcome = class) + Σ over status lines of (# episodes with f-outcome = status) + n_trigger-unknown, where n_trigger-unknown is the residual. **Requirement: n_trigger-unknown = 0** for a valid P3 report (§4.4 rationale: every f-step in a P3-final episode has a tree outcome). Non-zero residual ⇒ trigger reporting invalid until investigated (classification gap, not a bucket).

Failure ⇒ the episode is not P3-final (P3-INVALID/TELESCOPE, §5.1) and its sums belong only to the excluded-episode descriptive ledger. P3-INVALID episodes' computed sums are **never** included in any I3 total (I3 covers P3-final episodes only).
- **I4 — Waste-undefined vs computed-zero separation (retained in substance from REV-04 §6 I4):**
  n_waste-undefined (by reason: MISSING-POSITION-AFTER, MISSING-REFERENCE, V-INFINITE/UNREACH, MISSING-POSITION-BEFORE) counts P0 steps whose waste cannot be computed. **Zero** waste-undefined steps are in any P3-final episode (Stage A4 forbids them). n_waste-undefined steps are assigned waste in **no** ledger (not 0, not unassigned, not descriptive-waste sums — they are counts only, with reasons). n_zero-computed counts P3-final steps whose waste is computed as 0 (OPT steps, crush steps). The two counts are distinct quantities and must never be merged, summed, or substituted: computed 0 is a value; undefined is an absence of value.
- **I5 — Per-population reconciliation (must be shown for every population a report uses):**
  For P1: total_recorded − n_CRUSH-ND − n_UNREACH − n_TERMINAL-DEV − n_INVALID-RECORD = n_P1 (same as I1, shown as a reconciliation).
  For failed-episode accounting (the P3/P4 reconciliation — **replaces REV-04's precedence-list reconciliation**): #failed-episodes-in-scope = #P3-final + #PROTOCOL + #SEQUENCE + #NONCONF-PATH + #WASTE-UNDEFINED + #INVALID-RECORD + #REPAIRED + #P3-INVALID/TELESCOPE + #P3-INVALID/NO-F.   For P2: (P3-final-episode pre steps) = n_pre, with P3-non-final-episode pre steps reconciled via the excluded-episode ledger (count of pre steps in excluded failed episodes, by episode ledger reason, shown separately — they are not in n_pre and not in any P2 numerator).

- **I6 — F/Q and job totals (retained in substance from REV-04 §6 I6, with P3-final scope):**

- Component outcomes are mutually exclusive and exhaustive over §3's domain (§3.2 matrix + §3.6 proof): every (est_full, completability, recorded-relation) combination yields exactly one outcome per component, including the previously unclassified combination (recorded = true, partial mismatch, est_full False, completable ⇒ INCONSISTENT-C). - Overlapping defects have one outcome everywhere (§4): the decision tree conditions on timing-criticality, so timing-critical K-defect + Q-defect ⇒ K-defect outcome (Q secondary) and non-timing-critical K-defect + Q-defect ⇒ SUBOPT-UNCLASS (K secondary), identically in P0/I0, P1, P2, trigger lines, and I0–I6. The flat I0 list that could not express this branch is retired.
- Episode accounting is complete and mutually exclusive (§5/§6 I5): Stage A (initial eligibility) → Stage B (validation, incl. telescoping and f-existence) → Stage C (final membership), with every failed episode in scope receiving exactly one ledger line (Stage-A code or P3-INVALID sub-reason) by construction, and P4 gated on final membership (zero Stage-A exclusions and zero P3-INVALID). Waste values are never adjusted to force an identity (Stage-B failures are reported descriptively with both sides of the failed equality shown).
- Waste computability and record conformance are separated (§5.3/§5.4): blocked-log-only (and crushed/reached-flag-only) discrepancies do not exclude an episode from P3 (LOG-FLAG, waste unaffected because blocked_spec is a deterministic function of already-PATH-checked fields), while still excluding the step from transition-event claims and blocking Ex-DEV full-conformance. P3-final membership therefore means waste computability, not full conformance — and the two gates are reported separately, never merged into one "conformant" verdict.
