**What this revision changes, in one paragraph:**
REVISION-05 resolved the previous defects substantially but left six formal gaps, all in edge cases where two rules meet. First, a current full-estimate status contradicting verified history could still reach §3 as K3-FULL or fall-through when the K flag was 1, because the only gate check for full-estimate status required K = 0. Second, the K-gate check for a genuinely absent open length required span cleanliness to be known, leaving the span-Unknown + open-length-absent + K = 1 combination unclassified even though a partial remaining value is impossible without open length. Third, the Unknown-path component rule claimed that matching the true schedule implies matching the partial expectation — an implication that fails for remaining (recorded open length need not equal true open length) and, by the same argument, for phase outside the first cycle (recorded opening need not equal true opening). Fourth, the F/Q identity called the Q-missing population "SUBOPT-UNCLASS" while also calling F/Q membership independent of tree outcomes, although a Q-missing step can be OPT, a K outcome, or a defect status under the tree. Fifth, Stage-A exclusion reasons were not fully deterministic: an episode violating both A5 conditions had no stated internal priority, and a missing field making a transition check unevaluable had no stated treatment against the NONCONF-PATH vs WASTE-UNDEFINED boundary. Sixth, the P2 denominator was stated two ways (all pre-segment steps in the flow table vs P1-line steps in the identity, with crush steps ambiguous between them), and the K3 counting identity was named as a class total while one of its terms is a status line. REVISION-06 corrects all six without redesigning the diagnostic: an estimate-state/provenance contradiction check with explicit precedence, applied regardless of K flag; a span-independent open-length gate check completing the necessary-condition coverage for K = 1 without full estimates; a corrected Unknown-path rule that separates value-correctness (the component outcome) from partial-path consistency (a separate attribute); F/Q redefined as an availability cross-tabulation independent of tree outcomes; Stage A renumbered as six ordered checks with an explicit unevaluable rule; and P2 denominators split into all-pre-steps vs P2-eligible-pre-steps with the K3 identity renamed to the K3-labelled-outcome identity.

## 2. Estimate-state/provenance contradiction and completed K-gate coverage (supersedes REV-05 §2.3 in part and §4.1 K-defect definition in part; deliverable: updated field/provenance contradiction checks and K-gate rules)

### 2.1 EST-PROV check — current full-estimate status vs verified history and vs required held values (new; outcome INVALID-EST-STATE)

**Fields involved:** R-EST-CUR (True/False/Unknown), R-EST-TUPLE (status VERIFIED/UNKNOWN; first_estimates_ordinal or NEVER), current step's job_step_ordinal, R-OPEN-LEN (integer / NONE-GENUINE / NOT-RECORDED), R-LAST-OPEN (integer / NONE-GENUINE / NOT-RECORDED). The check is evaluated **regardless of K flag**: it fires for R-K-FLAG = 0, R-K-FLAG = 1, and R-K-FLAG NOT-RECORDED alike, because it concerns the estimate-state record, not the K gate. (Outcome precedence when several defects co-occur is governed by §2.3; evaluation independence means the check is *computed* for every step with the cited fields recorded, even when another defect outcome ultimately wins.)

**Clause (a) — True vs verified history.** R-EST-CUR = True ∧ R-EST-TUPLE status = VERIFIED ∧ (tuple = NEVER ∨ first_estimates_ordinal > current job_step_ordinal) ⇒ **INVALID-EST-STATE**.
- Rationale: full estimates cannot be current before they first appear (ordinal comparison — first appearance at an ordinal means estimates become available at that step's post-observe state, so first_estimates_ordinal ≤ current ordinal is consistent, first_estimates_ordinal > current ordinal is not), and cannot be current if they never appear (VERIFIED NEVER). These are the contrapositives of REV-05 §2.1 inference rules (a)/(b) (retained): rule (a) says ordinal < first_ordinal + VERIFIED ⇒ False certain; rule (b) says VERIFIED NEVER ⇒ False certain for every step. A recorded True in either case contradicts the certain False.
- UNKNOWN tuple status never fires clause (a) (unknown history cannot contradict a state claim).
- R-EST-CUR = Unknown never fires (unknown state cannot contradict history).
- **False-side asymmetry (binding):** R-EST-CUR = False never fires EST-PROV for any tuple. Estimates are losable after first appearance (contradiction handling clears estimates and re-estimation restarts — carried from REV-04 §2.1): False after first appearance is possible (loss), False before first appearance is required (rule (a)), False with NEVER is required (rule (b)). There is therefore no False-side contradiction to define; a future rule claiming one must first refute the estimates-losable property with code evidence.

**Clause (b) — True vs genuinely absent required held values.** R-EST-CUR = True ∧ (R-OPEN-LEN = NONE-GENUINE ∨ R-LAST-OPEN = NONE-GENUINE) ⇒ **INVALID-EST-STATE**.
- Rationale: full estimates require period, open_len, and last_opening all non-None (carried-forward _has_estimates). Genuine absence (NONE-GENUINE, recorded — not Unknown, not NOT-RECORDED) of open_len or last_opening therefore contradicts a True full-estimate state on its own, regardless of tuple status (even UNKNOWN tuple: the held-value contradiction does not need history).
- NOT-RECORDED / Unknown held values never fire clause (b) (missing provenance ≠ contradiction — the distinction preserved from REV-05 §2.3).
- **Period limitation (stated, not hidden):** full estimates also require period, but no R-PERIOD field is defined in REV-05/REV-06 field sets, so a genuinely absent period cannot be checked by EST-PROV as defined here. Period-absence contradictions are therefore **undetectable** under the current field set and must be labelled UNKNOWN (not assumed present, not assumed absent) for any step whose period is not recorded. A future collection that wants period-contradiction coverage must define R-PERIOD (see §8, OQ-4); until then, clause (b) covers the two checkable held values only, and its incompleteness for period is explicit.

**Outcome and routing (binding):** INVALID-EST-STATE is a **status line** (descriptive record-defect outcome, same family as INVALID-K / INVALID-FEAT-RECORD / FIELD-MISSING-PATTERN / K3-PARTIAL-INCONSISTENT in REV-05 §6 vocabulary): counted in I0/I1 as a status line, unassigned waste sub-bucket in P3-final episodes where the step's outcome is INVALID-EST-STATE (timing-critical defect outcomes only — see §2.3 routing), descriptive frequency/trigger lines only, never in any assigned sum, set, or threshold.
- **Strict non-classification rule (per work-order item 1):** no step with an EST-PROV contradiction may receive a K3 outcome (K3-FULL / K3-UNRESOLVED / K3-PARTIAL-INCONSISTENT) or a K-fall-through outcome in any tree branch. Timing-critical suboptimal steps receive INVALID-EST-STATE as their outcome (unless a higher-precedence defect outcome wins per §2.3, in which case INVALID-EST-STATE is a secondary attribute and the step still receives no K3/fall-through outcome). Non-timing-critical steps receive their HEAD/SEL/SUBOPT-UNCLASS outcome with INVALID-EST-STATE as a secondary attribute — and such steps must never be described as "K fall-through": K classification was not attempted for them (tree T3d), so there is no K outcome to fall through from. OPT steps receive OPT with INVALID-EST-STATE as a secondary attribute (OPT determination does not use estimate state). Availability assignment (KB/KN/KU/KX1) never occurs for EST-PROV steps: defect routing precedes availability assignment, so a K_rec = 0 step with contradictory estimate state is a defect outcome/attribute, not an availability state.

### 2.2 KX2d-open — open-length necessary condition, span-independent (new; subsumes REV-05 KX2d narrow row)

**Check:** R-EST-CUR = False ∧ R-OPEN-LEN = NONE-GENUINE ∧ R-K-FLAG = 1 ⇒ **INVALID-K**, regardless of R-LAST-OPEN value (integer / NONE-GENUINE / NOT-RECORDED) and regardless of R-SPAN-CLEAN value (True / False / Unknown / NOT-RECORDED).
- Rationale: K = 1 requires remaining available. Remaining availability requires (full estimates) OR (clean opening + clean span + open_len). With est_full = False, the first disjunct fails; with open_len genuinely absent, the second disjunct fails (open_len is a necessary condition for partial remaining) — irrespective of opening and span, whose values cannot rescue a missing necessary condition. The genuinely missing span affects partial **comparisons** (§3: the remaining comparison is then uncompletable or absent), but it does not affect this gate conclusion, which depends only on the open_len condition. This is the correction to REV-05's gap: span Unknown no longer leaves the combination unclassified.
- Missing-provenance distinction preserved: R-OPEN-LEN = NOT-RECORDED or Unknown never fires KX2d-open (absence of evidence about open_len is not evidence of its absence). Only a recorded NONE-GENUINE value fires.
- REV-05 KX2d (all-conditions form: est False + opening integer + span True + open_len NONE + K = 1) is **subsumed**: every case it covered is covered by KX2d-open with the same INVALID-K outcome; the narrower row is retired as a separate rule (see §7 audit) and must not be cited as an additional condition. REV-05 KX2d-span (est False + span False + K = 1) is retained as a separate row (phase-necessary condition, see lemma below) — it is not subsumed by KX2d-open (span False contradicts K = 1 via phase, not via remaining).

**Necessary-condition completeness lemma (for est_full = False + K = 1; specification-level, not empirical):** remaining availability requires open_len (KX2d-open); phase availability requires an opening (KX2c: opening NONE-GENUINE + est False + K = 1 ⇒ INVALID-K, retained) and a clean span (KX2d-span: span False + est False + K = 1 ⇒ INVALID-K, retained); either feature's recorded unavailability contradicts K = 1 (KX2b OR-form: either -AVAIL recorded False + K = 1 ⇒ INVALID-K, retained). Therefore every K = 1 contradiction that follows from a **genuinely absent** (recorded NONE-GENUINE / recorded False) necessary condition under est_full = False is caught by {KX2b, KX2c, KX2d-span, KX2d-open}. Unknown/NOT-RECORDED conditions catch nothing (by design — missing provenance is not contradiction). Full-estimate (est_full = True) K = 1 contradictions from genuine absences are caught by EST-PROV clause (b) (open_len/last_opening NONE + True ⇒ INVALID-EST-STATE, which outranks gate outcomes per §2.3) and by KX2a (True + K = 0 ⇒ INVALID-K, retained, as secondary where EST-PROV also fires). Period-absence contradictions under est_full = True remain undetectable (no R-PERIOD field — §2.1 limitation, OQ-4). The lemma's scope is exactly this: it claims completeness over checkable genuine-absence conditions, not over unrecorded fields.

### 2.3 K-defect definition (extended) and defect-outcome precedence (new; supersedes REV-05 §4.1 K-defect paragraph in part)

**K-defect (extended definition, binding):** a step has a K-defect iff any of: (a) K fields missing (any of R-K-FLAG / R-SLOT-PHASE / R-SLOT-REM absent); (b) estimate-state/provenance contradiction (EST-PROV, §2.1); (c) gate contradiction (KX2a–KX2e, REV-05 §2.3 retained, plus KX2d-open, §2.2); (d) feat/slot contradiction (KX2f, REV-05 §2.3 retained). (REV-05's K-defect definition covered (a), (c), (d); (b) is new.)

**Defect-outcome precedence (timing-critical suboptimal steps only; REV-05's tree had no inter-defect precedence — this rule supplies it):** when several defects co-occur on a timing-critical suboptimal step, the step's single outcome is determined by the first applicable rule in this order, and every non-winning defect is recorded as a secondary attribute (shown, never a second summand):
- **D1 — Presence:** K fields missing ⇒ **FIELD-MISSING-PATTERN**. (Presence is checked first because gate/estimate consistency conclusions about K data are moot without K data — except EST-PROV evaluation, which needs no K fields and is still computed; if EST-PROV also fires, it is recorded as a secondary attribute alongside FIELD-MISSING-PATTERN, not as a second outcome.)
- **D2 — Branch coherence:** EST-PROV contradiction ⇒ **INVALID-EST-STATE**. (Estimate-state coherence governs whether §3 branching is even defined, so it outranks gate conclusions that assume an estimate state. Example: True + K = 0 + VERIFIED NEVER fires both EST-PROV (D2) and KX2a (D3) — outcome INVALID-EST-STATE, INVALID-K secondary. Example: True + K = 1 + avail-REM False + before-first-ordinal fires both EST-PROV (D2) and KX2b (D3) — outcome INVALID-EST-STATE, INVALID-K secondary.)
- **D3 — Gate coherence:** any KX2a–KX2e or KX2d-open contradiction ⇒ **INVALID-K**. (Multiple gate contradictions on one step yield one INVALID-K outcome; the firing rows are all recorded as attributes of that outcome.)
- **D4 — Internal identity:** any KX2f contradiction ⇒ **INVALID-FEAT-RECORD**.
- If no defect fires, the tree proceeds to §3 outcomes (T3b) or fall-through (T3c) as in REV-05 §4.2 (retained).
- **Non-timing-critical steps and OPT steps:** defect precedence does not apply (no defect outcome is assigned): all firing defects are secondary attributes only, and the outcome is determined by T2 (OPT) or T3d (HEAD/SEL/SUBOPT-UNCLASS by Q-defect) as in REV-05 §4.2 (retained). This preserves the tree's proportionality principle: a defect blocks only the classification it affects (K classification for timing-critical steps), never an outcome determined without K data.
- **Justification for the order (stated so it can be challenged):** presence (D1) before coherence (D2–D4) because absent data cannot be checked for consistency; branch coherence (D2) before gate coherence (D3) because gate checks interpret the estimate state (KX2a uses True; KX2c/d use False) and cannot be trusted when the state itself is impossible; gate coherence (D3) before internal identity (D4) because the gate is the encoder's own K rule (K = 1 iff both available), while feat/slot identity is a record-internal check that presupposes a coherent gate state. A different order would still be deterministic if stated, but it would assign different single outcomes to multi-defect steps — so the order above is part of the specification, not an implementation choice, and reports must state it when multi-defect steps occur.

**I0/I1 consequence (stated for §6 accounting):** INVALID-EST-STATE joins the status lines in I0/I1 (see §6.3 terminology update): I0 summands now include n_INVALID-EST-STATE as a status line alongside INVALID-K, INVALID-FEAT-RECORD, FIELD-MISSING-PATTERN, and K3-PARTIAL-INCONSISTENT. Waste for INVALID-EST-STATE steps in P3-final episodes (timing-critical defect outcomes only) is unassigned (own sub-bucket); non-timing-critical/OPT INVALID-EST-STATE attributes do not create a waste bucket entry beyond the step's HEAD/SEL/OPT waste (same rule as REV-05 §3.5 notes for INVALID-K attributes, extended to EST-PROV).

## 3. Corrected Unknown-path component rule — value-correctness separated from partial-path consistency (supersedes REV-05 §3.2 Unknown rows' rationale and §3.5 rows KU2/KU3 notes in part; deliverable: revised component matrix, decision table, and proof)

### 3.1 Retraction and replacement rationale (binding)

**Retracted (REV-05 §3.2 Unknown-row rationale, quoted for audit purposes only):** "if the path was partial, recorded = true implies elapsed = true phase (first cycle), hence recorded = partial_exp as well." This implication is invalid as a general claim, for two independent reasons:
- **Remaining:** partial_remaining_exp is computed from the **recorded** open_len, while true_remaining is computed from the **true** schedule's open length. Recorded open_len need not equal true open_len (a wrong open_len estimate is exactly the kind of error full/partial estimation can produce), so recorded_remaining = true_remaining does **not** imply recorded_remaining = partial_remaining_exp. Example (illustrative numbers, not data): true open_len 10, recorded open_len 12, door open, elapsed 5 → true_remaining 5, partial_remaining_exp from recorded open_len 7; a recorded value of 5 equals true but differs from partial expectation.
- **Phase outside the first cycle:** partial_phase_exp is computed from the **recorded** opening (elapsed = t_pre − recorded opening), while true_phase is computed from the **true** opening modulo period. Outside the first cycle (elapsed ≥ 20), recorded_phase = true_phase does **not** imply recorded_phase = partial_phase_exp (elapsed, unwrapped). The REV-05 rationale's "first cycle" parenthetical assumed elapsed < 20 without stating it as a condition, so the implication failed whenever elapsed ≥ 20 or recorded opening ≠ true opening.
**Replacement rationale (binding):** under est_full = Unknown, the component outcome answers exactly one question — **value-correctness**: does the recorded value equal the true schedule value? If yes, the value the network received is the true value, so it cannot mislead the network via schedule error on either path (full path with correct estimates, or partial path whose output happens to equal true) — hence MATCH-TRUE (no error via this component). If no, full-estimation error and partial-path inconsistency cannot be distinguished without knowing the path — hence UNRESOLVED-C. The outcome asserts **nothing** about partial-path consistency, which is recorded separately via the P- attribute (§3.2). A reader who cites MATCH-TRUE as evidence that "the partial path was verified" or "partial expectations were satisfied" misapplies REV-06.

### 3.2 Revised Unknown-branch matrix rows and P- attribute (the outcome is unchanged in label; what it claims changes, and the attribute is new)

For each component c ∈ {phase, remaining} with est_full_cur = Unknown (all other matrix rows — est_full True/False — are retained unchanged from REV-05 §3.2):

| est_full_cur | Recorded relation to true_c | Component outcome (Q1: value-correctness) | P- attribute (Q2: partial-path consistency; recorded for every Unknown-branch component where partial_exp_c is defined or definable) |
| --- | --- | --- | --- |
| Unknown | recorded_c = true_c | **MATCH-TRUE** — value correct; no schedule error via this component on either path. Asserts nothing about partial consistency (see §3.1). | If partial_exp_c is **computable** (phase: R-LAST-OPEN integer ∧ R-SPAN-CLEAN True; remaining: phase completable ∧ R-OPEN-LEN integer): recorded_c = partial_exp_c ⇒ **P-CONSISTENT** (value consistent with the partial path as well — note: this does not prove the path *was* partial, only that the value is consistent with it); recorded_c ≠ partial_exp_c ⇒ **P-INCONSISTENT-IF-PARTIAL** (inconsistency conditional on the partial path — asserted as a conditional only: if the path was partial, the value conflicts with its own rules; if the path was full, no inconsistency arises; since the path is unknown, neither the inconsistency nor its absence may be asserted unconditionally). **Rules governing the P- attribute (binding):**
- The P- attribute is defined **only** for Unknown-branch components. For est_full = True components, P- attribute = **P-NOT-APPLICABLE** (full path governs; partial expectations are not applicable — consistency with a path the model did not take is not a question the diagnostic asks). For est_full = False components, P- attribute = **P-NOT-APPLICABLE** as a separate field (consistency is already encoded in the outcome itself: MATCH = consistent, INCONSISTENT-C = inconsistent, MATCH-TRUE/UNRESOLVED-C = true-comparison outcomes where partial consistency is unestablished by incompletability — duplicating it as an attribute would double-report the same finding). The attribute therefore adds information exactly where the outcome is silent (Unknown branch), and nowhere else.
- The P- attribute **never changes** the component outcome, the step outcome, any waste bucket, any frequency numerator, or any trigger line. It is cross-tabulated descriptively (counts of P-CONSISTENT / P-INCONSISTENT-IF-PARTIAL / P-UNKNOWN / P-NOT-APPLICABLE components, per component, per job, shown alongside Unknown-branch outcome counts). A step's outcome with a P-INCONSISTENT-IF-PARTIAL attribute is still MATCH-TRUE (if value-correct) or UNRESOLVED-C (if value-incorrect) — the attribute is a flag for readers and for future verification (e.g. if path provenance is later established, P-INCONSISTENT-IF-PARTIAL components are the candidates for reclassification), not a reclassification.
- **Step combination under Unknown (unchanged in outcome logic, clarified in wording):** step outcome follows REV-05 §3.3 steps 2–5 with Unknown-branch component outcomes as above (any UNRESOLVED-C ⇒ K3-UNRESOLVED unless an INCONSISTENT-C also present — which cannot occur under Unknown per REV-05 §3.2, since INCONSISTENT-C requires a known partial path; any FULL-MISMATCH cannot occur under Unknown for the same reason; all MATCH-TRUE ⇒ fall-through with P- attributes recorded). The proof addendum (§3.3) states outcome uniqueness is preserved because the attribute is orthogonal: outcome is a function of (recorded vs true) under Unknown; attribute is a function of (recorded vs partial_exp, computability) under Unknown; neither function constrains the other, and no step receives two outcomes because it carries an attribute.

### 3.3 Proof addendum (Unknown branch; supplements REV-05 §3.6 proof, which is otherwise retained)

**Claim:** under est_full = Unknown, each component receives exactly one outcome (MATCH-TRUE or UNRESOLVED-C) and exactly one P- attribute value, with no conflation between them.
**Argument:** recorded_c = true_c and recorded_c ≠ true_c are mutually exclusive and exhaustive (equality over integers) — hence exactly one outcome. Independently, partial_exp_c is either computable or incompletable (by the §3.2 completability conditions, which are decidable from recorded provenance fields — integer/True vs missing/Unknown/absent are disjoint field states), and if computable, recorded_c = partial_exp_c or ≠ partial_exp_c (equality, exhaustive) — hence exactly one attribute value among {P-CONSISTENT, P-INCONSISTENT-IF-PARTIAL, P-UNKNOWN} (P-NOT-APPLICABLE does not occur in the Unknown branch). Outcome and attribute are functions of different comparisons (true vs partial), so their joint assignment is a pair (outcome, attribute) with no outcome ambiguity: MATCH-TRUE pairs with any of the three attribute values; UNRESOLVED-C pairs with any of the three. The REV-05 error was to treat one pair (MATCH-TRUE, P-CONSISTENT) as the only possible pairing for true-matching values — i.e. to collapse the pair into the outcome alone. REV-06 restores the pair. ∎
**Table updates (REV-05 §3.5 rows KU2/KU3, restated with attributes):** row KU2 (Unknown + any UNRESOLVED-C ⇒ K3-UNRESOLVED, unassigned) now carries "P- attributes per component (§3.2) shown alongside; P-INCONSISTENT-IF-PARTIAL does not change the outcome." Row KU3 (Unknown + both MATCH-TRUE ⇒ fall-through) now carries "P- attributes per component shown alongside; a P-INCONSISTENT-IF-PARTIAL attribute on a fall-through step is a conditional-consistency flag only (path unknown), never evidence of inconsistency and never a reason to withhold fall-through (value-correctness governs the outcome)." Row KF1/KF2 tuple condition is tightened per §2.1/§3.4 below (not part of the Unknown correction, but stated here for table completeness).

### 3.4 KF1/KF2 tuple condition (tightened per R6-01; stated here so the K3 table is complete in one place)

REV-05 §3.5 rows KF1 (K3-FULL) and KF2 (fall-through, est_full True) permitted "any tuple except VERIFIED NEVER". The permitted tuple set is now: **UNKNOWN-status tuple, or VERIFIED tuple with first_estimates_ordinal ≤ current job_step_ordinal**. VERIFIED NEVER and VERIFIED tuple with first_estimates_ordinal > current ordinal are **excluded** — such steps are INVALID-EST-STATE via EST-PROV (§2.1), routed by the tree before §3, and must never appear as KF1/KF2 rows in a report. ## 4. F/Q accounting repaired — cross-tabulation independent of tree outcomes (supersedes REV-05 §6 I6 in full; deliverable: corrected F/Q identities)

### 4.1 Definitions (binding; "Q-missing population (SUBOPT-UNCLASS)" wording is retired)

- **Q-availability (per step, independent of tree outcome):** a step is **Q-present** iff selector Q present ∧ every head Q present ∧ taken act present (all three needed for the SEL/HEAD split — REV-05 §4.1 Q-defect definition, retained, now used as the availability predicate). A step is **Q-missing** iff any of the three is absent (i.e. iff the step has a Q-defect in REV-05 §4.1 terms).
- **F-population** = set of Q-present steps. **Q-population** = set of Q-missing steps. Every recorded step belongs to exactly one of F/Q by availability, regardless of its tree outcome (OPT, K class, status line, state line, INVALID-RECORD — all cross-tabulated). F/Q membership is an availability dimension, not a classification: it answers "could the SEL/HEAD split be determined for this step?" (F: yes; Q: no), not "what is this step's outcome?"
- **SUBOPT-UNCLASS is a tree outcome, not a population.** It arises only via REV-05 §4.2 tree branches T3c (timing-critical fall-through + Q-defect) and T3d (non-timing-critical + Q-defect) — both of which require a Q-defect by construction. Hence **SUBOPT-UNCLASS ⊆ Q-population** (every SUBOPT-UNCLASS step is Q-missing), stated as the inequality **n_SUBOPT-UNCLASS ≤ n_Q**, with equality only in the degenerate case where no non-SUBOPT-UNCLASS outcome has any Q-missing member (not expected in any real collection, and a report claiming equality must show the cross-tabulation proving it). The converse is false: Q-missing steps also occur as OPT (T2, needs neither field), K outcomes (T3b, needs K not Q), defect outcomes (T3a), and state/INVALID outcomes (T0/T1) — all counted in n_Q but not in n_SUBOPT-UNCLASS. Any sentence of the form "the Q-missing steps (SUBOPT-UNCLASS)" or "Q-missing population = SUBOPT-UNCLASS count" misapplies REV-06 and must be corrected to the cross-tabulation below.

### 4.2 Cross-tabulation and identities (replace REV-05 §6 I6 combined-total wording)

For each I0 outcome O (classes: OPT, K3-FULL, K3-UNRESOLVED, KBLANK, KNEVER, KUNK, K-STATUS-UNKNOWN, HEAD, SEL, SUBOPT-UNCLASS; status lines: INVALID-K, INVALID-FEAT-RECORD, FIELD-MISSING-PATTERN, K3-PARTIAL-INCONSISTENT, INVALID-EST-STATE (§2.1, new); state/INVALID lines: TERMINAL-DEV, UNREACH, CRUSH-ND, INVALID-RECORD), define n_O,F = steps with outcome O and Q-present, n_O,Q = steps with outcome O and Q-missing. Then:
- Per outcome: **n_O = n_O,F + n_O,Q** (every step with outcome O is F or Q by availability — exhaustive, disjoint).
- Population totals: **n_F = Σ_O n_O,F**; **n_Q = Σ_O n_O,Q**; **total_recorded = n_F + n_Q** (the F/Q reconciliation — this is the identity REV-05 §6 I6 attempted with its combined-total wording; the corrected form is a cross-tabulation sum, not two separate I0 partitions: F and Q do **not** each satisfy I0 independently as partitions, because I0's summands are tree outcomes and F/Q splits each summand. A report must show the cross-tabulation table (rows = outcomes, columns = F/Q/total) or, at minimum, n_F, n_Q, and the F/Q split for SUBOPT-UNCLASS and for each K outcome it cites.)
- **Check quantities (must hold in any valid report; violations indicate classification errors, investigated as such):** n_HEAD,Q = 0 and n_SEL,Q = 0 (HEAD/SEL require Q present by construction — a Q-missing HEAD/SEL row is impossible under the tree and indicates a reporting error). n_SUBOPT-UNCLASS,F = 0 (SUBOPT-UNCLASS requires Q-defect by construction — an F-column SUBOPT-UNCLASS count is impossible). These zeros are consequences of the tree definitions, not additional assumptions; a report showing non-zero values for them is invalid until corrected.
- **Relationship to the tree (clarified, not changed):** the tree already handles Q-defect routing per step (T3c/T3d fall-through to SUBOPT-UNCLASS; T3b K outcomes independent of Q; T2 OPT independent of Q). F/Q as defined here does not replace tree routing and does not create a second partition: it is the reporting/reconciliation dimension that makes Q-availability auditable across outcomes. The REV-02-era "Population F / Population Q" eligibility language (full-Q steps eligible for HEAD/SEL; Q-missing steps routed to SUBOPT-UNCLASS at fall-through) is subsumed by the tree's Q-defect handling — cite the tree for routing, cite this section for F/Q totals, never cite F/Q membership as a routing rule on its own.

## 5. Deterministic Stage-A exclusion rules (supersedes REV-05 §5.1 Stage-A conditions A1–A5 and §5.2 ledger reason list in part; deliverable: deterministic Stage-A rules and updated I5 reconciliation)

### 5.1 Six ordered Stage-A checks (renumbered; REV-05's combined A5 is split, and waste/invalid order is fixed)

Stage A (initial eligibility, for failed episodes) is evaluated as six checks in this exact order. The episode's single exclusion reason is the first check that fails. Checks are evaluated over the episode's steps as stated; a check that cannot be evaluated for a step is UNEVALUABLE for that step (§5.2), never FAIL.

- **A1 — PROTOCOL (C-PROTO):** episode/job protocol holds (length ≤ 200; ends after a reached step per positions or at exactly 200 steps; does not continue after a reached step per positions; start_phase S ∈ 0..19; episodes in stated order with stated start_phases). Protocol is judged on **positions** (reached per position_after = goal), not on reached flags (REV-05 §5.3 boundary retained: flag-following-structure ⇒ PROTOCOL, see §5.2 note).
- **A2 — SEQUENCE (C-CONT):** continuity holds for the whole episode (position_before(0) = (0,0); position_before(s) = position_after(s−1) for s > 0; t_pre(0) = S; t_pre(s) = t_pre(s−1) + 1).
- **A3 — TRANS-PATH (C-TRANS-PATH):** every **evaluable** step passes C-TRANS-PATH (REV-05 §5.3 definition retained: position_after, next t_pre, door_open_pre, and position_after's consistency with crush/movement outcomes under T_spec). Steps lacking a field needed for the check are UNEVALUABLE at A3 (§5.2), not failures.
- **A4 — INVALID-RECORD (T0):** no step has a T0 INVALID-RECORD outcome (missing position_before / missing action / missing t_pre / contradictory phase — REV-05 §4.2 T0, retained). (A4 precedes A5 deliberately: invalidity is more fundamental than computability — a step whose record is invalid should not reach waste computation, and an episode containing one is excluded on invalidity grounds even if its waste is also uncomputable for other steps. See §5.2 for the worked consequences.)
- **A5 — WASTE-UNDEFINED (computable waste):** every step has position_before present, position_after present, t_pre present (for phase), and reference V finite/computable for its (position, phase) state. (Missing position_after, missing position_before (if not already caught at A4 — note A4 precedes A5, so a missing-position_before episode is already excluded at A4; A5's missing-position_before case therefore arises only in the formal check definition, not as a distinct episode reason — see §5.2), missing t_pre (if not already caught at A4, same note), missing reference, or V = ∞ fails A5. Note: UNREACH steps (V = ∞) fail A5 — consistent with REV-05 Stage-A condition A4 in substance, renumbered.)
- **A6 — REPAIRED:** no REPAIRED step in the episode. (Provenance status, checked last deliberately: repair status is about how the data was produced, not about the data's current validity or computability, so it yields to demonstrated deviations (A1–A3), invalidity (A4), and incomputability (A5) when several apply. An episode failing only A6 is excluded on provenance grounds alone — the weakest exclusion ground, stated as such so its reason is never mistaken for a data defect.)
- **Order justification (stated so it can be challenged):** demonstrated deviations first (A1–A3: protocol, sequence, path mismatch — each is positive evidence of non-conformance among evaluable steps), then invalidity (A4: data untrustworthy), then incomputability (A5: data insufficient for waste), then provenance (A6: data repaired). Any other total order would also be deterministic if stated, but would assign different single reasons to multi-failure episodes — so this order is part of the specification, and reports must cite it when multi-failure episodes occur. Stage-B/C definitions (REV-05 §5.1, retained) are unchanged: Stage B (validation) is evaluated only for Stage-A passes; Stage C (final membership) = Stage-A pass ∧ Stage-B pass.

### 5.2 Unevaluable rule and the NONCONF-PATH vs WASTE-UNDEFINED boundary (binding)

**Check-evaluation statuses:** every Stage-A check, applied to a step (or boundary/pair where applicable), returns PASS, FAIL, or UNEVALUABLE. UNEVALUABLE means: a field needed for that check is missing for that step (or boundary/pair). **UNEVALUABLE is never FAIL.** A check fails for an episode iff at least one evaluable application returns FAIL. An episode with no FAIL among evaluable applications but at least one UNEVALUABLE application does **not** fail that check — it proceeds to later checks, where the missing field's consequence is determined by the check that actually needs it:
- **TRANS-PATH unevaluability (the owner's case):** C-TRANS-PATH needs position_before, position_after, action, t_pre, door_open_pre. If position_after is missing for a step, that step's TRANS-PATH check is UNEVALUABLE at A3 (no mismatch demonstrated — a missing field cannot demonstrate a mismatch). The episode therefore does **not** fail A3 on that step. It then reaches A4 (no T0 step on that ground alone — missing position_after is not a T0 field) and A5, where missing position_after fails waste computability ⇒ **WASTE-UNDEFINED**. Hence: missing position_after + no demonstrated mismatch ⇒ WASTE-UNDEFINED, never NONCONF-PATH. (This resolves the owner's boundary question in favour of missing-data-as-undefined rather than missing-data-as-nonconformant, for the reason stated: nonconformance requires a demonstrated deviation from T_spec, and a deviation cannot be demonstrated without the field that would show it.)
- **Demonstrated mismatch beats missingness elsewhere:** if one step has an evaluable TRANS-PATH mismatch (FAIL at A3) and another step has missing position_after (UNEVALUABLE at A3), the episode fails at A3 with **NONCONF-PATH** (check order: A3's FAIL is determined before A5 is reached). Missingness does not shield a demonstrated mismatch, and a demonstrated mismatch does not convert missingness elsewhere into nonconformance — each step contributes its own evaluation status, and the episode reason follows check order.
- **Protocol/sequence unevaluability:** A1 boundaries needing position_after (reached checks) and A2 pairs needing position_before/position_after are UNEVALUABLE when those fields are missing, by the same rule (never FAIL). Such unevaluability defers to A4/A5 as above (missing position_before/action/t_pre ⇒ A4 INVALID-RECORD via T0; missing position_after ⇒ A5 WASTE-UNDEFINED). Exception (retained from REV-05 §5.3 boundary): if episode **structure** followed a wrong reached flag rather than positions (terminated early on flag-reached with position ≠ goal, or continued past position-goal on flag-not-reached), that is an evaluable PROTOCOL failure at A1 (structure is observed, not missing) — not unevaluability, not LOG-FLAG.
- **T0-field missingness vs waste computability (why A4 precedes A5):** missing position_before, missing action, and missing t_pre are T0 INVALID-RECORD fields. A step missing position_before is also waste-incomputable (V(state) needs position_before), and a step missing t_pre is also waste-incomputable (phase needs t_pre) — but under check order A4 precedes A5, so such episodes receive **INVALID-RECORD**, not WASTE-UNDEFINED. This is deliberate: invalidity (data untrustworthy) dominates incomputability (data insufficient) in the reason hierarchy. Missing action is T0-invalid but does **not** block waste computation (waste uses positions/reference, not action) — such episodes receive INVALID-RECORD at A4 with A5 passing, which is why A4 is non-vacuous even though some T0 fields also block waste. Reports must not reassign A4 episodes to WASTE-UNDEFINED on the grounds that their waste is also uncomputable — the reason follows check order, not "also-true" properties.

### 6.1 P2 denominator — n_pre-all vs n_pre (and post-segment pair)

**Definitions (binding):** for P3-final episodes, let pre segments be defined from f as in REV-02 §4.2 (retained: pre = steps s < f; at = step f; post = steps s > f).
- **n_pre-all** = count of **all** pre-segment steps of P3-final episodes (every pre step, whatever its tree outcome, including CRUSH-ND pre steps).
- **n_pre** (P2 denominator, retained as the denominator symbol) = count of **P2-eligible** pre-segment steps = pre steps with a P1 line (class or status line, REV-05 §4.4 — classes + status lines including INVALID-EST-STATE, §2.1, now one of the status lines). Equivalently: **n_pre = n_pre-all − count_CRUSH-ND_pre**, where count_CRUSH-ND_pre = CRUSH-ND steps in pre segments of P3-final episodes.
- **Why only CRUSH-ND differs:** TERMINAL-DEV steps cannot occur in failed episodes (failed = goal never reached, so no step starts at the goal); UNREACH steps fail Stage A5 (V = ∞ ⇒ waste uncomputable), so no UNREACH step occurs in a P3-final episode; INVALID-RECORD steps fail Stage A4, so none occur in P3-final episodes. CRUSH-ND steps are therefore the **sole** P1-excluded step type that can occur in P3-final episodes (crush steps are legitimate steps with computed-zero waste — REV-05 §6 I4, retained). The identity n_pre = n_pre-all − count_CRUSH-ND_pre is exact for P3-final episodes (not an approximation, not a bound).
- **Reporting requirement:** every report using P2 quantities must show **both** n_pre-all and n_pre, plus count_CRUSH-ND_pre, so the exclusion is auditable (a report showing only n_pre without n_pre-all, or only n_pre-all without the CRUSH-ND count, is incomplete for P2 purposes). Contributor frequencies are computed over n_pre (P2-eligible steps only) — contrib_freq(P) = count_P_pre / n_pre for classes P; status-line pre counts are shown as descriptive frequencies over n_pre (denominator-only, never class numerators — REV-05 §4.4, retained).
