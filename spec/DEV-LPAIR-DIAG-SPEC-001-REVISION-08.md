## 2. P- attribute domain — restricted to the comparison matrix (R8-01)

### 2.1 Definition (governing)

**The P- attribute is defined if and only if the §3 comparison matrix assigns the component a component outcome.** The five values are P-CONSISTENT, P-INCONSISTENT, P-INCONSISTENT-IF-PARTIAL, P-UNKNOWN, and P-NOT-APPLICABLE, with the meanings given in REV-07 §3.1 (retained unchanged for domain components). A component with no component outcome has no P- attribute. In tables, its attribute cell is shown as "—" (em dash). The em dash is an absence marker, not a sixth P- value: it is never counted in P- attribute counts, never averaged, never treated as a consistency finding, and never cited as evidence for or against partial-path consistency.

**When does a component enter the matrix?** A component enters the §3 matrix if and only if the step reaches §3 comparison for that component under the decision tree (REV-05 §4 as amended by REV-06 §2.3 defect precedence D1–D4, retained). In particular:

- (a) **K_rec = 1 and no earlier tree exit.** The step passes T0 (as split in §4 below), passes OPT routing, and is not routed to a winning defect outcome (FIELD-MISSING-PATTERN, INVALID-EST-STATE, INVALID-K, INVALID-FEAT-RECORD) before §3. Both components (phase, remaining) then receive component outcomes under §3, and both receive P- attributes under §2.2.
- (b) **K_rec = 0.** The step is classified as an availability state (KBLANK, KNEVER, KUNK, K-STATUS-UNKNOWN, or a phase-only sub-state). No component outcome is assigned, because there is no recorded feature pair to compare in the matrix sense (blanked slots are 0.0 by the blanking rule and must never be compared as estimates, per REV-04 §2.2, retained). Neither component receives a P- attribute, regardless of `est_full_cur`. This holds for `est_full_cur = True` (where K_rec = 0 is itself a K-gate defect, KX2a, and the step outcome is INVALID-K, not a component outcome) and for `est_full_cur = False` (availability states) alike.
- (c) **Earlier tree exit.** A step routed to FIELD-MISSING-PATTERN (T0 presence failure or missing feature field, including missing recorded phase under §4), to a winning defect outcome (INVALID-EST-STATE, INVALID-K, INVALID-FEAT-RECORD under D1–D4), or to OPT before §3, receives no component outcome and therefore no P- attribute. The defect or pattern outcome is the step's classification; the P- attribute does not exist for that step to qualify it.
- (d) **Q-routing does not create or destroy the domain.** Whether a Q-missing step's components enter §3 is determined by the tree's T3 routing as already specified (REV-05 §4, retained): if T3 routes the step to §3 comparison (a component outcome is assigned, with the Q-defect carried as a secondary attribute where the tree so provides), the P- attribute follows that outcome under §2.2; if T3 exits before §3 comparison (SUBOPT-UNCLASS as the outcome-defining routing), no component outcome and no P- attribute. This revision does not change T3 routing; it only makes the P- domain follow the matrix assignment that routing already produces. A report must not assign P- attributes to SUBOPT-UNCLASS steps on the assumption that K classification "must have" been performed — it must cite the tree routing for that step.

**Per-component independence.** Domain membership is per component, not per step, in the following limited sense: the §3 matrix assigns outcomes per component, and a component's P- attribute follows its own outcome. In practice, both components of a K_rec = 1 step that reaches §3 receive outcomes together (the step-level K flag and defect routing are shared), while neither component of a K_rec = 0 or earlier-exit step receives one. The per-component statement matters only for §3's completability distinction (a partial phase expectation may be computable while a partial remaining expectation is not, under `est_full_cur = False` — see §3.1); it does not create a case in which one component of a K_rec = 0 step receives a P- attribute while the other does not, because K_rec = 0 steps do not enter the matrix at all.

### 2.2 Attribute assignment within the domain (retained from REV-07 §3.2, restated with domain qualifier)

For a component **in the domain** (i.e., with a component outcome), the attribute is determined exactly as in REV-07 §3.2, restated here with the domain qualifier made explicit so the table cannot be read as applying outside the domain:

- `est_full_cur = True` → **P-NOT-APPLICABLE** (partial-path consistency genuinely does not apply, because the full path governs; component outcome KF1/KF2 as applicable).
- `est_full_cur = False` + partial expectation computable + recorded matches partial expectation → **P-CONSISTENT** (component outcome: partial-match, KP-CORR row).
- `est_full_cur = False` + partial expectation computable + recorded differs from partial expectation → **P-INCONSISTENT** (component outcome: INCONSISTENT-C, KI row).
- `est_full_cur = False` + partial expectation incomputable + recorded equals true periodic value → **P-UNKNOWN** (component outcome: MATCH-TRUE, KP-TRUE row; cited as "true-matching, partial consistency unknown", never as "partially consistent").
- `est_full_cur = False` + partial expectation incomputable + recorded differs from true periodic value → **P-UNKNOWN** (component outcome: UNRESOLVED-C, KU1 row; cited as "true-differing, partial consistency unknown").
- `est_full_cur = Unknown` + partial expectation computable → **P-CONSISTENT** if recorded matches the partial expectation, **P-INCONSISTENT-IF-PARTIAL** if it differs (component outcome in both cases: MATCH-TRUE if recorded equals true, UNRESOLVED-C if it differs — the partial comparison determines the attribute only, conditionally, because the governing path is unknown; see §3.1).
- `est_full_cur = Unknown` + partial expectation incomputable → **P-UNKNOWN** (component outcome: MATCH-TRUE or UNRESOLVED-C by true comparison).

**Restated iff-claim (domain-qualified).** Within the domain, P-NOT-APPLICABLE occurs if and only if `est_full_cur = True`. Proof: by the table above, True rows assign NOT-APPLICABLE and no other row assigns it. Outside the domain, the attribute is undefined ("—") for every estimate state, including True — so the unqualified claim "P-NOT-APPLICABLE occurs iff True" is false as a claim about all components, and is superseded by this domain-qualified claim. Any report citing the unqualified claim must be corrected to the domain-qualified form.

**Table-row updates (superseding REV-07 §3.3 where stated).** KF rows (True): P-NOT-APPLICABLE (retained, now explicitly domain-qualified). KI rows (False + completable + INCONSISTENT-C): P-INCONSISTENT (retained). KU1 (False + incompletable + UNRESOLVED-C): P-UNKNOWN (retained). KP-CORR (False + completable + partial-match): P-CONSISTENT (retained). KP-TRUE (False + incompletable + MATCH-TRUE): P-UNKNOWN (retained). K_rec = 0 rows (availability states): "— (no component outcome)" (retained, now generalised by §2.1(b)–(c) to every no-outcome row, including defect-routed, FIELD-MISSING-PATTERN, and OPT rows, which must likewise show "—" and never a P- value). REV-07 §3.3's statement that K_rec = 0 rows show "—" is retained; REV-07 §3.3's completeness claim is superseded by §2.3 below.

### 2.3 Completeness claim and proof (restated for the restricted domain)

**Claim (governing).** Every component that enters the §3 comparison matrix receives exactly one P- attribute, and no component outside the matrix receives one. Equivalently: domain membership and P- attribute existence coincide.

**Proof (by case analysis over the domain).** Let c be a component in the domain. By §2.1(a)/(d), its step has K_rec = 1 and reaches §3, so `est_full_cur` is True, False, or Unknown, and for each component the partial expectation is either computable or incomputable (computability is per component: phase needs a clean opening; remaining needs a clean opening plus open_len — REV-04 §2.2, retained). Enumerate: (True, any computability) → NOT-APPLICABLE by §2.2 (partial comparison irrelevant under True); (False, computable) → CONSISTENT or INCONSISTENT by recorded-vs-partial relation, exactly one by excluded middle on equality; (False, incomputable) → UNKNOWN by §2.2 (recorded-vs-true relation determines the component outcome MATCH-TRUE/UNRESOLVED-C, while consistency is undetermined); (Unknown, computable) → CONSISTENT or INCONSISTENT-IF-PARTIAL by recorded-vs-partial relation; (Unknown, incomputable) → UNKNOWN. Every domain component falls in exactly one case, and each case assigns exactly one value. No case assigns two values, and no domain component falls outside the enumeration. Conversely, a component outside the domain has no component outcome by §2.1, and §2.1 defines its attribute as absent ("—"), so it receives no P- value. QED (as a proof about the rules, not about any data — see §7).

**What this proof does not show.** It does not show that any real record enters the matrix, that any recorded field satisfies the matrix preconditions, or that any partial expectation is in fact computable for a given record. Computability for a given record is a field-presence fact (provenance fields recorded or not), not a consequence of this proof. A report must establish domain membership per component from the record (K_rec, tree routing, provenance presence) before citing its P- attribute; it must not cite the proof as evidence that a component "must" have an attribute.

### 2.4 Alternative NOT adopted (explicit)

The owner's audit offered an alternative: introduce an explicit sixth value for "no component outcome". This alternative is **NOT adopted**. Reasons (stated so a future revision does not reintroduce it silently): (i) a sixth value would be counted, by any reader or script that sums P- values, as a consistency finding, when it asserts only that no comparison was performed; (ii) it would break the domain-qualified iff-claim in §2.2 (a no-outcome value would occur for True, False, and Unknown alike, while NOT-APPLICABLE is the True-only value within the domain); (iii) the existing absence marker "—" already serves the reporting need without creating a value that can be mistaken for a finding. If a future owner decision adopts a sixth value, it must redefine the domain, the iff-claim, and Table C P- counts together in one amendment — a single-table change is insufficient.

### 2.5 Counting consequence (Table C)

P- attribute counts in Table C (REV-07 §4.4, retained in form) are defined over **domain components only**. The denominator for any P- attribute count or proportion is the number of domain components in the relevant population, stated explicitly alongside the count. Steps or components outside the domain contribute zero to every P- count and zero to the denominator; they are shown in a separate "no component outcome (—)" count, never merged into any P- value count. A P- proportion whose denominator includes no-outcome components is invalid under this revision and must be recomputed.

## 3. Provenance-omission handling — component level and step level, separately (R8-02)

REV-07 §5.3/§5.4's sentence "true-matching fall-through (any est state) is never blocked by omission" and its §5.4 repetition ("recorded values matching the true schedule, 'any est state', permit fall-through") are **superseded in full** by this section. They must not be cited as governing. The replacement has two levels, and neither level uses "recorded = true, any est state" as a sufficient condition.

### 3.1 Component level — which comparison governs, for each estimate state

For a component in the domain (§2), exactly one comparison governs its **component outcome**. Omission affects the outcome only insofar as it removes the governing comparison's inputs. The table below is governing; the prose after it states the omission permissions that follow from it.

| Estimate state (step-level `est_full_cur`) | Partial expectation | Governing comparison for the component outcome | Component outcomes (recorded relation) | Effect of true-matching on the outcome |
| --- | --- | --- | --- | --- |
| True | Irrelevant (partial path does not govern; partial provenance omission does not affect the outcome) | Recorded vs true periodic value | Recorded ≠ true → K3-FULL (KF1). Recorded = true → fall-through-eligible outcome (KF2). | True-matching **is** the outcome-determining relation (KF2 vs KF1). |
| False | Computable (required partial provenance present: clean opening for phase; clean opening + open_len for remaining) | Recorded vs partial expectation (model-self-referential consistency test, REV-05 §3.4 principle, retained) | Recorded = partial → partial-match (KP-CORR row), fall-through-eligible. Recorded ≠ partial → INCONSISTENT-C (KI row), not fall-through-eligible. | True-matching has **no outcome-determining effect**. A component that equals the true value but differs from its partial expectation is INCONSISTENT-C. A component that equals both is partial-match (its true-matching is descriptive only, not the reason for the outcome). |
| False | Incomputable (required partial provenance omitted or unknown) | Recorded vs true periodic value, **for value-correctness only** (partial consistency undetermined) | Recorded = true → MATCH-TRUE (KP-TRUE row), fall-through-eligible as a component (see §3.3 for the step-level condition). Recorded ≠ true → UNRESOLVED-C (KU1 row), not fall-through-eligible. | True-matching determines the value outcome (MATCH-TRUE vs UNRESOLVED-C) but does **not** determine partial consistency (P-UNKNOWN in both cases, §2.2). |
| Unknown | Computable or incomputable | Recorded vs true periodic value, for the component outcome (MATCH-TRUE / UNRESOLVED-C). Partial comparison, when computable, determines the P- attribute only (P-CONSISTENT / P-INCONSISTENT-IF-PARTIAL, §2.2), conditionally, because the governing path is unknown. | Recorded = true → MATCH-TRUE, fall-through-eligible as a component. Recorded ≠ true → UNRESOLVED-C, not fall-through-eligible. | True-matching determines the value outcome. A partial mismatch under Unknown does **not** convert MATCH-TRUE to INCONSISTENT-C, because the partial path may not govern; it is carried conditionally in the attribute (P-INCONSISTENT-IF-PARTIAL), never as an outcome override. |

**Omission permissions that follow (component level).** (i) Under True, omission of the estimate tuple (first-estimates provenance), of period provenance, and of partial provenance does **not** block KF1/KF2 — flag sufficiency (REV-07 §5.1, retained as a True-branch rule). What blocks KF1/KF2 is not omission but contradiction: EST-PROV firing (VERIFIED NEVER, VERIFIED first-ordinal later than current ordinal, or genuinely absent open_len/last_opening held against True) routes to INVALID-EST-STATE, and a K-defect routes to INVALID-K, before §3 is reached. (ii) Under False + computable, the case is defined by partial provenance being present; omission of tuple/period does not block the partial comparison (it does not need them), and omission of the true reference does not block it either (true relation is irrelevant to the outcome). (iii) Under False + incomputable, omission of partial provenance **is** the cause of incomputability: it blocks the partial comparison (hence P-UNKNOWN) but does not block the value comparison (MATCH-TRUE/UNRESOLVED-C still assigned). Omission here therefore permits a value outcome while blocking a consistency outcome — the two must not be conflated. (iv) Under Unknown, omission of the tuple is the cause of Unknown; omission of partial provenance moves the component to the incomputable branch (P-UNKNOWN) but never blocks the value outcome. (v) Omission of VAL/AVAIL fields makes gate checks inapplicable (REV-07 §5.2, retained); it does not, by itself, assign or block a §3 component outcome, because gate inapplicability is a pre-§3 condition (if the gate cannot be evaluated, the step's K-defect status is undetermined, and the step must not be forced into §3 as if the gate had passed — see §3.4).

**Invariance rule (retained and restated).** Omission never converts a matrix-determined outcome into a different outcome. In particular: omission under True never converts KF1 to UNRESOLVED-C; omission under False + computable cannot occur for the governing inputs (if they were omitted, the case would be incomputable, not computable); omission under False + incompletable never converts MATCH-TRUE to a partial-match (there is no partial comparison to match) and never converts UNRESOLVED-C to INCONSISTENT-C (inconsistency requires a computable partial expectation to differ from). A report that describes an outcome as "defaulted to UNRESOLVED because provenance was omitted" must name the matrix row that actually assigns UNRESOLVED-C (False + incomputable + true-differing, or Unknown + true-differing) — otherwise the description is invalid.

### 3.2 What "fall-through" means at component level vs step level (terminology fixed)

- **Component-level fall-through-eligible outcome** means: the component's outcome, taken alone, does not block step-level fall-through. The eligible set is: KF2 (True + true-matching), partial-match (False + computable + partial-matching), MATCH-TRUE (False + incomputable + true-matching, or Unknown + true-matching). The ineligible set is: KF1 (K3-FULL), INCONSISTENT-C, UNRESOLVED-C. Note that MATCH-TRUE is eligible **as a component** — it does not by itself block fall-through — but eligibility as a component is not sufficient for step-level fall-through (§3.3).
- **Step-level fall-through** means: the step proceeds to pattern classification (HEAD / SEL / SUBOPT-UNCLASS as applicable under the tree) with no K-class or K-status-line outcome assigned as its step outcome. Step-level fall-through is a property of the **complete component combination**, defined in §3.3. It is not a property of any single component.
- **K outcome (non-fall-through)** means: the step's outcome is a K-class (K3-FULL, K3-UNRESOLVED) or a K-status line (K3-PARTIAL-INCONSISTENT), as determined by the combination rule in §3.3, and the step does not proceed to pattern classification as a K-cleared step. (A K-status-line step's waste is unassigned and descriptive-only, per REV-05 §3.4, retained; a K-class step's waste follows its class assignment rules, per REV-05 §6 / REV-06 §6, retained.)

### 3.3 Step level — fall-through permitted only for a complete eligible combination (governing)

**Rule (governing).** A step falls through to pattern classification if and only if **all** of the following hold:

1. K_rec = 1 (the step is not an availability state; availability steps have step outcomes KBLANK/KNEVER/KUNK/K-STATUS-UNKNOWN and never fall through as K-cleared steps).
2. The step reaches §3 comparison (no winning defect, FIELD-MISSING-PATTERN, or OPT exit before §3, per §2.1).
3. Every domain component's outcome is fall-through-eligible under §3.2 (KF2, partial-match, or MATCH-TRUE, as applicable to that component's estimate/completability combination).
4. No component outcome is KF1, INCONSISTENT-C, or UNRESOLVED-C.

**Combination consequences (all follow from the rule; stated explicitly so no single-component citation can override them).**

- True branch: all components KF2 → fall-through. Any component KF1 → step outcome K3-FULL (not fall-through), regardless of the other component's outcome. (Both components share the step-level estimate state True, so the KF1/KF2 split is per component; one KF1 suffices to block fall-through.)
- False + computable (per component): all components partial-match → fall-through. Any component INCONSISTENT-C → step outcome K3-PARTIAL-INCONSISTENT (status line, unassigned waste, descriptive-only), regardless of the other component's outcome — including the case where the other component is true-matching. **This is the owner's counterexample, now stated as a rule: recorded = true for one component, with a partial mismatch for that same component under False + computable, is INCONSISTENT-C and blocks fall-through; recorded = true for the other component does not cure it.**
- False + incomputable (per component) and Unknown (per component): all components MATCH-TRUE → fall-through. Any component UNRESOLVED-C → step outcome K3-UNRESOLVED (class, unassigned waste), regardless of the other component's outcome. **This is the owner's step-level distinction, now stated as a rule: one MATCH-TRUE component does not establish fall-through if the other component is UNRESOLVED-C (or INCONSISTENT-C, in a mixed-completability case below).**
- Mixed completability under False (the case the per-component table makes possible): phase computable, remaining incomputable (or vice versa) is a legitimate combination, because computability is per component (§2.3). Step fall-through in a mixed case requires **each** component's outcome to be eligible **under its own combination**: e.g., phase partial-match (eligible) + remaining MATCH-TRUE (eligible) → fall-through permitted; phase partial-match + remaining UNRESOLVED-C → NOT fall-through (step outcome K3-UNRESOLVED, because the blocking component's outcome is UNRESOLVED-C); phase INCONSISTENT-C + remaining MATCH-TRUE → NOT fall-through (step outcome K3-PARTIAL-INCONSISTENT, because the blocking component's outcome is INCONSISTENT-C). If both a blocking INCONSISTENT-C and a blocking UNRESOLVED-C occur in the same step (possible only in a mixed-completability False case, or in a step whose components were assigned under different branches by an error), the step outcome precedence is: INCONSISTENT-C (demonstrated internal inconsistency against a known governing path) takes precedence over UNRESOLVED-C (undetermined) for the step's status-line/class label, and **both** component outcomes are retained in the component table (the step label does not erase the other component's outcome). This precedence is for labelling the step outcome only; it does not change either component's outcome, its P- attribute, or its waste treatment (both components' waste follows the step outcome's unassigned treatment — see §3.4).
- **No partial fall-through.** There is no such outcome as "fall-through for the matching component, K outcome for the other". Fall-through is step-level and all-or-nothing. A report that counts a step as both a pattern step (HEAD/SEL) and a K-class/status-line step double-counts it and violates the single-counting rule (REV-07 §4, retained).

### 3.4 Omission and the pre-§3 gates (boundary stated)

§3.1–§3.3 govern components **in the domain** (steps that reach §3). They do not govern steps that never reach §3 because a gate or defect check could not be evaluated due to omission. If VAL/AVAIL fields are omitted so a K-gate check is inapplicable, or if the estimate tuple is omitted so EST-PROV clause (a) cannot be evaluated, the step's pre-§3 status is **undetermined**, not "passed". Such a step must not be assigned a §3 component outcome, a P- attribute, or a fall-through outcome on the assumption that the unevaluated check would have passed. It is held as unclassified-pending for the affected attribution (reported with the omitted field named), unless another tree rule independently determines its outcome (e.g., a FIELD-MISSING-PATTERN exit on a different field, or a demonstrated defect on a present field). This boundary is the step-level analogue of REV-07 §2's Stage-A rule (unknown required condition ≠ pass); §3 does not override it, and §3's omission permissions apply only within §3, after the gates have been evaluated or held as above.

### 3.5 Worked combinations (illustrative, derived from §§3.1–3.3, not new rules)

- **W1 (True, both true-matching):** phase KF2, remaining KF2 → step falls through. Omission of tuple/period does not change this (flag sufficiency, True branch).
- **W2 (False + computable, phase partial-matching, remaining partial-mismatching but true-matching):** phase partial-match (eligible), remaining INCONSISTENT-C (blocking) → step outcome K3-PARTIAL-INCONSISTENT, no fall-through. The remaining component's true-matching is descriptive only and must not be cited as a fall-through match.
- **W3 (False + incomputable, phase MATCH-TRUE, remaining UNRESOLVED-C):** phase eligible as a component, remaining blocking → step outcome K3-UNRESOLVED, no fall-through. The phase MATCH-TRUE must not be cited as establishing fall-through.
- **W4 (False mixed: phase computable partial-match, remaining incomputable MATCH-TRUE):** both eligible under their own combinations → step falls through. The fall-through rests on the combination, not on either component alone, and the report must cite both.
- **W5 (Unknown, phase MATCH-TRUE with partial mismatch, remaining MATCH-TRUE with partial match):** both components MATCH-TRUE → step falls through; phase attribute P-INCONSISTENT-IF-PARTIAL (conditional, §2.2) is carried alongside the fall-through, not as a block. The conditional attribute must not be cited as an INCONSISTENT-C outcome.

## 4. Missing recorded phase — field requirement and outcome per check, then reconciliation (R8-03)

### 4.1 The two checks, defined independently

There are two distinct checks that both involve recorded phase. They answer different questions, operate at different levels, and have different outcome sets. Defining them independently first is what makes the reconciliation in §4.3 possible; collapsing them into one "T0 check" is the error REV-07 left open.

**Check T (tree T0, step classification, P0 → P1).** Object: the step's recorded state as a classifiable record. Requirement, split into two sub-checks:

- **T0-P (presence):** the T0 fields are present. "T0 fields" means the fields required to place the step in sequence and identify it, as defined in REV-05 §4 / REV-06 §2.3 (retained), **excluding** recorded phase itself, **excluding** `door_open_pre` (handled by Stage-A A3 / tree transition check), and **excluding** `position_after` (handled by Stage-A A5 / waste computability). If any T0 field as so defined is missing, T0-P fails.
- **T0-C (comparison):** recorded phase is present **and** consistent with `t_pre` (i.e., recorded phase equals the true phase derived from `t_pre` under the stable 20/10 schedule, per REV-01 §3 clock rules, retained). Recorded phase here means R-FEAT-PHASE-VAL (raw value), not the blanked slot (R-SLOT-PHASE, which is 0.0 under K = 0 and must never be compared as an estimate, per REV-04 §2.2, retained) and not a derived value (see §4.4 no-substitution rule, retained from REV-07 §2.1).

Outcomes for Check T (governing, §4.2):

- T0-P fails (T0 field missing) → step outcome **INVALID-RECORD** (defect outcome, D1-class presence failure; see §4.2 precedence).
- T0-P passes + T0-C present-but-inconsistent (recorded phase present, differs from `t_pre`-derived true phase) → step outcome **INVALID-RECORD** (demonstrated inconsistency).
- T0-P passes + T0-C present-and-consistent → T0 passes; step proceeds to subsequent tree routing (OPT, defect precedence, §3 as applicable).
- T0-P passes + recorded phase missing → step outcome **FIELD-MISSING-PATTERN** (see §4.2 rationale). T0-C is **unevaluable** for this step (comparison cannot be performed without a recorded value), and unevaluability here does **not** produce INVALID-RECORD in the tree — it produces the field-missing pattern outcome, for the reason in §4.2.

**Check A (Stage-A A4, episode eligibility, P3 Stage A).** Object: whether an episode's conformance is **established** well enough for P3-final membership. Requirement, split into two sub-checks mirroring Check T:

- **A4-P (presence):** the same T0 fields as T0-P (same definition, same exclusions) are present for every step in the episode that is a candidate for T0 comparison (see §4.2 scope note). If any such step lacks a T0 field, A4-P fails for the episode.
- **A4-C (comparison):** for every such step, recorded phase is present **and** consistent with `t_pre` (same comparison as T0-C). If any such step's recorded phase is missing, A4-C is **unevaluable** for the episode. If any such step's recorded phase is present but inconsistent, A4-C fails for the episode.

Outcomes for Check A (governing, §4.2, under REV-07 §2.3 two-tier determination, retained):

- A4-P fails → episode final-status contribution **FAIL INVALID-RECORD** (FAIL tier; FAIL dominates UNEVALUABLE regardless of check order, per REV-07 §2.3).
- A4-P passes + A4-C present-but-inconsistent for any step → **FAIL INVALID-RECORD**.
- A4-P passes + A4-C present-and-consistent for all steps → A4 passes (episode proceeds to subsequent Stage-A checks / Stage B as applicable).
- A4-P passes + A4-C unevaluable (any step's recorded phase missing, T0 fields present) → **UNRESOLVED-INVALID-RECORD** (UNRESOLVED tier; episode eligibility not established, not a demonstrated violation). This retains REV-07 §2.2's UNRESOLVED-INVALID-RECORD code and reachability (recorded-phase absent with T0 fields present), now with its tree counterpart defined in §4.2.

### 4.2 Tree outcome for missing recorded phase — FIELD-MISSING-PATTERN (governing, with rationale)

**Rule.** A step with T0 fields present but recorded phase missing receives the tree outcome **FIELD-MISSING-PATTERN**, not INVALID-RECORD. Rationale (stated so the distinction is auditable, not merely asserted): INVALID-RECORD in the tree is reserved for (i) presence failure of the step's identity/ordering fields (without which the step cannot be placed in sequence at all) and (ii) demonstrated inconsistency (a present value that contradicts its specification). A missing **feature** value (recorded phase) is neither: the step can still be placed in sequence (T0 fields present), counted in denominators, and described, but its phase consistency cannot be evaluated. The existing FIELD-MISSING-PATTERN bridge (REV-04 §5 / REV-05 §5, retained) is exactly the outcome for that situation: denominator in P2, unassigned waste in P3-final episodes, no class count, and (by REV-07 §4) attribute occurrences recorded separately without creating outcome summands. Assigning INVALID-RECORD to a missing feature value would conflate "not shown to be consistent" with "shown to be inconsistent" — the same conflation REV-07 §2 corrected at Stage-A level, now corrected at tree level as well.

**Precedence within Check T.** If both T0-P fails (T0 field missing) and recorded phase is missing, the step outcome is INVALID-RECORD (T0-P dominates, because the step cannot be placed). If T0-P passes and recorded phase is missing, the outcome is FIELD-MISSING-PATTERN (above). If T0-P passes and recorded phase is present but inconsistent, the outcome is INVALID-RECORD (demonstrated inconsistency dominates the field's mere presence). This precedence is exhaustive for Check T: every step falls in exactly one of the four rows in §4.1.

**Scope note (candidates for T0 comparison).** A4-C and T0-C are evaluated over steps that are candidates for T0 comparison — i.e., steps not already excluded by step-type exclusion (CRUSH-ND, TERMINAL, UNREACH as defined in REV-02 §2 / REV-05 §5, retained) before T0 is reached. A step excluded by type does not create an A4-C UNRESOLVED, because T0 comparison is not performed for it; its exclusion reason stands on its own. This scope note follows tree order (type exclusion precedes T0 comparison for those classes) and does not narrow REV-07 §2.2: REV-07 §2.2's UNRESOLVED-INVALID-RECORD reachability was stated for steps with T0 fields present, and type-excluded steps are not T0-comparison candidates in the first place. If a future collection evaluates A4-C over all steps including type-excluded ones, it must state that scope explicitly and must not count type-excluded steps as additional UNRESOLVED-INVALID-RECORD episodes beyond their type exclusion (single-counting, REV-07 §4, retained).

### 4.3 Reconciliation across tree, I0/I1, and Stage-A eligibility (governing)

The three levels now reconcile as follows, and a report must show all three consistently or state explicitly where it does not:

| Case (T0 fields present unless stated) | Tree outcome (step, I0) | Stage-A outcome (episode, ledger) | P3-final consequence |
| --- | --- | --- | --- |
| T0 field missing (any step) | INVALID-RECORD | FAIL INVALID-RECORD (A4-P, FAIL tier) | Episode not P3-final (FAIL exclusion). |
| Recorded phase present, inconsistent with `t_pre` | INVALID-RECORD | FAIL INVALID-RECORD (A4-C, FAIL tier) | Episode not P3-final (FAIL exclusion). |
| Recorded phase present, consistent with `t_pre` | T0 passes (step proceeds) | A4 passes for this step (episode proceeds, subject to other checks) | No exclusion from this step. |
| Recorded phase missing, T0 fields present | **FIELD-MISSING-PATTERN** | **UNRESOLVED-INVALID-RECORD** (A4-C, UNRESOLVED tier) | Episode not P3-final (UNRESOLVED exclusion, unless a FAIL on another check dominates — see below). |

**Why the fourth row's two labels are not contradictory.** They answer different questions. I0 answers: "How is this step counted?" Answer: as a field-missing step — counted in the P2 denominator, assigned no pattern class, contributing unassigned waste if (counterfactually) its episode were P3-final, which it is not. Stage-A answers: "Is this episode's conformance established?" Answer: not established for phase consistency, because the comparison could not be performed — so the episode cannot be certified P3-final. A step can be **counted** (I0) while its episode is **uncertified** (Stage-A), because P3-final requires established conformance, not merely counted steps. The labels differ because the tests differ; the reconciliation is that both labels are shown, with their dimensions named ("I0: FIELD-MISSING-PATTERN" vs "Stage-A: UNRESOLVED-INVALID-RECORD"), never merged into a single "invalid" count.

**I0/I1 consequence.** Steps in the fourth row contribute one I0 summand to n_FIELD-MISSING-PATTERN and zero summands to n_INVALID-RECORD. Reports that previously (under REV-07's gap) might have counted missing-phase steps as INVALID-RECORD in I0 must be corrected to FIELD-MISSING-PATTERN. The I1 status-line breakdown for FIELD-MISSING-PATTERN must be reconcilable: the sub-count of FIELD-MISSING-PATTERN steps whose missing field is recorded phase must be stated (as a sub-count, not as a separate I0 summand) so it can be checked against the Stage-A ledger's UNRESOLVED-INVALID-RECORD episodes (see ledger note below).

**Stage-A ledger consequence.** Episodes in the fourth row contribute one ledger entry to the UNRESOLVED section with code UNRESOLVED-INVALID-RECORD, and zero entries to the FAIL section for A4 (unless another check FAILs — see below). Descriptive waste for such episodes may be shown only where computable, labelled "descriptive only; eligibility not established" (REV-07 §2.4, retained).

**FAIL-dominance interaction (stated so the reconciliation survives multi-check episodes).** Under REV-07 §2.3 two-tier determination (retained), if an episode has both a FAIL on any check (e.g., A1 PROTOCOL) and an A4-C UNRESOLVED (missing phase), its **final** Stage-A status is the FAIL (first failing check in A1→A6 order), and it is counted in I5 as a FAIL exclusion, not as an UNRESOLVED exclusion. The underlying A4-C UNRESOLVED reason must still be recorded in the ledger entry (ledger entries record every FAIL and UNRESOLVED reason found; final status is single per the two-tier rule — clarification of REV-07 §2.4, which required exactly one final status but did not state whether underlying reasons are retained; they are). Step-level I0 counting is independent of episode final status: the missing-phase step still counts as FIELD-MISSING-PATTERN in I0 even when its episode's final status is FAIL on another check. A reconciliation that equates "episodes with final status UNRESOLVED-INVALID-RECORD" with "episodes containing a missing-phase step" is therefore invalid; the correct reconciliation is at step level (FIELD-MISSING-PATTERN sub-count for recorded phase) against ledger entries **recording** UNRESOLVED-INVALID-RECORD as a reason (final or underlying), not against final statuses alone.

### 4.4 Rules retained (no-substitution, T0-field definition)

- **No-substitution rule (REV-07 §2.1, retained).** A missing recorded phase must never be replaced by the `t_pre`-derived true phase (or by any derived, interpolated, or sibling-step value) for T0-C/A4-C purposes. Derivation would substitute the specification for the record and would falsely convert an unevaluable comparison into a PASS. The true phase is the **comparison target**, never a substitute for the recorded value.
- **T0-field definition (supersession note).** If any REV-05/REV-06 text lists recorded phase among the T0 fields whose absence is a presence failure, that listing is **superseded** by §4.1: recorded phase is removed from the T0 presence set and placed in the comparison set (T0-C/A4-C). All other T0 fields retain their REV-05/REV-06 definitions. A future collection plan must cite §4.1's T0-field set (presence set excluding recorded phase, `door_open_pre`, and `position_after`, each handled by its own check), not an earlier listing that includes recorded phase as a presence field.
- **Other Stage-A checks unchanged.** A1 (PROTOCOL), A2 (SEQUENCE), A3 (TRANS-PATH, including `door_open_pre` missing → UNRESOLVED-TRANS-PATH), A5 (WASTE-UNDEFINED / computability), and A6 (REPAIRED, including flag unrecorded → UNRESOLVED-REPAIRED) retain their REV-07 §2.2 definitions, sources, and reachability, except that A4 is now read as A4-P + A4-C per §4.1. The two-tier determination (FAIL first, then UNRESOLVED, then PASS) is retained unchanged.

## 5. I5 terminology — "failed episode" retired as an unqualified term (R8-04)

### 5.1 Three terms, fixed meanings (governing)

- **Non-success episode** (episode-outcome term): an episode in scope that did not reach the goal. "In scope" means: in the episode population for the claim being reconciled (P3-candidate episodes for I5 — see §5.2). Non-success says nothing about any check: a non-success episode may be P3-final, Stage-A FAIL, Stage-A UNRESOLVED, or P3-INVALID. It is the neutral total term.
- **Stage-A FAIL episode** (check-outcome term): an episode whose **final** Stage-A status is FAIL (a demonstrated failure of at least one Stage-A check, determined by the two-tier rule, REV-07 §2.3, retained). "FAIL" without the "Stage-A" qualifier, when used for an episode, must be read as Stage-A FAIL and must not be used for the episode outcome.
- **Stage-A UNRESOLVED episode** (check-outcome term): an episode whose **final** Stage-A status is UNRESOLVED (eligibility not established for at least one mandatory check, with no FAIL). An UNRESOLVED episode has **not** violated, failed, or been shown nonconformant on the unevaluable check; it has not been shown conformant either.

**Prohibited term (governing).** The unqualified phrase **"failed episode"** (and its variants "failed episodes", "episode failures", "failure count" for episodes) **must not be used** in any report, table, ledger, or summary under this specification, because it is ambiguous between the episode outcome (did not reach the goal) and the check outcome (failed Stage A). Every occurrence must be replaced by one of the three terms above, as applicable, or by "P3-INVALID episode" where that is the intended meaning. A report that uses "failed episode" without a qualifier must be corrected before its totals are evaluated; a total labelled "failed" that sums FAIL + UNRESOLVED exclusions is invalid under this revision, because it presents unresolved eligibility as violation.

**Related terms (clarified, not changed).** "Failed step" is not a term in this specification and must not be introduced as a synonym for any step outcome (use the step's actual outcome: INVALID-RECORD, FIELD-MISSING-PATTERN, K-class, status line, HEAD, SEL, SUBOPT-UNCLASS, OPT, etc.). "Non-success step" is likewise not a term; steps do not succeed or fail in the episode sense (a step's outcome is its classification, and a step on a non-success episode's path may itself be OPT, HEAD, or any other classification). "P3-final episode" means a non-success episode that passed Stage-A/B/C (it is a subset of non-success episodes, never a subset of successful episodes, because waste accounting in this track is defined over non-success episodes only — see §5.2).

### 5.2 I5 identity restated with the renamed quantity (governing; arithmetic unchanged)

**I5 (REV-08 form).** Let S be the set of non-success episodes in scope for the claim. Then:

> #non-success-episodes-in-scope
> = #P3-final
> + Σ FAIL codes (PROTOCOL + SEQUENCE + NONCONF-PATH + INVALID-RECORD + WASTE-UNDEFINED + REPAIRED, counting episodes by **final** Stage-A status)
> + Σ UNRESOLVED codes (PROTOCOL + SEQUENCE + TRANS-PATH + INVALID-RECORD + WASTE + REPAIRED, counting episodes by **final** Stage-A status; SEQUENCE and WASTE terms are zero under current definitions, included for code-set completeness — a non-zero value for either indicates an evaluation error, per REV-07 §2.4, retained)
> + #P3-INVALID/TELESCOPE + #P3-INVALID/NO-F

**Scope rule (governing).** Every term in I5 counts **non-success episodes only**. If Stage-A is evaluated over all episodes (including successful ones), successful-episode Stage-A results are reported separately and are **excluded** from I5 entirely; they must not be added to any I5 term, and they must not be used to inflate or deflate the non-success total. Conversely, a non-success episode is in S whether its Stage-A status is PASS (→ P3-final, subject to Stages B/C), FAIL, UNRESOLVED, or P3-INVALID; there is no non-success episode in scope outside the right-hand terms, and no right-hand term counts an episode outside S. The identity is a partition of S by final eligibility/accounting status, not a partition of all episodes.

**Reading rule (governing).** I5 must be read as: "Of the non-success episodes in scope, this many were P3-final (accountable), this many were excluded for demonstrated Stage-A failures (by code), this many were excluded because eligibility was not established (by code), and this many were P3-invalid (by sub-reason)." It must never be summarised as "X episodes failed Stage A" (which would merge FAIL + UNRESOLVED) or as "X failed episodes" (which would merge the episode outcome with check outcomes). The summary sentence form above is the required form; any shorter summary must preserve the FAIL/UNRESOLVED split and the non-success qualifier.

**Interaction with §4.3 (ledger reasons vs final statuses).** I5 counts episodes by **final** Stage-A status (single status per episode, two-tier rule). Ledger entries record every reason found (final + underlying, §4.3). Therefore: Σ FAIL codes in I5 = number of episodes whose final status is FAIL, broken by their FAIL code (first failing check); Σ UNRESOLVED codes in I5 = number whose final status is UNRESOLVED, broken by their UNRESOLVED code (first unevaluable check). An episode whose final status is FAIL but which also has an underlying UNRESOLVED reason (e.g., missing phase, §4.3) contributes to the FAIL term only in I5, and its underlying UNRESOLVED reason appears in the ledger entry but not in the I5 UNRESOLVED sum. A reconciliation that sums ledger **reasons** instead of final statuses will overcount I5 and is invalid; the reconciliation must state whether it sums final statuses (I5) or reasons (ledger audit), and must not present one as the other.

### 5.3 Flow-table and Table C wording updates (governing)

- Flow-table Stage-A box (REV-07 §4.4, retained in form): its three exits are now labelled "PASS → Stage B", "FAIL (Stage-A FAIL) → ledger FAIL section", "UNRESOLVED (Stage-A UNRESOLVED) → ledger UNRESOLVED section". The word "failed" must not appear as an exit label.
- Table C ledger summary (REV-07 §4.4, retained in form): the summary row formerly headed (in REV-07's I5/flow wording) by a failed-episode total is now headed "#non-success-episodes-in-scope", with separate sub-rows for #P3-final, FAIL by code, UNRESOLVED by code, and P3-INVALID by sub-reason. No row may be headed "failed" without the "Stage-A" qualifier and the final-status meaning stated.
- P4 gate wording (REV-07 §2.4, retained in substance): "zero FAIL and zero UNRESOLVED exclusions" is now written as "zero Stage-A FAIL exclusions and zero Stage-A UNRESOLVED exclusions" wherever it appears, so the gate condition cannot be misread as a condition on episode outcomes.

**Specification consistency — what is now established (formally, within the text, subject to owner approval):**
- The P- attribute no longer contradicts its own table (§2): the domain is exactly the set of components that enter the §3 matrix, the five values keep their REV-07 meanings within that domain, no-outcome components show "—" (absence, not a finding, never counted), the iff-claim is domain-qualified, and the completeness proof is proved over the domain by exhaustive case analysis (True/False/Unknown × computability).
